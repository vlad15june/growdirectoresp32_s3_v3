# Отладка датчиков через MQTT

Гоняет команды работы с RS485-шиной на **живой модуль в поле** через MQTT-брокер и читает ответы датчиков. Прошивать/подключать кабель не нужно — модуль уже слушает команды `ModuleCommandNotification`.

Канонические доки (specs-репо, резолв по CLAUDE.md `.specs-repo.local`→`.specs-repo`):
- [features/module-command/raw-bus-cli-guide.md](specs/docs/features/module-command/raw-bus-cli-guide.md) — транспорт: как команды летят через MQTT, топики, лимиты, обработка ошибок.
- [features/sensor/modbus-sensor-address-commands.md](specs/docs/features/sensor/modbus-sensor-address-commands.md) — per-model справочник: регистры данных, чтение/смена адреса, готовые HEX-кадры.
- [contracts/backend-firmware/06-module-commands.md](specs/docs/contracts/backend-firmware/06-module-commands.md) — полный контракт команд.

## Главное правило: работать через CLI, не через сырой mosquitto

Весь обмен идёт **только** через [gd_sensor.py](.claude/skills/sensor-mqtt-debug/gd_sensor.py), лежащий рядом с этим скилом. Он экономит токены: один вызов = подписка + публикация + ожидание + разбор кадра + декод в одну строку. **Не** плодить руками `mosquitto_sub` в фоне + `mosquitto_pub` + чтение JSON + ручной разбор CRC — это то, что CLI автоматизирует.

CLI сам:
- берёт брокер/порт/юзера/пароль из [src/globals.h](src/globals.h) (пароль в скрипт не зашит);
- собирает payload `ModuleCommandNotification`, шлёт на `GrowDirectorMqttTopic/{uid}`;
- слушает `hardware/command_result/{uid}` и `hardware/raw_io_result/{uid}`;
- разбирает ответный кадр (адрес, функция, слова 16-бит, проверка CRC16-Modbus) и по флагу декодит инженерные значения.

## Вход

Нужен **UID модуля** (MAC, `XX:XX:XX:XX:XX:XX`). Передавать через `GD_UID` (env) или `--uid`.
Если UID не задан — спросить у пользователя (AskUserQuestion), не выдумывать.

Опционально уточнить у пользователя: какой порт/канал (0–3), модель датчика (для правильных регистров), что делаем (пинг / поиск адреса / чтение данных / смена адреса).

## Запуск

```bash
export GD_UID=<MAC модуля>
python3 .claude/skills/sensor-mqtt-debug/gd_sensor.py <команда> [флаги]
```

Общие флаги: `--timeout <сек>` (дефолт 2.5), `--retries <N>` (повтор по таймауту перед вердиктом «мёртво»; дефолт 0 = честная одна проба), `--print-cmd` (показать эквивалентные mosquitto-команды, пароль маскируется без `--show-pass`).

### Команды

- `read --channel C --address A --register R [--function 3] [--count 1] [--decode xf700a]`
  ModbusRead: прошивка сама считает CRC. `A`/`R` можно в hex (`0x70`, `0x0009`). Основной пинг данных.

- `read-addr --channel C [--register 0x0001]`
  Broadcast-чтение (address 0) текущего ModBus-адреса станции. `0x0001` для группы MP508/CGH/WS301/GW/VS09, `0x0000` для XF-серии (XF500S/SL/700A). В ответе выделяет байт адреса.

- `scan-addr --channel C --from 0x70 --to 0x73 [--register 0x0009] [--decode xf700a]`
  Перебор диапазона адресов на одном канале за **один вызов**. В конце — список ответивших (`# responders:`). Для перебора флаки-шины ставить `--retries 1..2`.

- `scan-ports --channels 0,1,2,3 --address A [--register 0x0009]`
  Одна пара адрес/регистр по нескольким каналам. В конце — список ответивших каналов.

- `write --channel C --address A --register R [--function 16] --data HEX`
  ModbusWrite (CRC считает прошивка). `--data` — байты **после регистра**, без CRC. ⚠️ меняет состояние устройства (адрес и т.п.) — на шине должен быть **один** датчик; после записи проверять `read`.

- `serial --channel C --bytes HEX [--no-expect]`
  SerialWrite: кадр уходит на линию **как есть**, ты передаёшь полный кадр **с CRC** (например готовую HEX-строку из дока по датчикам). `--no-expect` — не ждать ответа.

- `crc HEX`
  Offline-хелпер: дописать CRC16-Modbus к неполному кадру (для ручной сборки `serial`-кадров). Устройство не трогает.

## Как читать вывод

Одна строка на пробу:
- `... | OK  frame=<hex> addr=0xNN words=[...] crc=ok [декод]` — датчик ответил, кадр разобран, CRC сверен.
- `... | TIMEOUT (Read timeout)` — команда дошла до модуля, но датчик на шине не ответил за ~1000 мс.
- `... | ERROR: Invalid channel|Invalid hex bytes` — модуль отверг команду, на шину ничего не ушло.

`OK` со сходящимся CRC = датчик жив. Валидность инженерного значения (температура и т.п.) зависит от того, верны ли регистр и модель.

## Типовые сценарии

- **Жив ли датчик на порту N** (модель XF700A, адрес 0x70):
  `read --channel N --address 0x70 --register 9 --decode xf700a`
- **Найти адрес на порту N** (диапазон): `scan-addr --channel N --from 0x00 --to 0x7F --retries 1` (долго; сужать диапазон, если известен вендорский).
- **На каком порту сидит датчик** (адрес 0x70): `scan-ports --address 0x70 --register 9 --retries 1`
- **Узнать текущий ModBus-адрес** (один датчик на шине): `read-addr --channel N --register 0x0000` (XF-серия) или `0x0001` (группа MP508).
- **Сменить адрес** — по нужной модели из [modbus-sensor-address-commands.md](specs/docs/features/sensor/modbus-sensor-address-commands.md): собрать `write`/`serial`, затем проверить `read-addr`/`read`.

## Источник правды для декода и добавление моделей

Пересчёт сырых слов в физические величины — **в CLI**, в карте `SENSOR_DECODERS` в [gd_sensor.py](.claude/skills/sensor-mqtt-debug/gd_sensor.py). Это источник правды для инженерных значений; скрипт делает основную работу. `--decode <model>` автоматически подхватывает любую модель, добавленную в карту.

Модели добавляются **по мере тестирования на живом датчике**, не пачкой из даташита наперёд:
1. Снять сырые слова: `read --channel C --address A --register R --count N` (или `scan-addr`), убедиться `crc=ok`.
2. Сверить регистры и формулы по [modbus-sensor-address-commands.md](specs/docs/features/sensor/modbus-sensor-address-commands.md) для этой модели.
3. Добавить запись `"<model>": { <register>: ("<name>", <lambda>, "<unit>"), ... }` в `SENSOR_DECODERS`.
4. Прогнать `read ... --decode <model>` на живом датчике и глазами проверить, что значения осмысленны.

**Согласованность обязательна:** значения `--decode` должны сходиться с реальным датчиком и с формулами дока. При расхождении приоритет — за поведением живого датчика: поправить карту в CLI и, если разошлось с доком, синхронизировать док.

## Жёсткие правила

- **Все команды — через `gd_sensor.py`.** Сырой `mosquitto_pub/sub` руками — только если CLI физически не покрывает кейс; тогда сперва подумать, не добавить ли подкоманду.
- **Пароль не печатать** в чат и не хардкодить в артефакты. `--print-cmd` маскирует его по умолчанию; `--show-pass` — только по явной просьбе.
- `write`/`serial` меняют железо — перед записью убедиться, что на шине один датчик, и предупредить пользователя (см. [feedback_approve_before_edit]). Для смены адреса брать точный кадр из дока по датчикам, а не сочинять.
- **Декод-значения — из CLI (`SENSOR_DECODERS`), это источник правды.** Регистры и схему адреса при добавлении модели сверять с [modbus-sensor-address-commands.md](specs/docs/features/sensor/modbus-sensor-address-commands.md). Не путать схемы адреса: у группы MP508 адрес в регистре `0x0001` по broadcast 0, у XF-серии — в `0x0000`, данные с `0x0009`. Модель добавлять только после проверки на живом датчике (см. раздел «Источник правды для декода»).
- **Timeout — это факт, а не баг.** Не маскировать его ретраями по умолчанию: `--retries` включать осознанно (перебор/флаки-шина), в отчёте отделять «ответил с N-й попытки» от «ответил сразу».
- Выводы про шину строить только на фактическом ответе (`OK` + сошедшийся CRC), не на ожиданиях.
