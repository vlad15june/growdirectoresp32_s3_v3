# Создание архитектурного дока фичи (firmware)

Скил для проектирования firmware-части архитектуры фичи GrowDirector. Результат — markdown-файл **на русском языке** в `specs/docs/features/<feature>/jira-tickets/firmware/` строго по структуре шаблона `specs/templates/arch-doc-template.md`.

## Шаги (выполнять строго по порядку, не пропускать)

### Шаг 1. Определить фичу

**Обязательно через AskUserQuestion**, если из запроса пользователя неоднозначно понятно, какую фичу архитектурить. Спросить:

> Какую фичу архитектурим? Назови имя фичи (например `workflow`) или укажи путь к папке с её доками в `specs/docs/features/`.

После ответа резолвить путь: `specs/docs/features/<feature>/`. Проверить, что папка существует. Если нет — остановиться и спросить.

### Шаг 2. Уровень дока: feature или phase

**Обязательно через AskUserQuestion**:

> Это арх-док целой фичи (feature-level) или одной фазы (phase-level)?

- **Feature-level** — описывает всю firmware-часть фичи end-to-end, включает секцию «Дорожная карта по фазам».
- **Phase-level** — описывает одну фазу, ссылается на feature-doc, в конце добавляет секцию «Граница с другими фазами», без «Дорожной карты по фазам».

Если phase-level — дополнительно спросить номер и короткое имя фазы.

### Шаг 3. Прочитать контекст

В этом порядке, обязательно:

1. **Шаблон**: `specs/templates/arch-doc-template.md` — единственный источник структуры. Все секции и их порядок берутся отсюда.
2. **Доки фичи** в `specs/docs/features/<feature>/`: `index.md`, `overview.md`, `firmware.md` (если есть), `contracts/`, `questions.md`, `biz/`. Цель — понять замысел фичи, границы, что уже описано на уровне всей фичи.
3. **Существующая firmware-архитектура**: `specs/docs/components/firmware/` — `index.md`, `projectArchitecture.md`, `projectStructureDirectoryDescription.md`, и любые тематически близкие файлы (например `sensor-models.md`, `sensorOperationsGuide.md`).
4. **Если phase-level** — обязательно прочитать существующий feature-level арх-док в `specs/docs/features/<feature>/jira-tickets/firmware/` (если его нет — остановиться и предложить сначала сделать feature-level).
5. **Соседние firmware арх-доки других фич** в `specs/docs/features/*/jira-tickets/firmware/` — для согласованности тона и переиспользования контрактов.

### Шаг 4. Уточнить пробелы

Если после чтения остаются неоднозначности (что входит в скоуп firmware vs backend, какие фазы, какие границы), задать пользователю уточняющие вопросы через AskUserQuestion до начала написания. Не выдумывать ответы.

### Шаг 5. Согласовать план

До записи файла показать пользователю:

- Имя файла и путь (см. правила именования ниже).
- Список фаз (для feature-level) или границу фазы (для phase-level).
- Перечень внешних границ, которые попадут в раздел «Контракты».
- Список не-целей.

Дождаться явного одобрения. Без одобрения файл не писать (см. `feedback_approve_before_edit`).

### Шаг 6. Написать файл

Создать файл по согласованному пути. Заполнять строго по «Шаблон-каркасу» из `arch-doc-template.md`. Соблюдать чек-лист в конце шаблона — пройти по нему перед сохранением.

## Правила именования и расположения

- Расположение: `specs/docs/features/<feature>/jira-tickets/firmware/`. Если папки нет — создать.
- Feature-level: `architecture.md` (если такого файла ещё нет в папке; иначе уточнить у пользователя).
- Phase-level: `phase-<N>-<kebab-name>.md`, например `phase-1-rule-evaluator.md`.

## Жёсткие правила содержания

Берутся из шаблона, но критичны и легко забываются:

- **Язык документа — русский.** Все заголовки секций, таблицы, текст — на русском, ровно как в шаблоне `arch-doc-template.md` (Контекст, Цель, Не-цели / Что НЕ входит, Обзор архитектуры, Компоненты и зоны ответственности, Раскладка по реализации, Алгоритмы, Контракты между системами, Граница N: A ↔ B, Поток (happy path), Данные и состояние, Безопасность и приватность, Угрозы намеренно не покрытые, Деплой / Эксплуатация, Дорожная карта по фазам, Открытые вопросы, Граница с другими фазами, Ссылки) — на английский не переводить. Идентификаторы кода, пути к файлам, имена полей/enum/методов и contract-лексику не переводить. Без эмодзи, без маркетинга.
- **Feature-level: без DDL, без имён классов C++, без HTTP-методов конкретных эндпоинтов, без точных имён env-переменных.** Это уровень тикета на реализацию, не арх-дока. **Phase-level — наоборот: можно и нужно** ссылаться на конкретные слои (Core/Domain, Application, Infrastructure), на существующие классы/интерфейсы/сервисы по именам (`RuleService`, `IRepository`, `LoopServiceFactory` и т.п.) и на пути в `src/` — это нужно для верхнеуровневых деталей реализации.
- **Non-goals — обязательная секция** с причинами для каждой строки.
- **У каждой границы в Contracts** — все 7 подпунктов: Transport, Authentication, Operations, Data semantics, Errors, Idempotency, Limits. Если граница тривиальна (in-process вызов) — не включать в раздел вовсе.
- **Happy path** — одна последовательность без ветвлений в нумерации, 8–12 пунктов. Развилка — отдельным абзацем после списка.
- **Data and state** — таблица с владельцем и временем жизни для каждой строки.
- **Threats explicitly not covered** — обязательный подсписок в секции Security **только для feature-level**.
- **Open questions** — формулировать вопросами, не TODO.
- **ASCII-диаграммы**, не mermaid.
- **Без комментариев в коде** и без комментариев-плейсхолдеров типа `<!-- TODO -->` в финальном тексте — только содержательный текст или явные Open questions.

## Особенности для phase-level

Phase-level ближе к тикету на реализацию, чем feature-level. Это документ для разработчика, который будет писать код.

**Структурные отличия от шаблона:**

- Не повторять Context и Goal из feature-дока — ссылаться на него (через относительный путь к `architecture.md`) и описывать только границу фазы.
- Включать в Contracts **только** те границы, которые активны в этой фазе.
- Не включать раздел Phase roadmap.
- В конце — раздел Boundary with other phases: что намеренно оставлено на следующие фазы.

**Секции, которые опускаются или сильно сокращаются для phase-level:**

- **Security and privacy** — опустить полностью, если фаза не вводит новых секретов, доверительных границ или persisted-данных. Если опускается — упомянуть это одной строкой в Boundary with other phases. Подсписок Threats explicitly not covered **не обязателен**.
- **Deployment / Operations** — опустить, если локально не появляется новых конфигов/миграций/env. Контракты вида «требует backend ≥ vX» или «требует minimum-firmware-version Y» переносить в соответствующую Boundary как Limits/Errors, а не в отдельную секцию Deploy.

**Секции, которые ДОБАВЛЯЮТСЯ или РАСШИРЯЮТСЯ для phase-level** (вставлять между Components and responsibilities и Contracts, либо после Flow):

- **Implementation layout** — таблица или список: какой слой Clean Architecture (`Core/Domain/UseCases/<Feature>/`, `Application/Services/`, `Infrastructure/Adapters/`, `Infrastructure/Repositories/`, ...) что отвечает в этой фазе. Перечислять конкретные интерфейсы/сервисы, которые расширяются или добавляются, по их фактическим именам в `src/`. Указывать существующие классы, которые становятся точками вмешательства (например `RuleService`, `LoopServiceFactory`, `HybridAPIService`).
- **Algorithms** — раздел на 1–3 алгоритма, которые нетривиальны: матчинг правил, разрешение зависимостей, эвалюация условий, машина состояний. Псевдокод или нумерованные шаги. Без листингов C++.
- **State machines / lifecycles** — если фаза вводит новый стейт или меняет существующий (loop-сервисы: CanConfigure → Configuring → ConfigureDone и т.п.) — нарисовать ASCII state-diagram и перечислить переходы.
- **Error handling** — таблица: какая ошибка, кто её бросает (слой/сервис), как обрабатывается, превращается ли в диагностику. Только если фаза вводит новые классы ошибок.

Если фаза тривиальна и какой-то из добавочных разделов нечем заполнить — опустить, а не растягивать.

## После записи

Сообщить пользователю:

- Путь к созданному файлу (markdown-ссылкой).
- Какие открытые вопросы остались в доке — чтобы пользователь сразу мог их закрыть.
- Если в процессе обнаружились нестыковки в feature-уровневых доках (`overview.md`, `firmware.md`, `contracts/`) — перечислить отдельным списком, не править их без отдельного запроса.
