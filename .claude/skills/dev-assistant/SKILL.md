# dev-assistant — оркестратор задач разработчика

Скил — это **оркестратор**. Сам он работу не делает: он превращает слова пользователя в постановку, заводит по задаче **память**, запускает под задачу **отдельного суб-агента** и возвращает пользователю его результат.

## ⭐ Главное правило (приоритетнее всего)

**Любая задача, которую формулирует пользователь, выполняется в отдельном суб-агенте — не самим оркестратором.**

- Просят «проанализируй тикет GDV1-3463» → оркестратор готовит постановку и запускает суб-агента, тот анализирует, оркестратору возвращается результат.
- Просят «разбери баг по логам» → суб-агент (который внутри вызовет скил `log-analysis`), результат — оркестратору.
- Просят «изучи как работает X в коде», «спланируй фикс», «собери контекст по задаче» → тоже суб-агент.

Оркестратор сам лезет в код/логи/Jira **только** чтобы собрать постановку (быстрый recon) — саму задачу решает суб-агент. Если сомневаешься, «это задача или просто вопрос» — короткий фактический вопрос про сам скил можно ответить напрямую; **любая работа над продуктом (код, баг, тикет, логи, анализ) идёт в суб-агента.**

**По каждой задаче обязательна память** — файл `state/memory/task-<slug>.md` (постановка + находки + решения + статус). Заводит оркестратор, дополняет суб-агент.

## Модель организации

```
.claude/skills/dev-assistant/
├── SKILL.md                 ← этот файл (оркестратор)
├── agents/
│   └── _TEMPLATE.md         ← шаблон для будущих РУТИННЫХ суб-агентов (пока рутин нет)
└── state/                   ← локальное, в .gitignore
    └── memory/
        └── task-<slug>.md   ← память по каждой задаче
```

Виды суб-агентов:

1. **Пайплайн разбора задачи** (`agents/task-*.md`) — 3 стадии с гейтами апрува: `task-prep` → `task-investigate` → `task-solution`. Главный флоу для «разбери/повтори/найди причину/сделай по тикету». См. «Пайплайн разбора задачи».
2. **Динамический суб-агент под задачу** — для задач, которые не ложатся в пайплайн (разовое «изучи код», «собери контекст»). Спавнится из постановки оркестратора, в файлах не описан.
3. **Рутинный суб-агент** (`agents/<id>.md`, `cadence != manual`) — регулярная задача по расписанию. Пока таких **нет** — добавим позже (шаблон в `agents/_TEMPLATE.md`).

## Запуск: постоянный режим (always-on) vs разовый

Скил работает в двух режимах.

**Постоянный (штатный) — `/loop dev-assistant`.** Оркестратор стартует, обрабатывает что есть и
**остаётся жить, ожидая задач**. Дальше ты просто пишешь в чат «сделай то-то» — он выполняет по
скилу (постановка → память → суб-агент → результат, с гейтами). Держится живым через `ScheduleWakeup`.
Это же — **фундамент для каналов**: под `/loop` сессия не засыпает, и когда подключим Telegram
(`--channels …`), входящие из телеги придут как события `<channel source="telegram">` и разбудят
**тот же тик** — обработка одна и та же (шаг 0 ниже).

**Разовый.** Если скил вызван без `/loop` — отработать текущую задачу и в конце подсказать, что для
постоянной работы запускать `/loop dev-assistant`.

### Алгоритм тика (в постоянном режиме)
Каждое срабатывание петли = один **тик**:

0. **Обработать входящие инструкции.** Собрать всё, что пришло: сообщения пользователя из сессии и
   (когда подключим) события `<channel source="telegram">`. Разобрать:
   - `status` — коротко: какие задачи в работе, на каком гейте, что ждёт апрув.
   - `stop` — завершить петлю (следующий тик не планировать), подтвердить.
   - `pause` / `resume` — приостановить/возобновить обработку.
   - ответ на гейт (`ок`/`да`/правки) — продолжить соответствующую задачу со следующей стадии.
   - **любое другое → это задача**: обработать по «Главному алгоритму» (пайплайн или динамический
     суб-агент). Работу делает суб-агент, оркестратор диспатчит.
1. **Рутинные агенты по cadence.** Пока рутин нет — шаг пропускаем (появятся — здесь проверяем, кому due).
2. **Состояние активных задач.** Пришёл `<task-notification>` от фонового суб-агента → забрать отчёт,
   обновить память задачи, **провести гейт** (показать причину/описание на апрув) или запустить
   следующую стадию по уже данному апруву.
3. **Запланировать следующий тик** через `ScheduleWakeup(prompt: "dev-assistant")` — держать сессию
   живой. Есть активная фоновая задача → просыпаемся по её `<task-notification>`. Иначе (простой, рутин
   нет) — длинный idle-интервал (~1800с), только чтобы сессия/канал не засыпали. `stop` → не планировать.

## Ресурсы

Актуальные URL / id / креды — в [Resources.md](../../../Resources.md) в корне репо (Jira, Kibana/ELK, dev-приложение). Не хардкодить их в промптах — суб-агент читает `Resources.md` сам. Новые ресурсы под задачу дописывать туда же.

## Как обрабатывать задачу пользователя (главный алгоритм)

**Маршрутизация.** Если задача — разбор/воспроизведение/причина/фикс по багу или тикету → веди её
через **пайплайн** (`task-prep → task-investigate → task-solution`, см. ниже), выбрав нужное число
стадий. Иначе (разовое «изучи код», «собери контекст») → **динамический суб-агент** по алгоритму ниже.
В обоих случаях действуют правила: работа в суб-агенте + память задачи.

### 1. Собрать постановку (быстрый recon оркестратора)
Из слов пользователя вынь: что за задача, какой тикет/модуль/симптом, что считать результатом (анализ? фикс? план? отчёт?), какие ресурсы нужны (Jira-тикет, логи ELK, код). При необходимости — быстрый read-only recon (глянуть тикет через Jira MCP, найти файл в коде), **чтобы уточнить постановку, а не решить задачу**. Если критично не хватает вводных — задать **один** блок уточнений через `AskUserQuestion`, дальше действовать сам.

Придумай `slug` (kebab-case из сути: `gdv1-3463-rule-display`, `co2-sensor-restart`).

### 2. Завести/обновить память задачи
Файл `state/memory/task-<slug>.md`. Если нет — создай по структуре (см. «Память задачи»). Запиши **постановку** (что просили, что делаем, критерий готовности) и recon-находки. Если файл уже есть (задачу продолжаем) — прочитай его, не переразбирай решённое.

### 3. Запустить суб-агента
Через инструмент `Agent` (`subagent_type: "general-purpose"`, `model: "opus"`, `run_in_background: true`). В `prompt` передать:
- **Постановку** задачи (что сделать, критерий готовности, границы).
- Путь к [Resources.md](../../../Resources.md) — прочитать в начале, брать URL/креды оттуда.
- Путь к файлу памяти `state/memory/task-<slug>.md` — **прочитать в начале, дописать важное в конце**.
- Разрешение и указание **использовать доступные скилы репо** под задачу — прежде всего `log-analysis` (разбор бага по логам ELK); суб-агент вызывает скил через механизм Skill, как обычно.
- Требование вернуть **структурированный отчёт** (см. «Отчёт суб-агента»).

Несколько независимых задач — запускать суб-агентов **в одном сообщении** (параллельно).

Фон (`run_in_background: true`) — чтобы сессия оставалась живой и можно было вести несколько задач; отчёт заберём по `<task-notification>`. Для одной короткой задачи, где пользователь ждёт ответ прямо сейчас, допустимо запустить синхронно (`run_in_background: false`) — на усмотрение оркестратора.

### 4. Собрать результат и отчитаться
По `<task-notification>` о завершении суб-агента: прочитать его отчёт, убедиться что память дописана (если нет — дописать ключевое самому), дать пользователю **краткую** сводку результата (без воды: что выяснили/сделали, что дальше). Если суб-агент вернул «нужно действие/решение пользователя» — показать и ждать.

## Пайплайн разбора задачи (task-prep → task-investigate → task-solution)

Главный флоу для задач вида «проанализируй/повтори/найди причину/сделай по тикету GDV1-XXXX».
**Координирует оркестратор** — никакой вложенности агент-в-агенте. Все 3 агента `cadence: manual`,
запускаются **только** этим пайплайном. Общее состояние — один файл памяти задачи
`state/memory/task-<slug>.md`, который стадии по очереди дополняют.

Стадии и **гейты апрува**:

1. **`task-prep`** — собирает контекст: читает тикет (локальный `tickets/GDV1-XXXX.md` + Jira),
   качает вложения, изучает документацию (`specs/docs/`; фолбэк — локальные `doc/`, `tickets/`), поднимает релевантную
   память → пишет **досье** в память задачи. Read-only. **Можно запускать standalone** — как
   подготовку контекста для произвольного агента, не только перед `task-investigate`.
2. **`task-investigate`** — на базе досье **воспроизводит** и **ищет причину**: логи через скил
   `log-analysis` (пара «код ↔ лог»), код, dev-приложение → **корневая причина с доказательствами**.
   🚦 **Гейт №1** — причину показываем пользователю, ждём **апрув**. Read-only.
3. **`task-solution`** (только после апрува причины) — пишет **описание решения** по шаблону
   `specs/templates/GDV1-template.md` → сохраняет `tickets/GDV1-XXXX.md`. 🚦 **Гейт №2** — описание на
   **апрув**. По «да» → **реализует фикс** в коде строго по одобренному плану.

**Как оркестрирует оркестратор:**
- Определи по запросу, **сколько стадий** нужно: «собери контекст» → только prep; «найди причину» →
  prep + investigate (стоп на гейте №1); «сделай по тикету / фикс» → все три с обоими гейтами.
- Заведи память задачи (постановка + `slug` из номера тикета, напр. `gdv1-3463-rule-display`).
- Запусти стадию суб-агентом (`Agent`, `general-purpose`, `opus`, `run_in_background: true`),
  передав в промпт: **тело файла** `agents/task-<stage>.md`, путь к `Resources.md`, путь к файлу
  памяти задачи (читать в начале, дописывать в конце), требование вернуть отчёт.
- По `<task-notification>` забери отчёт, обнови память при необходимости, **проведи гейт** (покажи
  причину/описание пользователю) и запусти следующую стадию **только по апруву**.
- Правки пользователя на гейте — вноси в память/файл описания перед следующей стадией.
- Стадии одной задачи идут **последовательно** (каждая опирается на предыдущую). Разные задачи можно
  вести параллельно.

## Память задачи (`state/memory/task-<slug>.md`)

Человекочитаемый журнал по задаче, чтобы не делать одно и то же дважды и видеть прошлые решения. Структура:

```markdown
# Задача: <slug>

## Постановка
<что просил пользователь, критерий готовности, границы>

## Канон / решения
<устойчивые выводы и договорённости — курируется, актуальный срез>

## Открытые вопросы / ждёт апрув
<что не ясно, что ждёт решения пользователя>

## Журнал
### <YYYY-MM-DD>
<что сделали за прогон, ключевые находки, ссылки на код/логи>
```

Протокол: суб-агент **читает** память в начале (учитывает канон и открытые вопросы), **дописывает** только важное в конце (решения, нетривиальный контекст, почему что-то отложили). Рутину («посмотрел, пусто») не пишем. `## Журнал` — append-only, свежее сверху.

## Отчёт суб-агента (что он возвращает оркестратору)
- Что сделал (находки/действия, ссылки на файлы `path:line`, тикеты, строки логов).
- Результат по критерию готовности (готово / частично / blocked).
- Что пропустил и почему; нужно ли решение/действие пользователя.
- Память: что дописал в `state/memory/task-<slug>.md` (кратко) или «без изменений».
- Итоговый `status`: `ok` | `blocked` | `error`.

## Скилы репо (суб-агенты их используют)
Суб-агент (`general-purpose`) может вызывать скилы этого репо S3 под задачу. Оркестратор в постановке
прямо указывает, какой скил дёрнуть:
- **`log-analysis`** — доказательный разбор бага по логам ELK (пара «строка кода ↔ строка лога», md-отчёт в `doc/log-analysis/`). Для задач вида «разобрать инцидент/поведение модуля по логам».
- **`sensor-mqtt-debug`** — отладка RS485-датчиков живого модуля через MQTT (ping, чтение регистров, перебор адресов/портов, смена ModBus-адреса) без прошивки и Serial-кабеля.
- **`task-doc`** — BA-постановка задачи по шаблону; **`task-arch`** — арх-док задачи из BA-постановки;
  **`feature-arch`** — firmware-арх-док фичи; **`imp-doc`** — имп-док для джуна из арх-дока;
  **`bug-imp-doc`** — имп-док багфикса (из текста или Jira-тикета); **`ba-doc-review`** — гейт готовности
  BA-дока к арх-фазе; **`prepare_new_version`** — бамп версии + release notes + коммит.

Для флоу «оформи таск → арх → имп-док» по тикету предпочитай штатные скилы (`task-doc`/`task-arch`/
`imp-doc`/`bug-imp-doc`) — они уже кладут доки в `specs/docs/features/<feature>/jira-tickets/…` по
шаблонам. Собственный пайплайн (`task-*`) — для быстрого «разбери причину → опиши фикс → закодь».

По мере появления новых скилов — так же указывать их суб-агенту в постановке.

## Добавление рутинного суб-агента (режим add — на будущее)
Срабатывает, только когда скил вызван явно и пользователь просит «добавь рутину/суб-агента **в dev-assistant**» (или `add: <описание>`). Голое «добавь агента» — не этот режим.
1. Понять задачу рутины: что делает, что трогает, как часто (`cadence`). Чего нет — один блок уточнений.
2. Взять `agents/_TEMPLATE.md`, записать `agents/<id>.md` (`id` == имя файла). Frontmatter: `id`, `cadence`, `model: opus`, `enabled: true`, `description`. Тело — пошаговый алгоритм.
3. Новые ресурсы — в [Resources.md](../../../Resources.md).
4. Показать пользователю что за агент и предложить тест-прогон.

*(Пока рутинных суб-агентов нет — раздел активируется, когда попросят первую рутину. Логику расписания/тиков добавим тогда же.)*

## Telegram и другие каналы
Пока **не подключаем** — отчёты и вопросы идут в сессию. Но постоянный режим (`/loop dev-assistant`)
уже готов под это: входящие из любого канала приходят как события `<channel source="…">` и
обрабатываются в **шаге 0** тика тем же кодом, что и сообщения из чата. Подключение сведётся к запуску
сессии с `--channels …` и добавлению отправки ответов/саммари в канал — логику задач менять не нужно.

## Правила
- **Задача пользователя = отдельный суб-агент.** Это дефолт, не исключение. Оркестратор диспетчеризует и ведёт память, работу делает суб-агент.
- **Память обязательна** по каждой задаче (`state/memory/task-<slug>.md`).
- Суб-агенты — **Opus** (`model: "opus"`), если не указано иное.
- Ресурсы (URL/id/креды) — только в [Resources.md](../../../Resources.md), не хардкодить в промптах.
- **Jira — только чтение через MCP, фолбэк Playwright.** Для чтения тикетов/поиска сначала **Jira MCP**
  (read-only инструменты: `getJiraIssue`, `searchJiraIssuesUsingJql`, `getJiraIssueRemoteIssueLinks`,
  `search`, `fetch`). Если через MCP не выходит — **фолбэк на Playwright** (сессия залогинена). Пишущие
  Jira-операции скилом не делаем.
- **Playwright — не забивать контекст.** Не делать полные `browser_snapshot` больших страниц; сохранять снапшот в `.playwright-mcp/<имя>.yml` (gitignored) и искать `grep`-ом, либо брать target-снапшот элемента.
- `state/` — локальный, в `.gitignore`.
