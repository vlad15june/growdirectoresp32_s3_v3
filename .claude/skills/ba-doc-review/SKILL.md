# Ревью BA-дока перед арх-фазой (ba-doc-review)

Скил — **гейт качества перед арх-фазой**. Вход — уже написанная BA-постановка (task-doc по `task-template.md`) **или** BA-док фичи (`overview.md` / `firmware.md` / `backend.md` / `spec.md` / `proposal.md`). Скил не пишет арх и не правит вход — он отвечает на один вопрос: **можно ли по этому доку строить `task-arch` / `feature-arch` и дальше `imp-doc`, или сначала надо что-то закрыть.**

Место в цепочке:

```
task-doc / BA-док фичи  ──►  [ba-doc-review]  ──►  task-arch / feature-arch  ──►  imp-doc
        (ЧТО)                  (готов ли ЧТО)            (КАК на уровне арх)        (КАК пошагово)
```

Скил проверяет ровно три вещи:

1. **Согласованность.** Док не противоречит сам себе и не противоречит текущей системе (арх компонента, существующие инварианты, контракты, enum'ы, потоки). Если док **меняет** уже принятое решение/контракт/поведение — это изменение должно быть **явно объявлено** в доке, а не протащено молча.
2. **Контракты.** Все затронутые кросс-компонентные границы покрыты: либо канонический контракт в `docs/contracts/<pair>/` уже описывает изменение (и обновлён в том же workstream), либо в самом task-doc/BA-доке есть блок Contracts, описывающий новые изменения границы со всеми обязательными подпунктами.
3. **Полнота.** Есть все данные и закрыты все вопросы, чтобы построить арх- и имп-доки: наблюдаемые цели, фальсифицируемые `INV-n` со значениями, границы с единицами/энфорсером/реакцией, acceptance, покрывающий каждый инвариант и границу, входы/выходы, edge cases; нет открытых вопросов, плейсхолдеров и расплывчатых формулировок.

**Read-only по входу.** Скил не правит проверяемый док, контракты и другие доки фичи. Найденные нестыковки скил перечисляет, но чинит их только по отдельному запросу (см. `feedback_approve_before_edit`).

**Вывод — сначала в чат, сжато.** Отчёт всегда сперва идёт в чат: без воды, максимально сжатый и при этом полный, **не более 100 строк** — чтобы понять всё за один взгляд, без листания. Это правило держится **даже если вердикт READY**. Файл-отчёт (то же содержимое) пишется только после явного «да» — скил спрашивает.

## Шаги (выполнять строго по порядку, не пропускать)

### Шаг 1. Найти входной док и определить его тип

**Обязательно через AskUserQuestion**, если из запроса неоднозначно, какой док ревьюим:

> Какой док ревьюим? Укажи путь (например `specs/docs/features/sensor/tasks/<slug>/<slug>.md` для task-doc или `specs/docs/features/workflow/firmware.md` для BA-дока фичи).

Резолвить путь, проверить, что файл существует. Определить тип входа — от него зависит набор критериев на Шаге 4:

- **task-doc** — лежит в `features/<feature>/tasks/<slug>/<slug>.md`, оформлен по `task-template.md` (есть `Affects:`, `Invariants`, `Acceptance`). Проверяется как постановка задачи.
- **BA-док фичи** — `overview.md` / `<component>.md` / `spec.md` / `proposal.md` в корне `features/<feature>/`. Проверяется как BA-описание подсистемы: спецификация, требования, взаимодействие — то, из чего строится `feature-arch`.

Если файла нет — остановиться и сказать, что ревьюить нечего. Если это уже арх-док (по `arch-doc-template.md` / `task-arch-doc-template.md`) — сказать, что для арха гейт другой (это уже КАК), и предложить ревьюить его источник-истину (task-doc / BA-док фичи).

### Шаг 2. Определить фичу и затронутые компоненты

- Фича — из пути (`features/<feature>/...`).
- Затронутые компоненты — из строки `Affects:` (task-doc) или из того, какой это `<component>.md` / что в скоупе у BA-дока фичи. Если неоднозначно — **через AskUserQuestion** уточнить, какие части системы затрагивает док (`frontend` / `firmware` / `backend`, multiSelect).

Компоненты определяют, какие component-доки и какие пары контрактов читать на Шаге 3.

### Шаг 3. Прочитать контекст для сверки

Цель чтения — собрать «истину системы», против которой проверяется док. В этом порядке:

1. **Шаблон входного дока** — `specs/templates/task-template.md` (для task-doc) или конвенция BA-дока фичи из `specs/docs/conventions/file-placement-rules.md` §3 (для BA-дока фичи). Из шаблона/конвенции берётся чек-лист обязательных секций для Шага 4.
2. **Правила размещения и структуры** — `specs/docs/conventions/repository-structure.md` и `file-placement-rules.md`: что обязан содержать док этого типа, что обязан содержать контракт.
3. **Контекст агента** — `specs/docs/agent-context/index.md` (и `firmware.md`, если затронут firmware).
4. **Доки фичи** в `specs/docs/features/<feature>/`: `index.md`, `overview.md`, `<component>.md`, `spec.md`/`biz/`, `questions.md`, `contracts/`. Это база для проверки на противоречия и на «тихое изменение решения».
5. **Component-доки затронутых компонентов** — только релевантные:
   - firmware → `specs/docs/components/firmware/`: `index.md`, `projectArchitecture.md`, `projectStructureDirectoryDescription.md`, плюс тематически близкие (`sensor-models.md`, `sensorOperationsGuide.md`).
   - backend → `specs/docs/components/backend/index.md` и тематически близкие.
   - frontend → `specs/docs/components/frontend/index.md` и тематически близкие.
6. **Контракты активных границ** — индекс соответствующей пары и конкретный контракт по теме:
   - frontend+backend → `specs/docs/contracts/frontend-backend/`
   - backend+firmware → `specs/docs/contracts/backend-firmware/`
   - frontend+firmware → `specs/docs/contracts/frontend-firmware/`
7. **Decisions** — `specs/docs/decisions/`: если док затрагивает область принятого ADR, проверить, не противоречит ли он решению.
8. **System-обзор** — `specs/docs/system/index.md`.
9. **Реальный код** затронутого компонента — только при необходимости подтвердить/опровергнуть конкретное утверждение дока (существует ли класс/интерфейс/enum/значение, на которые опирается постановка). Читать `src/` напрямую (Read/Grep), не плодить агентов.

Читать по `related`-ссылкам, не сканировать папки целиком (см. `feedback_no_unprompted_repo_search` — в другие репозитории не лезть).

### Шаг 4. Прогнать три проверки

Для каждой находки фиксировать: **где в доке** (секция/строка), **с чем конфликтует** (путь к доку/контракту/коду или соседняя строка дока), **severity** (BLOCK / WARN / INFO).

#### Проверка 1 — Согласованность

Внутренние противоречия дока:
- Goal противоречит Non-goals; инвариант противоречит инварианту; Boundaries противоречат инварианту; Acceptance проверяет не то, что заявлено в Invariants/Goal; Inputs/Outputs не сходятся с Description.
- Edge case ссылается на несуществующий `INV-n` или границу.

Противоречия с текущей системой:
- Утверждение дока расходится с документированным поведением фичи (`overview.md`/`<component>.md`), с существующими инвариантами, с семантикой контракта, с именами/значениями enum'ов, с арх компонента.
- Док опирается на класс/интерфейс/значение, которых в системе нет (проверять по component-докам и, при сомнении, по коду).

Тихое изменение принятого решения (критично):
- Док **меняет** существующее поведение / контракт / семантику sync-state / инвариант / ADR, но не объявляет это явно (нет пометки «меняем X», нет ссылки на канонический узел под обновление).
- По Change Management такое изменение обязано быть объявлено и вести к обновлению канонического узла в том же workstream, либо к ссылке на принятый спек, либо к явной пометке. Молчаливое изменение — **BLOCK**: оно сломает согласованность доки и кода ниже по цепочке.

#### Проверка 2 — Контракты

- Выписать все кросс-компонентные границы, которые задача реально затрагивает (из `Affects` / `Scope per system` / описанного поведения). Тривиальные in-process вызовы — не контракт, не считать.
- Для каждой активной границы проверить покрытие **одним из двух**:
  1. **Канонический контракт** в `docs/contracts/<pair>/` уже описывает это изменение, и (если меняется payload/топик/семантика) контракт обновляется в том же workstream — в доке должна быть ссылка на него.
  2. **Блок Contracts в самом доке** (task-doc «Contracts between systems» / раздел контрактов BA-дока фичи) описывает новые изменения границы со всеми обязательными подпунктами: Transport, Authentication, Operations, Data semantics (поля/типы/единицы/смысл), Errors, Idempotency, Limits/Versioning.
- **BLOCK**, если граница затронута, но не покрыта ни каноническим контрактом, ни блоком в доке; либо контракт в доке неполон (нет полей payload, типов, единиц, кодов ошибок, направления операций, минимальной версии соседа).
- **WARN**, если контракт описан и в доке, и канонически, но они расходятся, или если изменение payload не помечено как требующее обновления канонического контракта.
- Канонический контракт **не должен переписываться** внутри task-doc — на него ссылаются. Если док копирует JSON канонического контракта вместо ссылки — INFO/WARN.

#### Проверка 3 — Полнота для арх- и имп-доков

Цель: хватит ли данных, чтобы `task-arch`/`feature-arch` мог разложить реализацию по слоям, а `imp-doc` — по шагам и acceptance.

Для **task-doc** (по `task-template.md`):
- `Affects` проставлен; для каждой затронутой системы есть Scope.
- Goal — наблюдаемые исходы, не формулировки реализации.
- Non-goals / Boundaries присутствуют, на каждую строку — причина.
- Invariants пронумерованы `INV-n`, каждый фальсифицируемый, со значением/единицей; нет «fast/soon/large».
- Boundaries / Limits: каждая граница с value+unit, кто энфорсит, что при нарушении.
- Acceptance: каждый `INV-n` и каждая строка Boundaries покрыты хотя бы одной фальсифицируемой проверкой; иначе арх/имп нечем замкнуть.
- Inputs/Outputs и Edge cases заданы; каждый edge case ведёт к `INV-n`/границе.
- Open questions: **все закрыты**. Любой открытый вопрос, влияющий на арх (поведение, граница, контракт, значение) — **BLOCK**; косметический — WARN. Сверить и с `questions.md` фичи.
- Нет плейсхолдеров (`<!-- TODO -->`, `<...>`, `TBD`) в содержательных секциях.

Для **BA-дока фичи**:
- Есть назначение (какие задачи решает, требования к покрытию), спецификация поведения подсистемы, требования к реализации, взаимодействие компонентов, ключевые решения — то, из чего `feature-arch` строит арх.
- Поведение задано однозначно: значения, единицы, границы, реакции на отказ/рестарт — а не общими словами.
- Затронутые контракты — см. Проверку 2.
- Открытые вопросы (в доке и в `questions.md`) закрыты; нерешённый вопрос, влияющий на арх — BLOCK.

### Шаг 5. Свести вердикт

- Каждая из трёх проверок → **PASS / WARN / BLOCK** (BLOCK, если есть хоть одна BLOCK-находка; WARN, если только WARN/INFO; иначе PASS).
- **Общий вердикт:**
  - **READY** — все три PASS (допустимы единичные INFO). Можно запускать `task-arch`/`feature-arch`.
  - **READY WITH NOTES** — нет BLOCK, есть WARN. Арх можно начинать, но перечисленные WARN надо учесть/закрыть по ходу.
  - **BLOCKED** — есть хотя бы одна BLOCK-находка. Арх не начинать, пока не закрыто; по каждому блокеру — что именно сделать.

### Шаг 6. Сначала — сжатый отчёт в чат

**Главное правило вывода:** сначала весь отчёт идёт в чат — это и есть содержимое будущего файла. Пользователь читать длинное и листать не будет, поэтому отчёт обязан быть таким, чтобы **всё стало понятно за один взгляд**:

- **Не более 100 строк.** Жёсткий лимит. Не лезет — резать воду, а не находки.
- **Без воды.** Никаких вводных, пересказа дока, «как известно», объяснений процесса. Только: вердикт, по-проверочный статус, находки с адресом, блокеры, что сделать.
- **Максимально сжато и при этом максимально полно.** Каждая реальная находка присутствует, но одной строкой. Severity, адрес (секция дока ↔ путь конфликта), суть — в одну строку.
- **Сверху — вывод.** Первая строка: общий вердикт + три статуса. Дальше — блокеры (если есть), потом WARN. Чтобы взгляд сверху вниз сразу давал картину.
- Формат в чате — тот же скелет отчёта (ниже), без раздувания: пустые секции (нет находок в проверке) — одной строкой «PASS — нет находок», а не пустой таблицей.
- Это правило действует **даже если вердикт READY** — короткий отчёт всё равно в чат, чтобы пользователь увидел, что и почему прошло.

### Шаг 7. Спросить про файл и записать

После отчёта в чат — **спросить, делать ли файл** (см. `feedback_approve_before_edit`); без явного «да» файл не писать. Файл содержит ровно то, что было в чате (тот же скелет; в файле таблицы можно развернуть полностью, без лимита в 100 строк, но без новой воды).

Расположение отчёта — **рядом с проверяемым доком**, не перезаписывая его:
- task-doc `tasks/<slug>/<slug>.md` → `tasks/<slug>/<slug>-review.md`.
- BA-док фичи `features/<feature>/<doc>.md` → `features/<feature>/<doc>-review.md`.
- Если файл отчёта с этим именем уже есть — уточнить: перезаписываем (новый прогон) или это другой ревью. Не перезаписывать молча.

Язык отчёта — по конвенции компонента (для firmware — английский, как сам проверяемый док); заголовки секций переводить с сохранением смысла.

## Скелет отчёта

```markdown
# BA-doc review — <имя проверяемого дока>

- **Reviewed:** <относительный путь к проверяемому доку>
- **Type:** task-doc | feature BA doc
- **Feature / Affects:** <feature> / <frontend|firmware|backend>
- **Verdict:** READY | READY WITH NOTES | BLOCKED
- **Checks:** Consistency = PASS/WARN/BLOCK · Contracts = PASS/WARN/BLOCK · Completeness = PASS/WARN/BLOCK

## Summary

<3–6 строк: можно ли строить арх, и что (если что-то) мешает>

## 1. Consistency

| Severity | Где в доке | С чем конфликтует | Находка |
|---|---|---|---|
| BLOCK/WARN/INFO | <секция/строка> | <путь к доку/контракту/коду или соседняя строка> | <в чём расхождение или тихое изменение решения> |

## 2. Contracts

| Граница | Затронута чем | Покрытие | Severity | Чего не хватает |
|---|---|---|---|---|
| A ↔ B | <операция/поле> | canonical / in-doc / отсутствует | BLOCK/WARN/INFO | <недостающие подпункты или ссылка> |

## 3. Completeness for arch/imp

| Severity | Что нужно арх/имп | Состояние в доке | Что сделать |
|---|---|---|---|
| BLOCK/WARN/INFO | <INV/boundary/acceptance/open question/...> | есть / нет / неоднозначно | <конкретное действие> |

## Blockers (must close before arch)

- [ ] <блокер — что сделать, где>

## Notes (учесть по ходу арха)

- <warn-находка>
```

## Жёсткие правила

- **Не править вход.** Проверяемый док, контракты и другие доки фичи скил не трогает. Только читает и пишет отчёт. Если пользователь хочет, чтобы скил починил находки, — это отдельный запрос после ревью.
- **Каждая находка — с адресом.** Секция/строка в доке + конкретный путь к доку/контракту/коду, с которым конфликт. Без адреса находка не засчитывается (см. `feedback_facts_not_advice` — факты со ссылкой, не советы).
- **Тихое изменение принятого решения — всегда BLOCK.** Молчаливая правка существующего контракта/инварианта/поведения/ADR без явного объявления и ссылки на канонический узел под обновление.
- **Затронутая граница без покрытия контрактом — BLOCK.** Либо канонический контракт (обновлён в том же workstream + ссылка из дока), либо полный блок Contracts в самом доке.
- **Открытый вопрос, влияющий на арх, — BLOCK.** Косметический — WARN.
- **Severity честное.** Не занижать BLOCK до WARN, чтобы «пройти». READY означает, что арх можно строить без доработки постановки.
- **Без C++-листингов и без комментариев в коде** в отчёте (см. `feedback_no_comments`).
- **Не выдумывать.** Если утверждение дока нельзя подтвердить ни по докам, ни по коду — это находка («не подтверждается»), а не молчаливое допущение.

## После записи

Сообщить пользователю:

- Путь к отчёту (markdown-ссылкой) и общий вердикт.
- Список блокеров (если есть) — коротко, что закрыть перед запуском `task-arch`/`feature-arch`.
- Список WARN, которые стоит учесть по ходу арха.
- Если по ходу всплыли нестыковки в самих канонических доках/контрактах (а не во входе) — перечислить отдельным списком, не правя их без отдельного запроса.
