# Создание BA-постановки задачи (task-doc)

Скил для оформления задачи в формате постановки от бизнес-аналитика. Результат — markdown-файл **на русском языке** строго по структуре `specs/templates/task-template.md` (Affects, Invariants, Boundaries, Contracts и т.д.).

Постановка фиксирует **что** должно быть истинно по завершении (цель, границы, инварианты, контракты между системами), а не **как** это реализуется. Детали реализации — в арх-доках (`feature-arch`) и Jira-тикетах.

## Шаги (выполнять строго по порядку, не пропускать)

### Шаг 1. Определить, для какой части системы задача

**Обязательно через AskUserQuestion** (multiSelect), если из запроса это неоднозначно:

> Для какой части системы задача? (можно несколько)

Опции: `frontend`, `firmware`, `backend`. Выбор — это значение строки `Affects:` в шаблоне и набор доков для чтения на Шаге 3.

### Шаг 2. Определить фичу / область и расположение

**Через AskUserQuestion**, если неясно:

> К какой фиче/области относится задача? Назови имя (например `workflow`, `sensor`, `rules`) или укажи, что это новая область.

Резолвить путь `specs/docs/features/<feature>/`. Каждая задача живёт в **своей подпапке** внутри `tasks/`, чтобы весь её цикл (BA-постановка → task-arch → imp-doc) лежал вместе:
```
specs/docs/features/<feature>/tasks/<task-slug>/
    <task-slug>.md                                   ← этот task-doc
    jira-tickets/<component>/<task-slug>.md           ← сюда позже ляжет task-arch
    jira-tickets/<component>/imp/GDV1-<task-slug>.md  ← и imp-doc
```
- Папка фичи существует → создать `specs/docs/features/<feature>/tasks/<task-slug>/` и положить файл туда.
- Новая область → спросить имя фичи в kebab-case, создать `specs/docs/features/<feature>/tasks/<task-slug>/`.
- `<task-slug>` — короткий kebab-case-слаг задачи (например `configurable-modbus-address-registers`); он же станет именем файла и слагом для арх/имп вниз по цепочке.
- **Не** класть task-doc плоско в `tasks/<task-slug>.md` (старый паттерн) — тогда задаче некуда вложить `jira-tickets/` и imp-doc оторвётся от постановки.

### Шаг 3. Прочитать основные доки

В этом порядке, обязательно:

1. **Шаблон**: `specs/templates/task-template.md` — единственный источник структуры. Все секции и их порядок берутся отсюда.
2. **Контекст агента**: `specs/docs/agent-context/index.md` (и `firmware.md`, если задача про firmware) — навигация по доке.
3. **Доки фичи** в `specs/docs/features/<feature>/` (если существует): `index.md`, `overview.md`, `biz/` (примеры BA-постановок этой фичи), `questions.md`, `contracts/`.
4. **Component-доки выбранных на Шаге 1 частей** — только релевантные:
   - firmware → `specs/docs/components/firmware/index.md`, `projectArchitecture.md`, плюс тематически близкие (`sensor-models.md`, `sensorOperationsGuide.md`).
   - frontend → `specs/docs/components/frontend/index.md` и тематически близкие.
   - backend → `specs/docs/components/backend/index.md` и тематически близкие.
5. **Контракты для активных границ** (по выбору на Шаге 1) — индекс соответствующей пары:
   - frontend+backend → `specs/docs/contracts/frontend-backend/index.md`
   - backend+firmware → `specs/docs/contracts/backend-firmware/index.md`
   - frontend+firmware → `specs/docs/contracts/frontend-firmware/index.md`
   Открыть конкретный контракт по теме задачи, если он уже существует, чтобы сослаться на него, а не переписывать JSON.
6. **System-обзор**: `specs/docs/system/index.md` — общесистемный контекст.

Читать только релевантное по `related`-ссылкам, не сканировать папки целиком.

### Шаг 4. Уточнить пробелы

Если после чтения остаются неоднозначности (что входит в скоуп каждой части, какие числовые границы, какие инварианты обязательны, какие контракты затрагиваются), задать уточняющие вопросы через AskUserQuestion **до** написания. Не выдумывать значения для Invariants/Boundaries/Contracts — это критичные секции.

### Шаг 5. Согласовать план

До записи файла показать пользователю:

- Имя файла и путь.
- Строку `Affects:` (выбранные части).
- Список не-целей (Non-goals / Boundaries).
- Перечень инвариантов (`INV-n`) одной строкой каждый.
- Перечень границ из таблицы Boundaries / Limits (с конкретными значениями).
- Перечень межсистемных границ, попадающих в Contracts (или ссылку на существующий контракт).

Дождаться явного одобрения. Без одобрения файл не писать (см. `feedback_approve_before_edit`).

### Шаг 6. Написать файл

Создать файл по согласованному пути строго по скелету из `task-template.md`.

## Правила именования и расположения

- Расположение: `specs/docs/features/<feature>/tasks/<task-slug>/` — **отдельная подпапка на каждую задачу**. Если папки (`tasks/` или `tasks/<task-slug>/`) нет — создать.
- Имя файла: `<task-slug>.md` (тот же kebab-слаг, что и у папки задачи; например `tasks/add-mcp-config-persistence/add-mcp-config-persistence.md`). Папка и файл носят одинаковый слаг, и этот же слаг переиспользуют `task-arch` (`jira-tickets/<component>/<task-slug>.md`) и `imp-doc` (`jira-tickets/<component>/imp/GDV1-<task-slug>.md`) внутри той же папки задачи.
- Если папка `tasks/<task-slug>/` уже существует — уточнить у пользователя, дополняем существующую задачу или это другая (другой слаг). Не перезаписывать молча.

## Жёсткие правила содержания (из шаблона, критичны)

- **Язык документа — русский.** Заголовки секций и структурные ключи (`Affects`, `INV-n`, `Boundary N`, названия секций шаблона) — ровно как в `task-template.md`, не переводить. Идентификаторы кода, пути к файлам, имена полей/enum/методов, MQTT-топики и contract-лексику не переводить. Весь остальной текст — прозу, буллеты, ячейки таблиц — писать по-русски, живым понятным языком, а не машинным переводом. Без эмодзи, без маркетинга.
- **Affects** вверху — только выбранные части; секции `Scope per system` и блоки Contracts — только для затронутых систем.
- **Под небольшую задачу не раздувать.** Большинство секций — 1–3 буллета. Пустую секцию удалить, а не оставлять заглушку.
- **Invariants, Boundaries, Contracts — только конкретные значения с единицами.** Никаких «fast / soon / large». Инварианты нумеровать `INV-n`; каждый инвариант и каждую границу покрыть строкой в Acceptance.
- **Non-goals / Boundaries — обязательная секция**, причина на каждую строку.
- **Contracts:** один блок на границу (`A ↔ B`) со всеми подпунктами шаблона (Transport, Authentication, Operations, Data semantics, Errors, Idempotency, Limits, Versioning). Тривиальные in-process вызовы не включать. Если канонический контракт уже есть в `docs/contracts/` — сослаться, не переписывать JSON.
- **WHAT, не HOW.** Без DDL, имён классов, HTTP-методов конкретных эндпоинтов, точных имён env — это уровень тикета/арх-дока.
- **Edge cases / Acceptance** трассируются обратно к `INV-n` или строке Boundaries.
- **Open questions** — формулировать вопросами, не TODO.
- **Без комментариев-плейсхолдеров** (`<!-- TODO -->`) в финальном тексте — только содержательный текст или явные Open questions.

## После записи

Сообщить пользователю:

- Путь к созданному файлу (markdown-ссылкой).
- Открытые вопросы, оставшиеся в доке.
- Если обнаружились нестыковки в существующих доках фичи или контрактах — перечислить отдельным списком, не править их без отдельного запроса.
