# Создание арх-дока задачи (task-arch-doc)

Скил проектирует, **как один компонент реализует** уже сформулированную задачу. Вход — готовая BA-постановка (task-doc по `task-template.md`). Результат — markdown-файл строго по структуре `specs/templates/task-arch-doc-template.md`.

task-arch относится к task-doc так же, как phase-doc к feature-doc: task-doc фиксирует **ЧТО** (цель, инварианты `INV-n`, границы, контракты, acceptance), task-arch — **КАК** этот компонент это строит (слои, точки вмешательства, алгоритмы, стейты, обработка ошибок). Не повторять то, что уже в task-doc — ссылаться.

Этот скил — для уровня **задачи**. Для архитектуры целой фичи или её фазы использовать `feature-arch`. Для самой постановки — `task-doc`.

## Шаги (выполнять строго по порядку, не пропускать)

### Шаг 1. Найти task-doc

**Обязательно через AskUserQuestion**, если из запроса неоднозначно, для какого task-doc делаем арх:

> Для какой задачи делаем арх? Укажи путь к task-doc (например `specs/docs/features/sensor/tasks/configurable-modbus-address-registers/configurable-modbus-address-registers.md`) или назови фичу и задачу.

Резолвить путь, проверить, что файл существует и оформлен по `task-template.md` (есть `Affects:`, `Invariants`, `Acceptance`). Если файла нет или это не task-doc — остановиться и предложить сначала сделать постановку через `task-doc`.

### Шаг 2. Определить компонент

Прочитать строку `Affects:` task-doc.

- Один компонент → он и есть целевой, отдельный файл арха на него.
- Несколько компонентов → **обязательно через AskUserQuestion** спросить, для какого компонента делаем арх сейчас (один арх-док = один компонент). Можно сделать несколько арх-доков, по одному на компонент, но каждый — отдельным проходом.

Компонент определяет язык документа, набор component-доков для чтения и расположение файла.

### Шаг 3. Прочитать контекст

В этом порядке, обязательно:

1. **Шаблон**: `specs/templates/task-arch-doc-template.md` — единственный источник структуры. Все секции и их порядок берутся отсюда.
2. **task-doc целиком** — это источник-истина. Выписать список всех `INV-n` и все строки `Acceptance`: под них в архе пойдут секции «Соответствие инвариантам» и «Тест-план».
3. **Component-доки выбранного компонента**:
   - firmware → `specs/docs/components/firmware/`: `index.md`, `projectArchitecture.md`, `projectStructureDirectoryDescription.md`, плюс тематически близкие (`sensor-models.md`, `sensorOperationsGuide.md`).
   - backend → `specs/docs/components/backend/index.md` и тематически близкие.
   - frontend → `specs/docs/components/frontend/index.md` и тематически близкие.
4. **Контракты для активных в задаче границ** — открыть конкретный контракт по теме задачи в `specs/docs/contracts/<pair>/`, чтобы сослаться на него, а не переписывать JSON.
5. **Если задача — часть фичи с уже написанным арх-доком фичи** в `specs/docs/features/<feature>/jira-tickets/<component>/architecture.md` — прочитать его и согласовать терминологию/контракты.
6. **Соседние task-arch / phase-доки** в `specs/docs/features/*/jira-tickets/<component>/` — для согласованности тона и переиспользования контрактов.
7. **Реальный код компонента** — при необходимости найти существующие классы/интерфейсы/сервисы, которые станут точками вмешательства, чтобы называть их фактическими именами и путями в исходниках.

Читать по `related`-ссылкам, не сканировать папки целиком.

### Шаг 4. Уточнить пробелы

Если после чтения остаются неоднозначности (какой слой берёт на себя какой `INV-n`, какие классы расширяются vs добавляются, какие границы активны в задаче, как именно покрываются acceptance-проверки), задать уточняющие вопросы через AskUserQuestion **до** написания. Не выдумывать имена классов и пути — если непонятно, спросить или найти в коде.

### Шаг 5. Согласовать план

До записи файла показать пользователю:

- Имя файла и путь (см. правила именования ниже).
- Целевой компонент.
- «Раскладку по реализации» одной строкой: какие слои/сервисы/классы затрагиваются.
- Таблицу `INV-n → как гарантируется` хотя бы тезисно (строка на каждый инвариант task-doc).
- Перечень границ, попадающих в Контракты (или ссылку на канонический контракт).

Дождаться явного одобрения. Без одобрения файл не писать (см. `feedback_approve_before_edit`).

### Шаг 6. Написать файл

Создать файл по согласованному пути строго по «Шаблон-каркасу» из `task-arch-doc-template.md`. Перед сохранением пройти по чек-листу в конце шаблона.

## Правила именования и расположения

- Расположение: **внутри папки задачи**, рядом с её BA-постановкой — `specs/docs/features/<feature>/tasks/<task-slug>/jira-tickets/<component>/`. Если папок (`jira-tickets/` или `jira-tickets/<component>/`) нет — создать. Слаг `<task-slug>` берётся из папки task-doc (`tasks/<task-slug>/<task-slug>.md`), которую и резолвишь как вход. Так весь цикл задачи (BA → task-arch → imp) лежит в одной папке `tasks/<task-slug>/`.
  - Исключение — задача является **частью фичи с feature-level арх-доком** (фичевый цикл, фазы): тогда место — `specs/docs/features/<feature>/jira-tickets/<component>/` в корне фичи, рядом с `architecture.md` и phase-доками (этим владеет `feature-arch`). Различай: отдельная задача → папка задачи; фаза/часть целой фичи → корень фичи.
- Имя файла: тот же kebab-slug, что у task-doc, например `configurable-modbus-address-registers.md`. Тот же слаг переиспользует `imp-doc` в подпапке `imp/` рядом.
- Если в той же папке уже есть файл с этим именем — уточнить у пользователя, дополняем существующий или это другой компонент.

## Жёсткие правила содержания

Берутся из шаблона, но критичны и легко забываются:

- **Язык документа — по конвенции компонента.** Для firmware — английский (как в `feature-arch`): заголовки секций переводить с сохранением смысла (`## Контекст` → `## Context`, `## Цель реализации` → `## Implementation goal`, `## Обзор реализации` → `## Implementation overview`, `## Раскладка по реализации` → `## Implementation layout`, `## Соответствие инвариантам` → `## Invariant mapping`, `## Контракты между системами` → `## Contracts between systems`, `## Поток (happy path)` → `## Flow (happy path)`, `## Алгоритмы` → `## Algorithms`, `## Машины состояний / lifecycles` → `## State machines / lifecycles`, `## Обработка ошибок` → `## Error handling`, `## Данные и состояние` → `## Data and state`, `## Безопасность и приватность` → `## Security and privacy`, `## Деплой / Эксплуатация` → `## Deployment / Operations`, `## Тест-план` → `## Test plan`, `## Открытые вопросы` → `## Open questions`, `## Ссылки` → `## References`). Без эмодзи, без маркетинга.
- **Не повторять task-doc.** Цель, не-цели, инварианты, границы, acceptance уже зафиксированы в постановке — на них ссылаться, не копировать. Дублирование целых кусков — сигнал плохой границы задачи.
- **Это документ уровня реализации.** Реальные имена слоёв (`Core/Domain`, `Application/Services`, `Infrastructure/Adapters`), существующие классы/интерфейсы/сервисы по именам (`SensorService`, `ModuleSetupService`, `ModbusSensorReader`, `IRepository`) и пути в `src/` — **ожидаются и нужны**. DDL и точные имена env — не сюда, в тикет.
- **Пути новых файлов/папок в Implementation layout сверять с `projectStructureDirectoryDescription.md`.** Если для категории уже есть папка (например утилиты — `Core/Utils`, а не `Core/Domain/Utils`), класть туда; не выдумывать путь по памяти и не плодить дубли-папки. Прежде чем ввести новую папку — убедиться, что в структурном доке нет существующей под эту категорию.
- **«Соответствие инвариантам» — строка на каждый `INV-n`** из task-doc. Если инвариант обеспечивается не этим компонентом — так и написать.
- **«Тест-план» — строка на каждую строку Acceptance** из task-doc, с указанием, чем покрывается (нативный unit-тест, мок, ручная проверка на железе).
- **Контракты** — только границы, активные в этой задаче. Канонический контракт из `docs/contracts/` — ссылкой, не переписывать JSON. У каждой включённой границы — подпункты шаблона (транспорт, auth, операции, данные, ошибки, идемпотентность, лимиты). Тривиальные in-process вызовы не включать.
- **Happy path** — одна последовательность без ветвлений в нумерации; развилка отдельным абзацем.
- **«Безопасность» и «Деплой»** — опустить, если задача не вводит новых секретов / доверительных границ / persisted-данных / конфигов / миграций / env. Требования к версиям соседей — в Контракты как Лимиты/Ошибки.
- **«Обработка ошибок» / «Машины состояний» / «Алгоритмы» / «Данные и состояние»** — заполнять там, где применимо; опускать, где нечем, а не растягивать.
- **Open questions** — формулировать вопросами, не TODO.
- **ASCII-диаграммы**, не mermaid.
- **Без комментариев в коде** и без комментариев-плейсхолдеров (`<!-- TODO -->`) в финальном тексте — только содержательный текст или явные Open questions.

## После записи

Сообщить пользователю:

- Путь к созданному файлу (markdown-ссылкой).
- Какие `INV-n` обеспечиваются не этим компонентом (если такие есть) — чтобы пользователь учёл это при разбиении по системам.
- Какие открытые вопросы по реализации остались в доке.
- Если в процессе обнаружились нестыковки между task-doc и реальностью кода (инвариант, который нечем обеспечить; acceptance, который невозможно проверить; контракт, расходящийся с `docs/contracts/`) — перечислить отдельным списком, не править task-doc и контракты без отдельного запроса.
