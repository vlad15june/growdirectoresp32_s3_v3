# Релиз: бамп версии + release notes

Скил поднимает версию, формирует release notes по изменениям с момента прошлого релиза и коммитит результат.

Артефакты:
- `VERSION` — единственная строка с версией в кавычках, например `"2.2.5"`.
- `ReleaseNotes.md` — человекочитаемые release notes, новая версия добавляется сверху.

## Шаги (строго по порядку)

### Шаг 1. Определить диапазон изменений

Коммиты бампа версии имеют сообщение вида `#ver X.Y.Z`. Найти последний такой коммит — это граница прошлого релиза:

```
git log --oneline --grep="#ver" -n 1
```

Диапазон изменений для анализа — от этого коммита до `HEAD`:

```
git diff <last_ver_commit>..HEAD
git log <last_ver_commit>..HEAD --oneline
```

Учитывать ТОЛЬКО изменения в этом диапазоне. Если новых коммитов нет — остановиться и сообщить пользователю, релиз делать не из чего.

### Шаг 2. Поднять версию

Прочитать текущую версию из `VERSION`. По умолчанию поднимать patch (последнее число): `2.2.4` → `2.2.5`. Если пользователь явно просит minor/major — поднять соответствующий разряд и обнулить младшие.

Записать новую версию в `VERSION` строго в том же формате — в кавычках, без перевода строки сверх исходного.

### Шаг 3. Проанализировать изменения

Прочитать `git diff` и сообщения коммитов из диапазона. Номера тикетов (`GDV1-XXXX`) брать из сообщений коммитов и тела diff.

Разложить изменения по категориям:
- **Added** — новое поведение / возможности устройства.
- **Changed** — изменения в существующем поведении.
- **Fixed** — исправления. Сюда — ТОЛЬКО существенные поломки. Одна строка на баг, с номером тикета из коммита.

### Шаг 3.6. Проверить и при необходимости обновить структурные доки

Если в диапазоне `<last_ver_commit>..HEAD` добавлялись/удалялись/переносились директории или файлы в `src/` (новые папки, реорг слоёв, новые сервисы/адаптеры/use cases) — сверить и привести в актуальное состояние два дока:
- `doc/projectStructureDirectoryDescription.md` — карта директорий; должна отражать КАЖДУЮ реальную папку `src/`.
- `doc/projectArchitecture.md` — концептуальный (слои + поток зависимостей); править ТОЛЬКО если изменились слои, направление зависимостей или ключевые компоненты (обычно при патч-релизе не требуется).

Проверка структурного дока:
```
find src -type d | sort
```
Каждая папка `src/` должна быть описана. Недостающие — добавить в том же стиле (заголовок-путь `##### \`/src/...\`` + строка описания, для вложенных — `######`).

Канон живёт в specs (`specs/docs/components/firmware/`). После правки локальной копии синхронизировать так, чтобы `doc/...` и `specs/docs/components/firmware/...` были ИДЕНТИЧНЫ:
```
diff doc/projectStructureDirectoryDescription.md specs/docs/components/firmware/projectStructureDirectoryDescription.md
diff doc/projectArchitecture.md specs/docs/components/firmware/projectArchitecture.md
```

Если структурных изменений в диапазоне нет — шаг пропустить, доки не трогать. Какие доки реально правились — запомнить для стейджа на Шаге 6.

### Шаг 4. Сформулировать release notes (язык поведения системы)

Release notes пишутся для бизнес-аналитиков и тестировщиков, которые НЕ знают код. Каждое описание — на уровне поведения системы: что теперь работает иначе, что появилось, что исправлено в поведении устройства или во взаимодействии с ним.

ЗАПРЕЩЕНО упоминать: имена переменных, функций, классов, констант, строки кода, значения, технические термины реализации.

Каждая строка — формата:
```
- **Краткий заголовок поведения**: GDV1-XXXX Описание того, что изменилось в работе системы с точки зрения пользователя или оборудования.
```

Пример (как уже принято в `ReleaseNotes.md`):
```
- **Sensor Type Synchronization**: GDV1-3261 Fixed critical bug where sensor types weren't being updated when server changed parameters
```

Язык записей — английский, как в существующем `ReleaseNotes.md`. Опускать пустые категории (если в релизе нет Fixed — секцию не добавлять).

### Шаг 4.5. АПРУВ release notes (обязательно, до записи файлов)

НИЧЕГО не записывать в файлы, пока пользователь не одобрил.

Показать пользователю в чате:
- новую версию (`X.Y.Z` → `X.Y.Z+1`) и тип бампа;
- полный текст черновика release notes (все категории и строки, как они лягут в файл).

Затем ЯВНО спросить апрув и ОСТАНОВИТЬСЯ, ждать ответа. Не писать `VERSION`/`ReleaseNotes.md` до явного «да/ок/апрув».

Если пользователь просит правки — внести и снова показать на апрув. Цикл повторять до явного одобрения.

### Шаг 5. Записать ReleaseNotes.md

Новый блок версии добавить СВЕРХУ (после строки `# Release Notes`), перед предыдущей версией. Формат блока — как у существующих:

```
## Version 2.2.5 (YYYY-MM-DD)

### Added
- ...

### Changed
- ...

### Fixed
- ...

---
```

Дату брать сегодняшнюю. Сохранить разделители `---` между версиями.

### Шаг 6. АПРУВ перед коммитом (обязательно), затем коммит

После записи обоих файлов НЕ коммитить сразу. Сначала второй апрув:
- показать `git diff --staged` (или содержимое staged-изменений) — ровно что уйдёт в коммит;
- подтвердить, что в стейдже только `VERSION` и `ReleaseNotes.md`, и назвать сообщение коммита `#ver X.Y.Z`.

Затем ЯВНО спросить апрув и ОСТАНОВИТЬСЯ, ждать ответа. Коммитить только после явного «да/ок/апрув».

После одобрения сделать коммит. В стейдж — `VERSION`, `ReleaseNotes.md` и (ТОЛЬКО если правились на Шаге 3.6) структурные доки `doc/projectStructureDirectoryDescription.md` / `doc/projectArchitecture.md` вместе с их specs-копиями `specs/docs/components/firmware/...`. Посторонние изменения рабочего дерева не подхватывать. Сообщение коммита — строго формата бампа:

```
#ver 2.2.5
```

Если ветка — `main`, сначала создать ветку (см. правила git в окружении), затем коммитить.

## Жёсткие правила

- ДВА обязательных апрува: (1) на текст release notes и версию ДО записи файлов (Шаг 4.5); (2) на staged-изменения ДО коммита (Шаг 6). Без явного апрува — не писать файлы и не коммитить. Молчание/продолжение разговора апрувом НЕ считается.
- Анализировать только диапазон `<last_ver_commit>..HEAD` — не тянуть старые изменения.
- В `### Fixed` — только существенные поломки, по строке на баг, с номером тикета.
- Никаких деталей реализации в тексте release notes (см. Шаг 4).
- Формат `VERSION` и стиль `ReleaseNotes.md` менять нельзя — следовать существующему.
- Сообщение коммита — ровно `#ver <new_version>`.
- В стейдж попадают `VERSION`, `ReleaseNotes.md` и — только если правились на Шаге 3.6 — структурные доки (`doc/...` + их specs-копии). Больше ничего.
- Структурные доки (Шаг 3.6) править только при реальных структурных изменениях в диапазоне релиза; `doc/...` и `specs/docs/components/firmware/...` обязаны остаться идентичны.
