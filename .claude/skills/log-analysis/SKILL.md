# Анализ бага по логам модуля

Скил для построения **доказательного** анализа бага: каждая гипотеза подтверждается парой «строка кода ↔ строка лога». Без этой пары — гипотеза не идёт в финальный отчёт.

Все артефакты складываются в `doc/log-analysis/<YYYY-MM-DD>-<slug>/`:

- `logs.txt` — скачанные логи из ELK
- `log-markers.md` — таблица маркеров логирования из кода
- `analysis.md` — финальный отчёт (создаётся только после апрува)

## Особый случай: ошибки сканирования / определения датчиков

Триггер: симптом про сканирование или определение датчиков (датчик не определился, определился не тот тип/модель, адрес не сменился, выбрана не та модель, дубликаты адресов и т.п.).

В этом случае задача — выдать **ОТЧЁТ О СКАНИРОВАНИИ** строго по алгоритму сканирования и определения датчика, со ссылками на строки скачанного лога. Только факты «что отправили / что получили / что прошло». Цель — чтобы пользователь сам проверил корректность.

ЗАПРЕЩЕНО в этом отчёте:
- давать советы, рекомендации, предлагать значения полей/регистров, предлагать фиксы кода;
- делать выводы «почему баг» и «как чинить»;
- любые гипотезы и интерпретации сверх того, что дословно в логе.

Если пользователь явно попросит анализ/причину/фикс — тогда отдельно и по его инструкции. По умолчанию — только отчёт.

Формат отчёта о сканировании:
- Идёт **перебор моделей** на каждом канале — обязательно показывать ПО КАЖДОМУ каналу (порту/пину) и ПО КАЖДОМУ перебираемому типу модели в порядке перебора:
  - **какой тип модели ищем** (имя типа + UID из лога);
  - **что отправили**: команда смены адреса (код функции, регистр, текущий адрес, новый адрес) и ping-кадр (дословно байтами из лога);
  - **что получили**: ответ/нет ответа, прочитанное значение, ожидаемый диапазон;
  - **что прошло / не прошло** и точная строка-причина (дословно из лога);
  - для **каждого** факта — **кликабельная markdown-ссылка** на конкретную строку скачанного лог-файла в формате `[logs-XXX.txt:NNNN](doc/log-analysis/<папка>/logs-XXX.txt#LNNNN)`. Номера строк брать ТОЛЬКО `grep -nE` по всему файлу целиком (абсолютные, без арифметики со смещениями/`sed`/`awk` диапазонами — это даёт неверные номера). Перед выдачей сверить 2-3 номера через `sed -n 'NNNNp' file`, чтобы строка совпадала с цитатой.
- В конце по каждому каналу: **какой тип модели в итоге выбран** (или «ни один»), на каком адресе сохранён.
- Отдельным блоком — **секция проверки и смены адресов** (`handleModbusAddressManagement` → `collectModbusSensorsAndAddresses` → `findDuplicateAddresses` → `assignNewAddresses`): что собрано, какие адреса, дубликаты, что помечено к смене, что реально сменили — каждый пункт со ссылкой `logs.txt:NNNN`.

Маркеры кода для отчёта (актуализировать чтением кода перед использованием): `scanPinForSensorTypes`, `detectSensor`, `assignNewAddresses` в [src/Application/Services/ModuleSetupService.h](src/Application/Services/ModuleSetupService.h); `scanModbusSensor`, `writeSensorAddress` в [src/Infrastructure/Adapters/Sensors/SensorReader.h](src/Infrastructure/Adapters/Sensors/SensorReader.h); `pingAddress`, `writeSensorAddress` в [src/Infrastructure/Adapters/Sensors/HardwareSensors/ModbusSensors/ModbusSensorReader.h](src/Infrastructure/Adapters/Sensors/HardwareSensors/ModbusSensors/ModbusSensorReader.h).

## Шаги (строго по порядку, не пропускать)

### Шаг 1. Собрать вход

**Через AskUserQuestion**, если что-то из перечисленного не задано в запросе:

- `BUG_DATE` — дата/время симптома (ISO-8601, UTC). Если пользователь даёт локальное время — уточнить таймзону и перевести в UTC до записи.
- `BUG_DESC` — короткое описание симптома (1-2 предложения).
- `MODULE_UID` — UID модуля (MAC), формат `XX:XX:XX:XX:XX:XX`.

Сформировать `SLUG` — kebab-case из 2-4 слов `BUG_DESC` (например `mqtt-reconnect-loop`).
Создать рабочую папку `doc/log-analysis/<YYYY-MM-DD>-<SLUG>/` (использовать дату из `BUG_DATE`).

### Шаг 2. Контекст по фиче

Определить, какие фичи / функционал затронуты симптомом. Прочитать в этом порядке:

1. `specs/docs/components/firmware/index.md` — индекс firmware-доков, найти релевантные тематические файлы (например `sensor-models.md`, `sensorOperationsGuide.md`).
2. Тематически близкие файлы из `specs/docs/components/firmware/` целиком.
3. Если симптом затрагивает фичу — `specs/docs/features/<feature>/` (`index.md`, `firmware.md`, `contracts/`).
4. Контракты backend↔firmware из `specs/docs/contracts/backend-firmware/index.md`, если симптом про обмен сообщениями/MQTT/REST.

Резолв пути к specs-репо — по правилу из CLAUDE.md (`.specs-repo.local` → `.specs-repo`). Если не резолвится — остановиться и спросить путь.

Зафиксировать список релевантных доков (с путями) — он пойдёт в `analysis.md`.

### Шаг 3. Тянуть логи

Использовать готовый CLI-скрипт [test_scripts/elk_download_logs_cli.py](test_scripts/elk_download_logs_cli.py).

Дефолтное окно: **±2 часа** вокруг `BUG_DATE`. Если симптом редкий или растянутый — расширять до суток, объём логов не страшен.

Запуск **строго через активацию venv** (см. `feedback_python_run_command`):

```
source .venv/bin/activate && python3 test_scripts/elk_download_logs_cli.py \
  --uid <MODULE_UID> \
  --from <ISO_FROM> \
  --to   <ISO_TO> \
  --out  doc/log-analysis/<YYYY-MM-DD>-<SLUG>/logs.txt
```

Если `logs.txt` оказался пустым — расширить окно ещё в 2-4 раза и повторить. Если всё равно пусто — остановиться, сказать пользователю «логов за окно нет», спросить уточнённую дату или UID.

### Шаг 4. Понять, что искать в логах

Прочитать код, относящийся к фиче/симптому (на основе шага 2). Выписать **точные** строки логирования — копировать формат сообщения, не пересказывать.

**В ELK попадает только то, что публикуется через MQTT.** Конкретно — вызовы кастомного логгера, объявленного в [src/Core/Domain/Interfaces/ILogger.h](src/Core/Domain/Interfaces/ILogger.h) и реализованного в [src/Infrastructure/Logging/MqttLogger.h](src/Infrastructure/Logging/MqttLogger.h). Глобальный инстанс — `mqttLogger` в [src/globals.h](src/globals.h), в коде обычно используется через указатель `logger->...`.

Какие вызовы дают строки в ELK:

- `logger->print(msg)` / `logger->println(msg)` / `logger->printf(fmt, ...)` — публикуется в `<defaultTopic>/<moduleUid>`.
- `logger->print("SUB", msg)` / `logger->println("SUB", msg)` / `logger->printf("SUB", fmt, ...)` — публикуется в `<defaultTopic>/SUB/<moduleUid>` (часто `SUB` = `"ERROR"`, `"INFO"`, `"WARN"`).
- `logger->log(LogLevel::X, msg)` / `logger->log(LogLevel::X, "SUB", msg)` — сообщение префиксуется `[debug|info|warning|error|critical]`.
- `logger->logJson(feature, action, details)` / `logger->logJson("SUB", feature, action, details)` — структурный JSON `{"log_level":"info","uid":...,"email":...,"accountUid":...,"moduleUid":...,"feature":"...","action":"...","details":...}`. Это самый удобный маркер для греп-а: ищется по `"feature":"<name>"` и `"action":"<name>"`.
- Локальные хелперы в сервисах, например `CommandService::logError(fmt, ...)` → внутри `logger->println("ERROR", buffer)`, `CommandService::logInfo(...)` → `logger->println("INFO", buffer)`. Похожие обёртки могут быть в других сервисах — искать `void log[A-Z][a-z]*\(` в нужном `*.h`.

Какие вызовы **НЕ попадают в ELK** (только в Serial-консоль) — не использовать как маркеры:

- Прямые `Serial.print` / `Serial.println` / `Serial.printf`.
- `ESP_LOGI` / `ESP_LOGE` / `ESP_LOGW` / `ESP_LOGD` (ESP-IDF).
- Вызовы `logger->...` в режиме `MqttLoggerMode::SerialOnly` (см. конструктор `mqttLogger` в `globals.h` — текущий дефолт может быть SerialOnly, тогда в ELK уйдут только явные `MqttOnly`/`MqttAndSerial` override).

Сохранить в `doc/log-analysis/<YYYY-MM-DD>-<SLUG>/log-markers.md` таблицу:

| Маркер (фрагмент сообщения) | Файл:строка | Метод логгера | Топик в MQTT | Что значит | Условие срабатывания |
|---|---|---|---|---|---|

Колонка «Метод логгера» — конкретный вызов из списка выше (`logger->println`, `logger->printf`, `logger->logJson`, `CommandService::logError`, и т.п.). Колонка «Топик» — `<defaultTopic>[/SUB]/<moduleUid>`, чтобы потом можно было фильтровать греп по подтопику (`/ERROR/`, `/INFO/`).

**Без этой таблицы дальше не идти** — она якорь, защищающий от фантазий на следующем шаге.

### Шаг 5. Грепать и формулировать гипотезы

По каждому маркеру из `log-markers.md` — `grep -nE` по `logs.txt`. Смотреть:

- наличие / отсутствие ожидаемых маркеров;
- порядок и интервалы между ними;
- повторы, флапы, ретраи;
- маркеры ошибок и предупреждений.

Каждую аномалию сформулировать как **утверждение** (не вопрос). Это и есть гипотеза.

### Шаг 6. Доказательство каждой гипотезы (жёсткий формат)

Для каждой гипотезы собрать карточку строго по форме:

```
Гипотеза: <что произошло, одним предложением>

Код:
  <repo-path>:<line> — <одна строка кода, дословно>
  (опционально вторая строка для контекста)

Лог:
  <timestamp> | <topic> | <message>
  (1-3 строки дословно из logs.txt, не пересказ)

Связка:
  <почему именно эта строка кода даёт именно этот лог в этот момент>
```

Правила:

- Если нет строки кода ИЛИ строки лога — гипотеза помечается `unconfirmed` и **не идёт** в основной список, только в раздел «Что осталось неподтверждённым».
- Логи цитировать дословно, со временем и топиком, как они в `logs.txt`. Никаких «лог говорит примерно...».
- Строка кода — реально существующая, проверить через Read перед вставкой.

### Шаг 7. Короткое резюме пользователю

В чат — 3-7 пунктов, по одной гипотезе на пункт, с пометкой `confirmed` / `unconfirmed` и одной строкой обоснования. Без полных карточек — они уйдут в md.

Спросить апрув на запись `analysis.md` (см. `feedback_approve_before_edit`). Без явного «да / апрув / пиши» — файл не создавать.

### Шаг 8. Записать analysis.md

Только после апрува. Путь: `doc/log-analysis/<YYYY-MM-DD>-<SLUG>/analysis.md`. Секции в этом порядке:

1. **Симптом** — `BUG_DESC` + точная дата/время в UTC.
2. **Окно анализа** — диапазон логов, объём (`wc -l logs.txt`).
3. **Модуль** — `MODULE_UID`.
4. **Релевантные доки** — список markdown-ссылок из шага 2.
5. **Маркеры в коде** — таблица из `log-markers.md` (либо ссылка на файл).
6. **Подтверждённые гипотезы** — карточки из шага 6 по форме «Код / Лог / Связка».
7. **Что осталось неподтверждённым** — гипотезы без полной пары код↔лог, с указанием, чего не хватило.
8. **Следующие шаги** — что проверить дальше (доп. логи, воспроизведение, изменения в коде). Без «исправлений» — это отдельный workstream.

## Жёсткие правила

- **Никаких выводов без пары «строка кода ↔ строка лога».** Это центральное правило скила.
- **Логи — дословно**, со временем и топиком. Не нормализовать, не сокращать, не парафразировать.
- Имена файлов и строки — кликабельные markdown-ссылки (`[file.cpp:42](src/file.cpp#L42)`).
- Анализ — на русском. Цитаты кода и логов — как есть, без перевода.
- **Без комментариев в коде** (см. `feedback_no_comments`), включая сниппеты внутри `analysis.md`.
- Не править исходный код в рамках этого скила — анализ, не фикс. Если найдена однозначная починка — упомянуть в «Следующих шагах», не делать.

## Сохранность артефактов (важно)

Папка `doc/log-analysis/` и любая её подпапка `<YYYY-MM-DD>-<SLUG>/` — **постоянное хранилище**, не временное:

- **Никогда не удалять** ни `doc/log-analysis/`, ни её подпапки, ни файлы внутри (`logs.txt`, `log-markers.md`, `analysis.md`) — ни в рамках этого скила, ни «для чистоты» после завершения, ни в последующих сессиях.
- Запрещено выполнять любые `rm`, `rm -rf`, `find ... -delete`, `git clean`, `git rm` и аналоги, нацеленные на `doc/log-analysis/**`.
- Если предыдущий анализ для того же бага уже существует (та же папка `<YYYY-MM-DD>-<SLUG>/`) — **не перезаписывать молча**: либо добавить суффикс к слагу (`-v2`, `-recheck`), либо явно спросить пользователя, что делать. Никакого `Write` поверх существующего `analysis.md` без явного «перезаписать».
- `logs.txt` оставлять на диске даже после окончания анализа — он нужен для повторных проверок и для аудита доказательств. Не «чистить» под предлогом размера.
- Если пользователь сам попросит удалить — спросить подтверждение и удалять только конкретно названный путь, не родительские папки.

## Что НЕ делать

- Не использовать оригинальный [test_scripts/elk_download_logs.py](test_scripts/elk_download_logs.py) (там константы прибиты сверху). Использовать только `elk_download_logs_cli.py`.
- Не запускать Python без активации venv.
- Не писать `analysis.md` до апрува.
- Не выдвигать гипотезы про код, который не открыт и не процитирован.
- Не сокращать логи «для краткости» — большой файл нормален, поиск идёт грепом.
- **Не удалять `doc/log-analysis/` и её содержимое** ни при каких обстоятельствах (см. секцию «Сохранность артефактов»).
