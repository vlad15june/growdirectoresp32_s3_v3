# Workflow — Система автоматизации последовательностей

**Дата:** 8 апреля 2026

---

## 1. Главная идея

**Workflow — это НЕ новая сущность на прошивке.** Для модуля (ESP32) Workflow не существует. Модуль работает только с правилами (Rules) — как сейчас.

**Workflow = группа обычных правил**, связанных в цепочку через новое поле зависимости. Каждый шаг Workflow — это расширенное правило, которое знает:
- За каким правилом (шагом) оно следует
- По какому условию ему запускаться

Понятие «Workflow» живёт **только на бэкенде и фронтенде** — как агрегирующая обёртка над группой правил.

```
┌─────────────────────────────────────────────────────┐
│              Что видит ПОЛЬЗОВАТЕЛЬ                  │
│                                                      │
│   Workflow "Фертигация"                              │
│   ┌────────┐ → ┌────────┐ → ┌────────┐              │
│   │ Шаг 1  │   │ Шаг 2  │   │ Шаг 3  │              │
│   │Клапан  │   │Помпа   │   │Клапан  │              │
│   └────────┘   └────────┘   └────────┘              │
│                                                      │
├──────────────────────────────────────────────────────┤
│              Что видит МОДУЛЬ                         │
│                                                      │
│   Правило A        Правило B          Правило C      │
│   deviceUid:valve  deviceUid:pump     deviceUid:valve│
│   dependsOn: —     dependsOn: A       dependsOn: B   │
│   stepNumber: 1    stepNumber: 2      stepNumber: 3  │
│                                                      │
│   Это обычные правила. Модуль не знает что они       │
│   часть чего-то большего.                            │
└──────────────────────────────────────────────────────┘
```

## 2. Расширение правила (Rule) для поддержки Workflow

Стандартное правило уже содержит всё для автономной работы: тип, условие, устройство, параметры. Для работы в цепочке нужно добавить **минимум новых полей**:

### Новые поля в BaseHwRuleDto

| Поле | Тип | Описание |
|------|-----|----------|
| `dependsOnRuleUid` | string / null | UID правила-предшественника. Если null — правило работает самостоятельно (как сейчас). Если заполнено — правило активируется только после старта предшественника. |
| `dependsOnDeviceUid` | string / null | UID устройства предшественника. Нужно для межмодульной координации: модуль следит за состоянием этого устройства по MQTT. |
| `stepNumber` | int / null | Номер шага в цепочке. Null для обычных правил. |
| `workflowUid` | string / null | UID Workflow (для репортинга на бэкенд). Null для обычных правил. |
| `workflowPriority` | int / null | Приоритет Workflow. Для разрешения конфликтов при пересечении устройств между Workflow. |

### Что НЕ меняется

- Все существующие типы правил (`schedule`, `sensor`, `step`, `loop`, `ph`, `ec`, `dimmer_auto`, `dimmer_manual`) — без изменений
- Хранение в `/data/rules.json` — без изменений (новые поля просто добавляются к JSON)
- Цикл оценки `EvaluateRulesUseCase` — расширяется, но не заменяется
- Синхронизация через `GET /rulelist` — без изменений (правила Workflow приходят в том же списке)
- Репортинг через `hardware/update` — без изменений (DeviceUpdateDto уже содержит `ruleUid`, `ruleType`)

## 3. Как модуль выполняет правило-шаг

### Обычное правило (как сейчас)
```
EvaluateRulesUseCase (каждую секунду):
  │
  ├── dependsOnRuleUid == null?  → Да → Оценить условие как обычно
  │                                      (датчик / расписание / цикл)
```

### Правило в составе Workflow
```
EvaluateRulesUseCase (каждую секунду):
  │
  ├── dependsOnRuleUid != null?  → Да → Проверить:
  │                                      1. Предшественник СТАРТОВАЛ?
  │                                         (устройство предшественника включилось)
  │                                      2. Собственное условие выполнено?
  │                                         (для sensor-режима)
  │                                      │
  │                                      ├── Оба ДА → Активировать правило
  │                                      └── Нет → Ждать
```

**Проверка «предшественник стартовал»:**

| Предшественник на том же модуле | Предшественник на другом модуле |
|--------------------------------|-------------------------------|
| Прямая проверка: `device.state` нужного устройства | По MQTT: модуль уже транслирует состояние всех своих устройств. Другой модуль слушает и видит что устройство-предшественник включилось. |

## 4. Межмодульная координация — уже работает

Ключевой инсайт: **модули уже передают по MQTT состояние своих устройств** (через `hardware/update`). Каждый модуль в сети видит какие устройства включены на других модулях.

```
Модуль A                    MQTT (локальная сеть)                 Модуль B
   │                              │                                  │
   │ Правило-шаг 1 сработало     │                                  │
   │ Клапан → ON                  │                                  │
   │                              │                                  │
   │ hardware/update:             │                                  │
   │  device.uid=valve1           │                                  │
   │  device.state=on             │                                  │
   │  device.ruleUid=rule-A       │                                  │
   │──────────────────────────────►│                                  │
   │                              │──────────────────────────────────►│
   │                              │                                  │
   │                              │    Модуль B видит:               │
   │                              │    "valve1 включён по rule-A"    │
   │                              │                                  │
   │                              │    У Модуля B есть правило-шаг 2 │
   │                              │    dependsOnRuleUid = rule-A     │
   │                              │    dependsOnDeviceUid = valve1   │
   │                              │                                  │
   │                              │    → Предшественник СТАРТОВАЛ!   │
   │                              │    → Проверить своё условие      │
   │                              │    → Активировать правило-шаг 2  │
```

**Никаких новых MQTT-топиков не нужно.** Используется уже существующий механизм обмена состояниями устройств по локальной сети.

## 5. Два режима Workflow

Все правила одного Workflow работают в одном режиме. Режим определяет тип правил в цепочке.

### Schedule-режим (по времени)

Правила-шаги используют типы: **On / Off / Pulse** (реализуются через существующие `schedule` и `loop` типы правил).

```
Триггер (07:00)
    │
    ▼
Правило-шаг 1 (schedule)         Правило-шаг 2 (loop)         Правило-шаг 3 (schedule)
Клапан → ON                       Помпа → Pulse 10/30 ×10      Клапан → OFF
dependsOn: null (первый)          dependsOn: правило 1          dependsOn: правило 2
    │                                 │                             │
    │  device.state = on              │  device.state = on          │  device.state = off
    │  → шаг 2 видит старт           │  → шаг 3 видит старт       │
    └─────────────────────────────────┴─────────────────────────────┘
```

### Sensor-режим (по датчику)

Правила-шаги используют типы: **Regular / Stepper Motor / Loop** (реализуются через существующие `sensor`, `step`, `loop` типы правил с добавлением Until-условия завершения).

```
Триггер (CO₂ < 800)
    │
    ▼
Правило-шаг 1 (sensor)            Правило-шаг 2 (step)
Вентилятор: From 800, Until 600   Шторы: Run 5мин, Wait 3мин, Until T<25
dependsOn: null                    dependsOn: правило 1
    │                                  │
    │  Шаги могут работать             │
    │  ПАРАЛЛЕЛЬНО                     │
    └──────────────────────────────────┘
```

**В sensor-режиме:** правило-шаг N+1 активируется когда предшественник СТАРТОВАЛ **И** собственное условие датчика выполнено. Шаги могут работать одновременно.

## 6. Что делает бэкенд (агрегирующая логика)

Бэкенд — единственное место, где существует понятие «Workflow». Он выполняет три функции:

### 6.1. Создание: разбивает Workflow на правила

```
Пользователь создаёт              Бэкенд                         Модули
Workflow с 3 шагами               │                               │
         │                        │ Создаёт 3 правила:            │
         │                        │  Rule A (step 1, depends: —)  │
         │                        │  Rule B (step 2, depends: A)  │
         │                        │  Rule C (step 3, depends: B)  │
         │                        │                               │
         │                        │ Отправляет правила            │
         │                        │ через стандартный механизм    │
         │                        │ (RuleCommandNotification)     │
         │                        │──────────────────────────────►│
         │                        │                               │
         │                        │ Все правила Synchronized?     │
         │                        │◄──────────────────────────────│
         │                        │                               │
         │                        │ → Workflow = Synchronized     │
```

### 6.2. Мониторинг: агрегирует статусы правил в статус Workflow

Бэкенд **уже получает** `hardware/update` с `ruleUid`, `ruleType`, `device.state` и всеми полями выполнения. Ничего нового модуль не отправляет.

Бэкенд знает какие правила принадлежат какому Workflow. По состояниям правил он вычисляет состояние Workflow:

| Состояние правил | Состояние Workflow |
|------------------|--------------------|
| Все правила Synchronized, ни одно не сработало | **Idle** (ожидание триггера) |
| Хотя бы одно правило активно (устройство ON по ruleUid) | **Running** |
| Все правила завершили выполнение (все шаги Done) | **Completed** |
| Любое правило в Error | **Error** |
| Не все правила Synchronized | **Synchronizing** |

### 6.3. Конфликт-менеджмент

При создании/редактировании:
- Устройство в обычном правиле → нельзя добавить в Workflow (красный)
- Устройство в другом Workflow → можно, но проверяется приоритет (жёлтый)
- Одинаковый приоритет + общее устройство → блокировка сохранения

## 7. Жизненный цикл Workflow (вид с бэкенда)

```
                    Создание Workflow
                    (бэк создаёт N правил)
                           │
                           ▼
                    ┌─────────────┐
                    │  Disabled    │  правила в mode: Off
                    └──────┬──────┘
                           │  Enable
                           │  (бэк переводит правила в mode: On,
                           │   отправляет RuleCommandNotification)
                           ▼
                    ┌──────────────┐
                    │ Synchronizing │  бэк ждёт Synchronized от всех правил
                    └──────┬───────┘
                           │  Все Synchronized (или 5мин → Error)
                           ▼
                    ┌─────────────┐
                    │    Idle     │  правила на модулях, ждут условий
                    └──────┬──────┘
                           │  Первое правило сработало
                           ▼
                    ┌─────────────┐
                    │   Running   │  бэк видит ruleUid в hardware/update
                    └──────┬──────┘
                          ╱ ╲
                    ▼          ▼
             ┌───────────┐  ┌─────────┐
             │ Completed │  │  Error  │
             └───────────┘  └─────────┘
```

**Ключевой момент:** бэкенд **не управляет** выполнением. Он только наблюдает. Модули сами выполняют правила автономно — как сейчас.

## 8. Как триггер Workflow превращается в условие правила

### Schedule-триггер

Триггер «каждый день в 07:00» → первое правило в цепочке получает `schedule.startAt = 07:00`. Остальные правила-шаги не имеют собственного расписания — они активируются по `dependsOnRuleUid`.

### Sensor-триггер

Триггер «CO₂ < 800 AND T > 25» → первое правило получает эти условия как свои `valueLow`/`valueHigh`. Остальные правила-шаги получают свои собственные sensor-условия (From/Until) + `dependsOnRuleUid`.

### Active Hours

Временное окно применяется ко **всем правилам** цепочки как `startDayTime`/`endDayTime`.

## 9. Отказоустойчивость

Так как Workflow — это обычные правила, вся существующая отказоустойчивость правил действует автоматически:

| Сценарий | Поведение | Источник |
|----------|-----------|----------|
| Потеря интернета | Правила продолжают работать автономно. Межмодульная координация через локальный MQTT. | Существующее поведение правил |
| Потеря локальной сети | Модуль не видит состояние устройства-предшественника. Таймаут 5 мин → Fail-Safe, устройства ВЫКЛ. | **Новое**: таймаут ожидания dependsOn |
| Датчик недоступен | Правило переходит в Error (`sensor_unreachable`). Бэк видит → Workflow = Error. | Существующая обработка ошибок датчиков |
| Пропало питание | Правила не выполняются. После загрузки — ручной перезапуск Workflow (бэк переводит все правила в mode: Off, потом заново On). | Существующее поведение + логика бэка |
| ModBus не принята | Устройство не включается → следующий шаг не видит старт → цепочка не продолжается. | Существующее поведение |

### Дополнение: Fail-Safe для цепочки

Единственное **новое поведение** на прошивке: если правило с `dependsOnRuleUid` ждёт старта предшественника дольше **5 минут** — оно переходит в Error. Это предотвращает «зависание» цепочки при потере связи между модулями.

## 10. Поток hardware/update — ничего не меняем

Модуль уже отправляет в `hardware/update` для каждого устройства:

```json
{
  "uid": "device-123",
  "state": "on",
  "isAuto": true,
  "ruleUid": "rule-A",
  "ruleType": "schedule",
  "ruleVersion": 3,
  "sensorValue": 25.5,
  ...
}
```

Бэкенд получает `ruleUid`, смотрит в свою базу — этот ruleUid принадлежит Workflow X, шаг 1. Следующий `hardware/update` говорит что `rule-B` активен — бэк знает: это шаг 2 того же Workflow. И так далее.

**Фронтенд** получает от бэка агрегированное состояние: «Workflow Фертигация — Running, шаг 2 из 3 активен».

## 11. Конфликты устройств

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Устройство  │     │ Устройство  │     │ Устройство  │
│  в ПРАВИЛЕ  │     │ в другом    │     │  СВОБОДНО   │
│             │     │  WORKFLOW   │     │             │
│  🔴 Красный │     │  🟡 Жёлтый  │     │  ⚪ Доступно │
│  Нельзя     │     │  Можно      │     │  Можно      │
│  выбрать    │     │  выбрать    │     │  выбрать    │
└─────────────┘     └─────────────┘     └─────────────┘
```

Приоритет между Workflow: меньше число = выше приоритет. Два Workflow с одинаковым приоритетом не могут делить устройство — блокировка при сохранении.

На уровне модуля конфликт приоритетов разрешается через поле `workflowPriority` в правиле — если два правила претендуют на одно устройство, побеждает правило с меньшим `workflowPriority`.

## 12. Резюме: что меняется на каждом уровне

### Прошивка (минимальные изменения)

| Изменение | Описание |
|-----------|----------|
| Новые поля в правиле | `dependsOnRuleUid`, `dependsOnDeviceUid`, `stepNumber`, `workflowUid`, `workflowPriority` |
| Логика оценки `dependsOn` | Если `dependsOnRuleUid` заполнено → проверить состояние устройства-предшественника перед активацией |
| Таймаут dependsOn | 5 минут ожидания старта предшественника → Error |

Всё остальное — без изменений: хранение, синхронизация, оценка условий, репортинг.

### Бэкенд (основная логика)

| Изменение | Описание |
|-----------|----------|
| Сущность Workflow | CRUD Workflow с шагами, конвертация шагов в правила |
| Конвертация Workflow → Rules | При создании/редактировании разбивает Workflow на правила с `dependsOn` |
| Агрегация состояний | По `ruleUid` из `hardware/update` собирает статус Workflow |
| Конфликт-менеджмент | Проверка устройств: Rule ↔ Workflow, Workflow ↔ Workflow |
| API для фронтенда | CRUD Workflow, дашборд, история |

### Фронтенд (визуализация)

| Изменение | Описание |
|-----------|----------|
| UI конфигурации | Wizard создания Workflow с шагами |
| Дашборд | Агрегированное состояние Workflow в реальном времени |
| Device Picker | Цветовая индикация: красный/жёлтый/свободно |

## 13. Ограничения V1

| Ограничение | Комментарий |
|-------------|-------------|
| Зависимости линейные | Шаг N зависит только от шага N-1. Ветвления нет. |
| Один режим на Workflow | Schedule и Sensor нельзя смешивать. |
| Нет шаблонов | Готовых шаблонов нет. |
| Нет Safety Limits | Аварийная остановка по датчику — в будущих версиях. |
| Fail-Safe таймаут фиксирован | 5 минут, не настраивается. |
| Только S3-модули | Sensor Director S3, Multichannel Director S3. |
