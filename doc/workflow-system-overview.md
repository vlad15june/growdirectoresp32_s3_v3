# Workflow — Система автоматизации последовательностей

**Дата:** 8 апреля 2026

---

## 1. Что такое Workflow

**Workflow** — это упорядоченная цепочка шагов (Steps), где каждый шаг управляет одним устройством. Шаги выполняются последовательно: шаг N активируется только после того, как шаг N-1 начал работу.

Workflow строится **поверх существующей инфраструктуры правил**: используются те же датчики, те же устройства, те же каналы управления (ModBus) и тот же механизм обмена данными (MQTT + HTTP). Однако Workflow — это **отдельная сущность**, не группа правил. Правила и Workflow живут параллельно и взаимно исключают друг друга по устройствам.

**Правило** = одно устройство, одно условие, автономная работа.
**Workflow** = несколько устройств, общий триггер, строгий порядок выполнения.

---

## 2. Два режима работы

Все шаги одного Workflow работают в одном режиме. Смешивать нельзя.

| Режим | Суть | Пример |
|-------|------|--------|
| **Schedule** (по времени) | Шаги выполняются по длительности. Датчики не участвуют в выполнении. | Фертигация: открыть клапан → дозировка 10 мин → закрыть клапан |
| **Sensor** (по датчику) | Шаги реагируют на показания датчиков. Шаг завершается при достижении целевого значения. | Вентиляция: включить вентилятор пока T > 28°C → включить шторы пока T > 30°C |

## 3. Из чего состоит Workflow

```
┌─────────────────────────────────────────────────┐
│                  WORKFLOW                        │
│                                                  │
│  Имя: "Утренняя фертигация"                     │
│  Режим: Schedule                                 │
│  Приоритет: 1                                    │
│                                                  │
│  ┌──────────────────────────────────┐            │
│  │         ТРИГГЕР                  │            │
│  │  Тип: Расписание                 │            │
│  │  Каждый день в 07:00             │            │
│  └──────────────────────────────────┘            │
│                                                  │
│  ┌──────────────────────────────────┐            │
│  │      АКТИВНЫЕ ЧАСЫ (опц.)       │            │
│  │  06:00 — 20:00, Пн–Сб           │            │
│  └──────────────────────────────────┘            │
│                                                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐       │
│  │  Шаг 1   │→ │  Шаг 2   │→ │  Шаг 3   │      │
│  │ Клапан   │  │ Помпа    │  │ Клапан   │       │
│  │ Вкл      │  │ Пульс    │  │ Выкл     │       │
│  └──────────┘  └──────────┘  └──────────┘       │
└─────────────────────────────────────────────────┘
```

### Триггер — что запускает Workflow

| Тип триггера | Описание |
|--------------|----------|
| **Расписание** | Запуск в конкретное время дня / по интервалу. Дни недели. |
| **Датчик** | Запуск при выполнении условий датчика. Несколько датчиков объединяются через AND/OR. Опциональная задержка (debounce) — условие должно держаться N секунд непрерывно. |

### Активные часы — когда Workflow разрешено работать

Опциональное временное окно (от–до) + дни недели. Вне этого окна триггер игнорируется. Если Workflow уже работает и окно закрывается — текущий шаг доработает, после чего Workflow остановится.

### Шаги — что делает Workflow

Каждый шаг = одно устройство + одно действие. Одно устройство — один шаг (нельзя использовать одно устройство дважды в рамках одного Workflow).

---

## 4. Типы действий в шагах

### Schedule-режим

| Действие | Описание |
|----------|----------|
| **On** | Включить устройство. Шаг считается начатым сразу. |
| **Off** | Выключить устройство. Шаг считается начатым сразу. |
| **Pulse** | Цикл вкл/выкл: N циклов с заданной длительностью каждого. Шаг считается начатым при запуске первого цикла. |

### Sensor-режим

| Действие | Описание |
|----------|----------|
| **Regular** | Устройство включается при значении From, работает пока не достигнет Until. |
| **Stepper Motor** | Включается на Run минут → ждёт Wait минут → проверяет Until. Если не достигнуто — повторяет. |
| **Loop** | Циклы вкл/выкл с проверкой Until после каждого. Завершается при достижении Until ИЛИ по числу циклов — что раньше. |

## 5. Как работает выполнение — Schedule-режим

```
Триггер сработал (07:00)
         │
         ▼
   ┌───────────┐
   │   Шаг 1   │  Клапан → ON
   │  Команда   │──── ModBus команда принята?
   │  принята   │              │
   └─────┬─────┘         Нет → СТОП. Ошибка.
         │ Да
         ▼
   ┌───────────┐
   │   Шаг 2   │  Помпа → Pulse (10мин вкл / 30мин выкл × 10 циклов)
   │  Запуск    │──── ModBus команда принята?
   │  первого   │              │
   │  цикла     │         Нет → СТОП. Все устройства ВЫКЛ.
   └─────┬─────┘
         │ Циклы завершены
         ▼
   ┌───────────┐
   │   Шаг 3   │  Клапан → OFF
   │  Команда   │
   │  принята   │
   └─────┬─────┘
         │
         ▼
   ✅ COMPLETED
```

**Ключевой принцип:** шаг N+1 запускается сразу после того, как шаг N **начался** (команда принята). Шаги НЕ ждут завершения предыдущего — они ждут только **старта**.

## 6. Как работает выполнение — Sensor-режим

```
Триггер сработал (CO₂ < 800 ppm)
         │
         ▼
   ┌───────────┐
   │   Шаг 1   │  Вентилятор → Regular
   │  From:800  │  Включается при CO₂ < 800
   │  Until:600 │  Работает пока CO₂ не достигнет 600
   └─────┬─────┘
         │ Устройство стартовало (команда принята)
         │ + условие датчика шага 2 выполнено
         ▼
   ┌───────────┐
   │   Шаг 2   │  Шторы → Stepper Motor    ← работает ПАРАЛЛЕЛЬНО с шагом 1
   │  Run: 5мин │  Until: T < 25°C
   │  Wait: 3мин│
   └─────┬─────┘
         │ Первый Run завершён
         │ + условие датчика шага 3 выполнено
         ▼
   ┌───────────┐
   │   Шаг 3   │  CO₂ клапан → Loop
   └─────┬─────┘
         │
         ▼
   Все шаги завершены → ✅ COMPLETED
```

**Отличие от Schedule:** в Sensor-режиме шаги могут выполняться **параллельно**. Шаг N+1 активируется когда:
1. Шаг N достиг порога «started» (Regular — команда принята, Loop — первый цикл пройден, Stepper — первый Run пройден)
2. **И** условие датчика шага N+1 выполнено

## 7. Межмодульная координация

Workflow может управлять устройствами на **разных модулях** (Multichannel Director). Модули координируются через локальную сеть.

```
┌──────────────────┐          Локальная сеть (MQTT)          ┌──────────────────┐
│  Модуль A        │  ◄──────────────────────────────────►   │  Модуль B        │
│                  │     "Шаг 1 на модуле A СТАРТОВАЛ"       │                  │
│  Шаг 1: Клапан   │ ─────────────────────────────────────►  │  Шаг 2: Помпа    │
│  (Multichannel)  │                                         │  (Multichannel)  │
└──────────────────┘                                         └──────────────────┘
        ▲                                                            ▲
        │                                                            │
        └────────── Оба модуля получают ПОЛНУЮ конфигурацию ─────────┘
                    Workflow при активации (все шаги, все
                    зависимости, параметры триггера)
```

Каждый модуль:
- Знает весь Workflow (все шаги, не только свои)
- Следит за сигналами «шаг начался» от других модулей через локальный MQTT
- Если сигнал от предыдущего шага не пришёл в течение **5 минут** → Fail-Safe (см. раздел 10)

## 8. Жизненный цикл Workflow

```
                    Создание
                       │
                       ▼
                ┌─────────────┐
                │  Disabled    │  ← можно редактировать, удалять
                └──────┬──────┘
                       │  Включение (Enable)
                       ▼
                ┌──────────────┐
                │ Synchronizing │  ← конфиг отправляется на модули
                └──────┬───────┘
                       │  Все модули подтвердили (или 5мин таймаут → Error)
                       ▼
                ┌─────────────┐
                │    Idle     │  ← ожидание триггера
                └──────┬──────┘
                       │  Триггер сработал
                       ▼
                ┌─────────────┐
                │   Running   │  ← выполнение шагов
                └──────┬──────┘
                      ╱ ╲
                     ╱   ╲
                    ▼     ▼
         ┌───────────┐  ┌─────────┐
         │ Completed │  │  Error  │
         └───────────┘  └─────────┘
               │             │
               └──────┬──────┘
                      │  Ожидание следующего триггера
                      ▼
               ┌─────────────┐
               │    Idle     │
               └─────────────┘
```

**Completed → Idle:** после успешного завершения Workflow возвращается в Idle и ждёт следующего срабатывания триггера (если он повторяющийся).

**Error → требуется ручное вмешательство:** при ошибке Workflow останавливается, все устройства выключаются. Повторный запуск — вручную.

---

## 9. Состояния шагов при выполнении

| Состояние | Описание |
|-----------|----------|
| **Pending** | Шаг ещё не достигнут |
| **Running** | Шаг выполняется |
| **Done** | Шаг завершён успешно |
| **Error** | Шаг остановлен из-за ошибки |

Workflow считается **Completed** только когда ВСЕ активированные шаги перешли в Done — включая все циклы последнего шага.

## 10. Отказоустойчивость и офлайн

### Двухканальная передача данных

Система **всегда** передаёт данные по двум каналам одновременно:
- **Сервер** (через интернет)
- **Локальная сеть** (через роутер)

Каналы работают параллельно. Если один отключился — второй продолжает.

### Сценарии отказа

```
┌─────────────────────────────────────────────────────────────────┐
│ Интернет есть + Локалка есть   →  Нормальная работа            │
├─────────────────────────────────────────────────────────────────┤
│ Интернет потерян + Локалка есть →  Workflow продолжает работу   │
│                                     Логи хранятся локально     │
│                                     (до 24 часов)              │
├─────────────────────────────────────────────────────────────────┤
│ Интернет потерян + Локалка потеряна → Каждый модуль доделывает  │
│                                       текущий шаг              │
│                                       Через 5 мин → FAIL-SAFE │
│                                       Все устройства ВЫКЛ      │
├─────────────────────────────────────────────────────────────────┤
│ Пропало питание                  →  Workflow останавливается    │
│                                     После включения —          │
│                                     РУЧНОЙ перезапуск          │
│                                     Workflow стартует заново    │
└─────────────────────────────────────────────────────────────────┘
```

### Недоступность датчика (Sensor-режим)

- Данные считаются свежими если получены в последние **30 секунд**
- Если нет свежих данных → ждём ещё **30 секунд**
- Если данные не пришли → СТОП, все устройства ВЫКЛ, ошибка «Sensor Unavailable»

### Отказ устройства (ModBus)

- Команда ModBus не подтверждена в течение **30 секунд** → СТОП, все устройства ВЫКЛ
- Модуль перестал отвечать по локальной сети → ждём **5 минут** → СТОП

## 11. Конфликты: Workflow vs Правила vs Другие Workflow

Правила и Workflow **взаимно исключают** друг друга на уровне устройства. Одно устройство не может быть и в правиле, и в Workflow одновременно.

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Устройство  │     │ Устройство  │     │ Устройство  │
│  в ПРАВИЛЕ  │     │ в другом    │     │  СВОБОДНО   │
│             │     │  WORKFLOW   │     │             │
│  🔴 Красный │     │  🟡 Жёлтый  │     │  ⚪ Доступно │
│  Нельзя     │     │  Можно      │     │  Можно      │
│  выбрать    │     │  выбрать    │     │  выбрать    │
└─────────────┘     └─────────────┘     └─────────────┘
```

### Приоритет между Workflow

Каждый Workflow имеет числовой приоритет (меньше число = выше приоритет).

- Два Workflow с **одинаковым** приоритетом **не могут** использовать одно устройство → блокировка при сохранении
- Два Workflow с **разным** приоритетом могут делить устройство → при одновременном выполнении, устройством управляет Workflow с более высоким приоритетом

## 13. Связь с существующей системой правил

| Аспект | Правила (Rules) | Workflow |
|--------|----------------|----------|
| Хранение на модуле | `/data/rules.json` | `/data/workflows.json` (отдельно) |
| Цикл оценки | `EvaluateRulesUseCase` (1 сек) | Отдельный цикл оценки триггера + выполнения |
| Чтение датчиков | Общий `SensorRepository` | Тот же `SensorRepository` |
| Управление устройствами | ModBus через `DeviceDigitalOut` | Тот же ModBus через `DeviceDigitalOut` |
| Синхронизация с сервером | `GET /rulelist` + MQTT push | `GET /workflowlist` + MQTT push |
| Репортинг состояния | `hardware/update` (поля ruleUid, ruleType) | `hardware/update` (поля workflowUid, stepNumber) |
| Блокировка устройства | Устройство заблокировано для Workflow | Устройство заблокировано для правил |

**Что переиспользуется:**
- Чтение и подписка на датчики
- Отправка команд на устройства (ModBus)
- Алгоритмы сравнения значений датчиков с порогами
- Алгоритмы проверки расписания и временных окон
- Механизм `hardware/update` для репортинга на бэкенд
- MQTT-инфраструктура для приёма команд с сервера

**Что новое:**
- Сущность Workflow с шагами и зависимостями
- Оценка триггера (отдельно от оценки правил)
- Оркестрация шагов с отслеживанием зависимостей
- Межмодульная координация по локальному MQTT
- Fail-Safe при потере связи между модулями
- Механизм приоритетов между Workflow

## 14. Ограничения V1

| Ограничение | Комментарий |
|-------------|-------------|
| Зависимости линейные | Шаг N зависит только от шага N-1. Ветвления нет. |
| Один режим на Workflow | Schedule и Sensor нельзя смешивать в одном Workflow. |
| Нет шаблонов | Готовых шаблонов Workflow нет. |
| Нет версионирования | Нет истории изменений конфигурации. |
| Нет Safety Limits | Аварийная остановка по датчику — в будущих версиях. |
| Fail-Safe таймаут фиксирован | 5 минут, не настраивается пользователем. |
| Только S3-модули | Sensor Director S3, Multichannel Director S3. |
