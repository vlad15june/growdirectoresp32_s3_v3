# GDV1-3202: Automatic Offline Sensor Rescanning with Queue Management

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3202

---

## Ticket Description

### Problem Statement

Sensors with status `SENSOR_STATUS_ADDED` that go offline (disconnected, communication failures, hardware issues) remain in error state indefinitely without automatic recovery attempts. The system currently detects offline sensors and marks them with errors, but does not attempt to rescan them to check if they have reconnected or recovered. This results in false-negative sensor states where sensors may have physically reconnected but remain marked as offline in the system, requiring manual intervention or module reboot to restore functionality.

### Solution

Implement automatic offline sensor rescanning mechanism with queue-based management that:
- Continuously monitors sensors with status `SENSOR_STATUS_ADDED` for offline/error conditions
- Detects sensors that have been offline for more than **30 minutes**
- Adds offline sensors to a rescan queue for systematic recovery attempts
- Processes rescan queue with controlled timing: **one sensor every 20 minutes**
- Prevents simultaneous scanning of multiple sensors to avoid resource contention
- Uses existing sensor scanning infrastructure (`ISensorReader::scanSensor()`)
- Updates sensor status based on rescan results (restore to active or keep in error state)
- Provides comprehensive logging for monitoring and troubleshooting
- Works transparently in background without impacting normal sensor reading operations

### Technical Approach

Leverage existing infrastructure and implement queue-based scanning service:
1. Create new `SensorRescanService` to manage offline sensor detection and rescanning
2. Implement detection logic that monitors sensors with `SENSOR_STATUS_ADDED` and `isError == true`
3. Track offline duration for each error sensor using timestamps
4. Maintain rescan queue (FIFO) for sensors eligible for rescanning
5. Implement queue processing logic with 20-minute intervals between rescans
6. Use existing `ISensorReader::scanSensor()` for actual sensor detection
7. Update sensor status via `ISensorRepository` based on rescan results
8. Integrate into existing loop service architecture
9. Provide detailed logging for all queue operations and rescan attempts

## Development Plan

### **Overview**
Implement a dedicated `SensorRescanService` that operates as a background monitoring system for offline sensors. The service consists of two main components: (1) detection component that periodically scans all ADDED sensors for offline conditions lasting >30 minutes and enqueues them for rescanning, and (2) processing component that dequeues sensors one at a time with 20-minute spacing and attempts to rescan them using existing sensor scanning infrastructure. This two-service architecture ensures systematic recovery attempts without overwhelming the system, while maintaining full separation of concerns between detection and rescanning operations.

## Implementation Details

### **Rescan Queue Architecture:**

```
┌─────────────────────────────────────────────────────────────┐
│              SensorRescanService                             │
│                                                              │
│  ┌────────────────────────────────────────────────────┐    │
│  │  Detection Component (every 5 minutes)             │    │
│  │                                                     │    │
│  │  1. Get all ADDED sensors with isError=true        │    │
│  │  2. Calculate offline duration for each            │    │
│  │  3. If offline >= 30 min AND not in queue:         │    │
│  │     → Add to rescan queue                          │    │
│  └────────────────────────────────────────────────────┘    │
│                          ↓                                   │
│  ┌────────────────────────────────────────────────────┐    │
│  │  Rescan Queue (FIFO)                               │    │
│  │  [sensor1_uid, sensor2_uid, sensor3_uid, ...]      │    │
│  └────────────────────────────────────────────────────┘    │
│                          ↓                                   │
│  ┌────────────────────────────────────────────────────┐    │
│  │  Processing Component (every 20 minutes)           │    │
│  │                                                     │    │
│  │  1. Dequeue next sensor                            │    │
│  │  2. Call sensorReader->scanSensor()                │    │
│  │  3. Update sensor status based on result           │    │
│  │  4. Log rescan outcome                             │    │
│  └────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

### **State Machine for Sensor Rescanning:**

```
SENSOR_STATUS_ADDED (active, no error)
         ↓
   [Sensor goes offline]
         ↓
SENSOR_STATUS_ADDED (active=false, isError=true)
   offline_start_time = millis()
         ↓
   [Wait 30 minutes]
         ↓
   [Detection: offline >= 30 min]
         ↓
ADDED TO RESCAN QUEUE
         ↓
   [Wait in queue (up to 20 min)]
         ↓
   [Processing: dequeue and rescan]
         ↓
  sensorReader->scanSensor()
         ↓
    ┌─────────┴─────────┐
    ↓                   ↓
[SUCCESS]          [FAILURE]
    ↓                   ↓
Set active=true    Keep isError=true
Set isError=false  Continue offline tracking
Remove from tracking  May be re-queued later
    ↓                   ↓
RECOVERED          STILL OFFLINE
```

### **Timing and Queue Management:**

**Detection Interval:** 5 minutes
- Scans all ADDED sensors for error conditions
- Lightweight operation, only checks sensor status in repository
- Adds eligible sensors to queue

**Rescan Interval:** 20 minutes
- Processes exactly ONE sensor from queue
- Heavyweight operation, actual hardware communication
- Ensures controlled resource usage

**Offline Threshold:** 30 minutes
- Sensor must be offline for 30 consecutive minutes before first rescan attempt
- Prevents rescanning sensors that may be temporarily disconnected
- Reduces unnecessary scanning overhead

**Queue Behavior:**
- FIFO (First In, First Out) - oldest offline sensors rescanned first
- Duplicate prevention - sensor can only be in queue once
- Persistent tracking - offline duration tracking survives sensor state changes
- Automatic cleanup - sensors removed from tracking upon successful rescan

### **Example Timeline:**

```
T=0:    Sensor goes offline (isError=true)
T=5m:   Detection runs, sensor only offline 5 min (< 30 min threshold) - no action
T=10m:  Detection runs, sensor offline 10 min - no action
T=15m:  Detection runs, sensor offline 15 min - no action
T=20m:  Detection runs, sensor offline 20 min - no action
        Rescan processing runs, but queue is empty - no action
T=25m:  Detection runs, sensor offline 25 min - no action
T=30m:  Detection runs, sensor offline 30 min (>= threshold)
        → Sensor added to rescan queue
        Queue: [sensor1]
T=35m:  Detection runs (sensor already in queue - skip)
T=40m:  Rescan processing runs
        → Dequeue sensor1 and rescan
        → If successful: sensor recovered
        → If failed: sensor remains offline, may be re-queued later
        Queue: []
```

### **Rescan Results Handling:**

**Successful Rescan:**
- Update sensor: `updateSensorStatus(uid, true, false)` (active, no error)
- Remove from offline tracking map
- Remove from queue tracking set
- Log: "Sensor {uid} successfully rescanned and recovered after {duration}"

**Failed Rescan:**
- Keep sensor in error state: `isError=true`, `isActive=false`
- Update offline start time to current time for future tracking
- Remove from queue (will be re-queued after 30 min if still offline)
- Log: "Sensor {uid} rescan failed, remains offline (offline duration: {duration})"

**Sensor Not Found:**
- Remove from queue
- Remove from tracking
- Log warning: "Sensor {uid} not found during rescan, removed from queue"

### **Resource Management:**

**Memory Usage:**
- Rescan queue: ~50 bytes per sensor UID (std::string)
- Offline tracking map: ~100 bytes per sensor (string + unsigned long)
- Queue tracking set: ~50 bytes per sensor
- Total per sensor: ~200 bytes
- For 50 offline sensors: ~10KB memory overhead

**CPU Usage:**
- Detection: Minimal, repository queries only (every 5 minutes)
- Rescan processing: One sensor scan every 20 minutes
- No impact on normal sensor reading operations
- No concurrent scans with regular sensor reading

**Network/Hardware:**
- One additional sensor scan every 20 minutes maximum
- Spread out over time to avoid overwhelming sensor communication
- Uses existing sensor scanning infrastructure (no new protocols)

## Safety Considerations

- **No Concurrent Scans**: Only one rescan at a time prevents resource contention
- **Controlled Timing**: 20-minute spacing prevents overwhelming sensor bus
- **Duplicate Prevention**: Sensors can only be queued once
- **Graceful Failure**: Failed rescans don't block queue processing
- **Memory Bounds**: Queue size limited by number of ADDED sensors (typically <100)
- **Module Reboot**: Queue is transient, rebuilt after reboot (acceptable)
- **Sensor Deletion**: Service handles sensors deleted while in queue
