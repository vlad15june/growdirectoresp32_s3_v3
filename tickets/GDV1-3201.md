# GDV1-3201: Automatic Sensor Status Transition from NEW to ADDED After Stable Operation

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3201

---

## Ticket Description

### Problem Statement

Currently, when sensors are detected during sensor scan or manually added via SetSensorModel command, they are assigned a status of `SENSOR_STATUS_NEW`. This status remains unchanged indefinitely, even when sensors are working correctly and providing stable readings. There is no automatic mechanism to transition sensors from `NEW` to `ADDED` status after they demonstrate stable operation. This prevents the system from distinguishing between newly detected sensors that are still being validated and sensors that have proven to be reliable over time.

### Solution

Implement automatic sensor status transition mechanism that:
- Tracks sensor operational stability time for each sensor with status `SENSOR_STATUS_NEW`
- Monitors sensor read success rate and error conditions during the validation period
- Automatically updates sensor status from `SENSOR_STATUS_NEW` to `SENSOR_STATUS_ADDED` after **1 hour (3600 seconds)** of stable, error-free operation
- Persists status update to sensor repository (SPIFFS storage)
- Resets validation timer if sensor encounters errors during the validation period
- Works transparently in the background within the existing `SensorService` loop
- Provides clear logging for status transitions and validation progress
- Maintains backward compatibility with existing sensor management flow

### Technical Approach

Leverage existing `SensorService` infrastructure to:
1. Add tracking fields to `SensorEntity` to store validation start time and consecutive successful reads
2. Modify `SensorService` to track sensor stability metrics during normal sensor reading operations
3. Implement validation logic that checks elapsed time since first successful read
4. Apply automatic status transition after 1 hour of stable operation (no errors)
5. Reset validation tracking if sensor encounters errors during validation period
6. Use existing `ISensorRepository::updateSensorStatusEnum()` to persist status changes
7. Log status transitions with detailed information for monitoring and debugging
8. Ensure thread-safe access to validation tracking data structures

### Related Tickets

- **GDV1-3182**: Automatic Module Reset After Prolonged Offline State - Similar automatic monitoring and state management approach
- **GDV1-3169**: DELETE Command for remote module wipe - Uses sensor repository update operations similar to status transitions

## Implementation Details

### **Backward Compatibility After Firmware Update:**

When updating firmware with this feature to modules that already have sensors in SPIFFS:

1. **Existing sensors without new fields:**
   - JSON deserialization will use default values from constructor (all zeros/false)
   - Fields: `firstSuccessfulReadTime = 0`, `consecutiveSuccessfulReads = 0`, `validationStarted = false`
   
2. **Behavior by sensor status:**
   - **Sensors with SENSOR_STATUS_ADDED:** No impact, validation doesn't run for ADDED sensors
   - **Sensors with SENSOR_STATUS_NEW:** Validation starts fresh on next successful read
   
3. **First update after firmware upgrade:**
   - When sensor is first read successfully, validation fields will be populated
   - Next repository save will include new fields in JSON
   - Subsequent reboots will preserve validation state

4. **No migration code needed:**
   - Default values are safe and correct
   - No data corruption risk
   - System continues working normally
   - Validation begins automatically for NEW sensors

**Important:** After firmware update, sensors with SENSOR_STATUS_NEW will need full 1 hour validation even if they were already working. This is acceptable because:
- Ensures validation consistency
- Happens only once after update
- Doesn't break functionality
- Provides confidence in sensor stability

### **Persistence Strategy:**

All validation tracking fields MUST be saved to SPIFFS after each update to survive:
- Module reboots (technical, offline recovery, user-initiated)
- Power cycles
- Firmware updates
- Crashes and watchdog resets

**When to persist:**
- After each successful sensor read (validation tracking updated)
- After validation reset due to errors
- After status transition from NEW to ADDED

**Why persistence is critical:**
- Module can reboot frequently (GDV1-3182: 15min offline threshold for sensor modules)
- Without persistence, 1-hour validation is impossible to complete
- Validation state must accumulate across reboots

**Implementation note:**
- Use existing `sensorRepository->save(sensor)` after updating validation fields
- Repository automatically handles JSON serialization to SPIFFS
- JSON converter must include new fields in serialization/deserialization

### **Sensor Validation State Machine:**

```
SENSOR_STATUS_NEW (validationStarted=false)
         |
         | First successful read
         v
SENSOR_STATUS_NEW (validationStarted=true, firstSuccessfulReadTime=millis())
         |
         | Accumulate successful reads for 1 hour
         | PERSISTED TO SPIFFS - survives reboots
         | Reset on any error
         v
   [60 minutes elapsed]
   [consecutiveSuccessfulReads >= 4]
         |
         v
SENSOR_STATUS_ADDED (validation complete)
```

### **Validation Criteria:**
- **Duration**: Minimum 1 hour (3600 seconds) of stable operation
- **Successful Reads**: At least 4 consecutive successful reads (with 15s read interval = 240 reads in 1 hour, we only require 4 minimum to avoid being too strict)
- **Error Tolerance**: Any read error during validation period resets the validation timer
- **Persistence**: Validation tracking fields are updated in repository after each read to survive reboots

### **Reboot Scenarios:**
1. **Module reboots during validation (e.g., offline recovery):**
   - Validation fields are loaded from SPIFFS
   - Validation continues from saved state
   - Example: 30 minutes accumulated before reboot → continues from 30 minutes after reboot
   
2. **Multiple reboots during validation period:**
   - Each reboot loads saved validation state
   - Validation accumulates across all reboots
   - Only successful uptime counts toward 1 hour total

3. **Reboot with sensor error before reboot:**
   - If sensor had error and validation was reset before reboot
   - Saved state reflects reset (validationStarted=false)
   - Validation starts fresh after reboot

**Critical:** Without SPIFFS persistence, frequent reboots would make it impossible to reach 1-hour validation threshold.

### **Example Log Output:**
```
SensorService: Sensor 48:27:E2:E2:01:78.01 validation started at 12345678 ms
SensorService: Sensor 48:27:E2:E2:01:78.01 validation progress: 4 successful reads, 60000 ms elapsed
SensorService: Sensor 48:27:E2:E2:01:78.01 validation progress: 8 successful reads, 120000 ms elapsed
...
SensorService: Sensor 48:27:E2:E2:01:78.01 status transitioned from NEW to ADDED after 3605000 ms (241 successful reads)
```

### **Error Handling:**
- If sensor read fails during validation: Reset validation, log reason, sensor remains in NEW status
- If repository update fails: Log error but continue operation, retry on next validation check
- If validation fields are corrupted: Reset validation automatically on next read

### **Thread Safety:**
- All sensor operations occur in main loop (single-threaded context)
- No mutex required as validation tracking runs in same context as sensor reading
- MQTT task may read sensor data but does not modify validation state
