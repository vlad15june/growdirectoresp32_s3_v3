# Workflow — Система автоматизации последовательностей

---

## 1. Главная идея

**Workflow — это НЕ новая сущность на прошивке.** Для модуля (ESP32) Workflow не существует. Модуль работает только с правилами (Rules) — как сейчас.

**Workflow = группа обычных правил**, связанных в цепочку через новое поле зависимости. Каждый шаг Workflow — это расширенное правило, которое знает:
- За каким правилом (шагом) оно следует
- По какому условию ему запускаться

Понятие «Workflow» живёт **только на бэкенде и фронтенде** — как агрегирующая обёртка над группой правил.

```
┌─────────────────────────────────────────────────────┐
│              Что видит ПОЛЬЗОВАТЕЛЬ                  │
│                                                      │
│   Workflow "Фертигация"                              │
│   ┌────────┐ → ┌────────┐ → ┌────────┐              │
│   │ Шаг 1  │   │ Шаг 2  │   │ Шаг 3  │              │
│   │Клапан  │   │Помпа   │   │Клапан  │              │
│   └────────┘   └────────┘   └────────┘              │
│                                                      │
├──────────────────────────────────────────────────────┤
│              Что видит МОДУЛЬ                         │
│                                                      │
│   Правило A        Правило B          Правило C      │
│   deviceUid:valve  deviceUid:pump     deviceUid:valve│
│   dependsOn: —     dependsOn: A       dependsOn: B   │
│   stepNumber: 1    stepNumber: 2      stepNumber: 3  │
│                                                      │
│   Это обычные правила. Модуль не знает что они       │
│   часть чего-то большего.                            │
└──────────────────────────────────────────────────────┘
```

## 2. Расширение правила (Rule) для поддержки Workflow

Стандартное правило уже содержит всё для автономной работы: тип, условие, устройство, параметры. Для работы в цепочке нужно добавить **минимум новых полей**:

### Новые поля в правиле

| Поле | Описание |
|------|----------|
| **Правило-предшественник** | Ссылка на предыдущее правило в цепочке. Если пустое — правило работает самостоятельно (как сейчас). Если заполнено — правило активируется только после старта предшественника. |
| **Устройство предшественника** | Ссылка на устройство предыдущего шага. Модуль следит за его состоянием для межмодульной координации. |
| **Номер шага** | Позиция в цепочке. Пустое для обычных правил. |
| **UID Workflow** | Принадлежность к Workflow (для бэкенда). Пустое для обычных правил. |
| **Приоритет Workflow** | Для разрешения конфликтов при пересечении устройств между Workflow. |
| **Блокирующие Workflow** | Список UID Workflow с более высоким приоритетом, которые делят устройства с этим Workflow. Заполняется бэкендом **только для первого шага**. Если любой из этих Workflow активен — первый шаг не запускается. |

### Что НЕ меняется

- Все существующие типы правил (schedule, sensor, step, loop, ph, ec, dimmer) — без изменений
- Правила Workflow хранятся, синхронизируются и репортятся **точно так же**, как обычные правила
- Модуль не различает «обычное правило» и «правило-шаг Workflow» — для него это одно и то же, просто с дополнительными полями

## 3. Как модуль выполняет правило-шаг

Модуль каждую секунду оценивает все свои правила. Единственное отличие для правил с предшественником:

```
Оценка правила (каждую секунду):
  │
  ├── Есть предшественник?  → Нет → Оценить условие как обычно
  │                                  (датчик / расписание / цикл)
  │
  └── Есть предшественник?  → Да  → Проверить:
                                     1. Устройство предшественника ВКЛЮЧИЛОСЬ?
                                     2. Собственное условие выполнено?
                                        (для sensor-режима)
                                     │
                                     ├── Оба ДА → Активировать правило
                                     └── Нет → Ждать
```

**Как модуль узнаёт что предшественник стартовал:**

| Предшественник на том же модуле | Предшественник на другом модуле |
|--------------------------------|-------------------------------|
| Прямая проверка состояния устройства | Модули уже обмениваются состояниями устройств по локальной сети. Модуль слушает и видит что устройство-предшественник включилось. |

## 4. Межмодульная координация — уже работает

Модули **уже передают по локальной сети состояние всех своих устройств**. Каждый модуль видит какие устройства включены на других модулях. Это существующее поведение — новых каналов связи не нужно.

```
Модуль A                    Локальная сеть                        Модуль B
   │                              │                                  │
   │ Правило-шаг 1 сработало     │                                  │
   │ Клапан → ON                  │                                  │
   │                              │                                  │
   │ Передаёт состояние:          │                                  │
   │  «Клапан включён,            │                                  │
   │   по правилу A»              │                                  │
   │──────────────────────────────►│                                  │
   │                              │──────────────────────────────────►│
   │                              │                                  │
   │                              │    Модуль B видит:               │
   │                              │    «Клапан включён по правилу A» │
   │                              │                                  │
   │                              │    У Модуля B есть правило-шаг 2 │
   │                              │    с предшественником = правило A│
   │                              │                                  │
   │                              │    → Предшественник СТАРТОВАЛ!   │
   │                              │    → Проверить своё условие      │
   │                              │    → Активировать правило-шаг 2  │
```

## 5. Два режима Workflow

Все правила одного Workflow работают в одном режиме. Режим определяет тип правил в цепочке.

### Schedule-режим (по времени)

Действия шагов: **On / Off / Pulse**.

```
Триггер (07:00)
    │
    ▼
Шаг 1                            Шаг 2                         Шаг 3
Клапан → ON                       Помпа → Pulse 10/30 ×10      Клапан → OFF
предшественник: —                 предшественник: шаг 1         предшественник: шаг 2
    │                                 │                             │
    │  Клапан включился               │  Помпа включилась          │
    │  → шаг 2 видит старт           │  → шаг 3 видит старт       │
    └─────────────────────────────────┴─────────────────────────────┘
```

### Sensor-режим (по датчику)

Действия шагов: **Regular / Stepper Motor / Loop**.

```
Триггер (CO₂ < 800)
    │
    ▼
Шаг 1                              Шаг 2
Вентилятор: From 800, Until 600    Шторы: Run 5мин, Wait 3мин, Until T<25
предшественник: —                  предшественник: шаг 1
    │                                  │
    │  Шаги могут работать             │
    │  ПАРАЛЛЕЛЬНО                     │
    └──────────────────────────────────┘
```

**В sensor-режиме:** правило-шаг N+1 активируется когда предшественник СТАРТОВАЛ **И** собственное условие датчика выполнено. Шаги могут работать одновременно.

## 6. Что делает бэкенд (агрегирующая логика)

Бэкенд — единственное место, где существует понятие «Workflow». Он выполняет три функции:

### 6.1. Создание: разбивает Workflow на правила

```
Пользователь создаёт              Бэкенд                         Модули
Workflow с 3 шагами               │                               │
         │                        │ Создаёт 3 правила:            │
         │                        │  Правило A (шаг 1, первое)    │
         │                        │  Правило B (шаг 2, после A)   │
         │                        │  Правило C (шаг 3, после B)   │
         │                        │                               │
         │                        │ Отправляет правила на модули  │
         │                        │ через стандартный механизм    │
         │                        │──────────────────────────────►│
         │                        │                               │
         │                        │ Все правила синхронизированы? │
         │                        │◄──────────────────────────────│
         │                        │                               │
         │                        │ → Workflow = Синхронизирован   │
```

### 6.2. Мониторинг: агрегирует статусы правил в статус Workflow

Бэкенд уже получает от модулей информацию о выполнении каждого правила. **Ничего нового модуль не отправляет.**

Бэкенд знает какие правила принадлежат какому Workflow. По состояниям правил он вычисляет состояние Workflow:

| Состояние правил | Состояние Workflow |
|------------------|--------------------|
| Все правила Synchronized, ни одно не сработало | **Idle** (ожидание триггера) |
| Хотя бы одно правило активно (устройство ON по ruleUid) | **Running** |
| Все правила завершили выполнение (все шаги Done) | **Completed** |
| Любое правило в Error | **Error** |
| Не все правила Synchronized | **Synchronizing** |

### 6.3. Конфликт-менеджмент

При создании/редактировании:
- Устройство в обычном правиле → нельзя добавить в Workflow (красный)
- Устройство в другом Workflow → можно, но проверяется приоритет (жёлтый)
- Одинаковый приоритет + общее устройство → блокировка сохранения

## 7. Жизненный цикл Workflow (вид с бэкенда)

```
                    Создание Workflow
                    (бэк создаёт N правил)
                           │
                           ▼
                    ┌─────────────┐
                    │  Disabled    │  правила выключены
                    └──────┬──────┘
                           │  Enable
                           │  (бэк включает все правила цепочки)
                           ▼
                    ┌──────────────┐
                    │ Synchronizing │  бэк ждёт синхронизации всех правил
                    └──────┬───────┘
                           │  Все синхронизированы (или 5мин → Error)
                           ▼
                    ┌─────────────┐
                    │    Idle     │  правила на модулях, ждут условий
                    └──────┬──────┘
                           │  Первое правило сработало
                           ▼
                    ┌─────────────┐
                    │   Running   │  бэк видит что правило цепочки активно
                    └──────┬──────┘
                          ╱ ╲
                    ▼          ▼
             ┌───────────┐  ┌─────────┐
             │ Completed │  │  Error  │
             └─────┬─────┘  └─────────┘
                   │
                   │  Все устройства выключились,
                   │  правила вернулись в ожидание
                   ▼
             ┌───────────┐
             │   Idle    │  готов к следующему запуску
             └───────────┘
```

**Ключевой момент:** бэкенд **не управляет** выполнением. Он только наблюдает. Модули сами выполняют правила автономно — как сейчас.

### Переход Completed → Idle

После завершения всех шагов Workflow остаётся в **Completed** до конца текущего периода активности.

- **Schedule-режим**: Workflow выполнился в 07:00 → Completed. Остаётся Completed до конца дня (00:00) → Idle. На следующий день в 07:00 → Running.
- **Sensor-режим**: цепочка сработала → Completed. Остаётся Completed пока действует Active Hours. Когда Active Hours закончились → Idle. При следующем Active Hours + условие датчика → Running.
- **Если Active Hours не задан**: Completed → Idle при наступлении нового дня (00:00).

## 8. Как триггер Workflow превращается в условие правила

### Schedule-триггер

Триггер «каждый день в 07:00» → первое правило в цепочке получает расписание 07:00. Остальные правила-шаги не имеют собственного расписания — они активируются по предшественнику.

### Sensor-триггер

Триггер «CO₂ < 800 AND T > 25» → первое правило получает эти условия как свои пороги. Остальные правила-шаги получают свои собственные sensor-условия (From/Until) + предшественника.

### Active Hours

Временное окно применяется ко **всем правилам** цепочки.

## 9. Отказоустойчивость

Так как Workflow — это обычные правила, вся существующая отказоустойчивость правил действует автоматически:

| Сценарий | Поведение | Источник |
|----------|-----------|----------|
| Потеря интернета | Правила продолжают работать автономно. Межмодульная координация через локальную сеть. | Существующее поведение правил |
| Потеря локальной сети | Модуль не видит состояние устройства-предшественника. Таймаут 5 мин → Fail-Safe, устройства ВЫКЛ. | **Новое**: таймаут ожидания предшественника |
| Датчик недоступен | Правило переходит в ошибку. Бэк видит → Workflow = Error. | Существующее поведение правил |
| Пропало питание | После загрузки правила восстанавливаются из памяти и продолжают работать. Если условие первого шага всё ещё выполняется — цепочка запустится заново с начала. Состояние «на каком шаге остановились» теряется. | Существующее поведение правил |
| Команда на устройство не принята | Устройство не включается → следующий шаг не видит старт → цепочка не продолжается. | Существующее поведение |

### Дополнение: Fail-Safe для цепочки

Единственное **новое поведение** на прошивке: если правило с предшественником ждёт его старта дольше **5 минут** — оно переходит в Error. Это предотвращает «зависание» цепочки при потере связи между модулями.

## 10. Как бэкенд собирает состояние Workflow

Модуль уже отправляет на сервер состояние каждого устройства, включая какое правило им управляет. **Ничего нового отправлять не нужно.**

Бэкенд получает информацию о правиле, смотрит в свою базу — это правило принадлежит Workflow X, шаг 1. Следующее обновление говорит что правило B активно — бэк знает: это шаг 2 того же Workflow. И так далее.

**Фронтенд** получает от бэка агрегированное состояние: «Workflow Фертигация — Running, шаг 2 из 3 активен».

## 11. Конфликты устройств

### 11.1. Защита при создании (бэкенд)

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Устройство  │     │ Устройство  │     │ Устройство  │
│  в ПРАВИЛЕ  │     │ в другом    │     │  СВОБОДНО   │
│             │     │  WORKFLOW   │     │             │
│  🔴 Красный │     │  🟡 Жёлтый  │     │  ⚪ Доступно │
│  Нельзя     │     │  Можно, но  │     │  Можно      │
│  выбрать    │     │  нужен      │     │  выбрать    │
│             │     │  приоритет  │     │             │
└─────────────┘     └─────────────┘     └─────────────┘
```

При сохранении Workflow бэкенд проверяет:
- Устройство в обычном правиле → **нельзя** добавить в Workflow (красный)
- Устройство в другом Workflow → **можно**, но приоритеты должны быть разные
- Одинаковый приоритет + общее устройство → блокировка сохранения

### 11.2. Как приоритет попадает на модуль

Приоритет — свойство Workflow, а не правила. Но модуль не знает что такое Workflow. Поэтому бэкенд записывает в каждое правило Workflow два поля:
- **UID Workflow** — к какой группе принадлежит правило
- **Приоритет Workflow** — числовой приоритет (меньше = выше)

Обычные правила этих полей не имеют.

### 11.3. Почему конфликт блокирует ВЕСЬ Workflow

Workflow — цепочка: шаг N+1 зависит от шага N. Если один шаг заблокирован, все последующие не запустятся. Поэтому достаточно **не дать первому шагу стартовать** — вся цепочка не запустится.

### 11.4. Что бэкенд вычисляет при создании Workflow

Бэкенд знает ВСЕ Workflow и ВСЕ устройства. При создании/редактировании он вычисляет для каждого Workflow: какие другие Workflow с **более высоким приоритетом** делят с ним хотя бы одно устройство (на любом модуле).

Этот список **блокирующих Workflow UID** бэкенд записывает в правило **первого шага** как новое поле `blockedByWorkflowUids`. У Workflow которые ни с кем не конфликтуют или имеют наивысший приоритет — список пустой.

### 11.5. Как модуль узнаёт что блокирующий Workflow работает

В существующее широковещание состояния устройств добавляется **workflowUid**. Каждый модуль, получая широковещание, видит какой Workflow сейчас активен на любом модуле в сети.

Модуль ведёт список **активных workflowUid** — собирая из двух источников:
- Собственные устройства, активированные правилом с workflowUid
- Широковещание от других модулей

### 11.6. Разрешение конфликтов в runtime: проверка только в первом шаге

Вся проверка — **только при оценке правила первого шага** (stepNumber = 1). Остальные шаги не проверяют приоритеты — они и так зависят от предшественника и не запустятся без него.

```
Оценка правила первого шага (stepNumber = 1):
  │
  ├── blockedByWorkflowUids пустой? → Оценить условие как обычно.
  │
  └── blockedByWorkflowUids не пустой?
        │
        ├── Любой UID из списка есть в «активных workflowUid»?
        │     │
        │     ├── Да → ПРОПУСТИТЬ. Первый шаг не запускается.
        │     │         Цепочка не стартует.
        │     │
        │     └── Нет → Оценить условие как обычно.
```

Модуль не знает какие устройства конфликтуют и на каких модулях. Ему не нужно. Он получил готовый список блокирующих UID от бэкенда и проверяет одно условие: активен ли хоть один из них. Решение принимается **только на модуле первого шага**.

### 11.7. Что нового на прошивке для приоритетов

| Что | Описание |
|-----|----------|
| Новое поле в правиле | `blockedByWorkflowUids` — список UID Workflow, которые блокируют запуск. Заполняется бэкендом только для первого шага. |
| workflowUid в широковещании | В существующее широковещание состояния устройств добавляется workflowUid правила. |
| Список активных workflowUid | Модуль ведёт из собственных устройств + из широковещания. |
| Проверка при оценке | Только для правил первого шага (stepNumber = 1): пересечение blockedByWorkflowUids ∩ активные workflowUid. |

**Итого:**
- Обычные правила — поведение не меняется
- Конфликт «обычное правило vs Workflow» — запрещён на бэкенде при сохранении
- Конфликт «Workflow A vs Workflow B» — проверка только в первом шаге, по списку от бэкенда
- Workflow без общих устройств — работают параллельно без ограничений

## 12. Резюме: что меняется на каждом уровне

### Прошивка (минимальные изменения)

| Изменение | Описание |
|-----------|----------|
| Новые поля в правиле | Предшественник, устройство предшественника, номер шага, UID Workflow, приоритет Workflow, blockedByWorkflowUids (только первый шаг) |
| Логика оценки предшественника | Если предшественник указан → проверить что его устройство включилось перед активацией |
| Таймаут ожидания | 5 минут ожидания старта предшественника → Error |
| workflowUid в широковещании | Добавить workflowUid в широковещание состояния устройств |
| Список активных Workflow | Модуль ведёт из собственных устройств + из широковещания |
| Проверка приоритета | Только первый шаг: если любой UID из blockedByWorkflowUids активен → не запускать |

Всё остальное — без изменений: хранение, синхронизация, оценка условий, репортинг.

### Бэкенд (основная логика)

| Изменение | Описание |
|-----------|----------|
| Сущность Workflow | CRUD Workflow с шагами, конвертация шагов в правила |
| Конвертация Workflow → Rules | При создании/редактировании разбивает Workflow на правила с `dependsOn` |
| Агрегация состояний | По `ruleUid` из `hardware/update` собирает статус Workflow |
| Конфликт-менеджмент | Проверка устройств: Rule ↔ Workflow, Workflow ↔ Workflow |
| API для фронтенда | CRUD Workflow, дашборд, история |

### Фронтенд (визуализация)

| Изменение | Описание |
|-----------|----------|
| UI конфигурации | Wizard создания Workflow с шагами |
| Дашборд | Агрегированное состояние Workflow в реальном времени |
| Device Picker | Цветовая индикация: красный/жёлтый/свободно |

## 13. Ограничения V1

| Ограничение | Комментарий |
|-------------|-------------|
| Зависимости линейные | Шаг N зависит только от шага N-1. Ветвления нет. |
| Один режим на Workflow | Schedule и Sensor нельзя смешивать. |
| Нет Safety Limits | Аварийная остановка по датчику — в будущих версиях. |
| Fail-Safe таймаут фиксирован | 5 минут, не настраивается. |
| Только S3-модули | Sensor Director S3, Multichannel Director S3. |
