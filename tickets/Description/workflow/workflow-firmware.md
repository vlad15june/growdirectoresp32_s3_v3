## 1. Расширение модели Rule

**Файл:** `src/Core/Domain/Data/Entities/Rule.h`

Добавить поля в структуру `Rule`:

| Поле | Тип | Описание |
|------|-----|----------|
| `dependsOnRuleUid` | `String` | UID правила-предшественника. Пустая строка = обычное правило. |
| `dependsOnDeviceUid` | `String` | UID устройства предшественника. Для отслеживания старта. |
| `stepNumber` | `uint8_t` | Номер шага в цепочке. 0 = обычное правило. |
| `complexRuleUid` | `String` | UID ComplexRule. Пустая строка = обычное правило. |
| `complexRulePriority` | `uint8_t` | Приоритет ComplexRule (меньше = выше). 0 = не задан. |
| `blockedByComplexRuleUids` | `String[]` | Список UID блокирующих ComplexRule. Заполняется **только для stepNumber = 1**. |

### Обратная совместимость

- Все новые поля опциональны. Если поле отсутствует в JSON — значение по умолчанию (пустая строка / 0).
- Обычные правила (без ComplexRule) работают как раньше — для них все новые поля пустые.

## 4. Логика оценки предшественника

**Файл:** `src/Core/Domain/UseCases/Rules/EvaluateRulesUseCase.h`

Текущая логика: каждую секунду перебирает все правила → оценивает условие → управляет устройством.

### Изменение в цикле оценки

```
Для каждого правила:
  │
  ├── dependsOnRuleUid пустой?
  │     └── Да → оценить условие как обычно (текущая логика)
  │
  └── dependsOnRuleUid не пустой?
        │
        └── Проверить: устройство dependsOnDeviceUid ВКЛЮЧЕНО?
              │
              ├── Источник 1: собственные устройства модуля
              │   (прямая проверка состояния устройства)
              │
              ├── Источник 2: широковещание от других модулей
              │   (из списка состояний устройств)
              │
              ├── Устройство включено И ruleUid совпадает?
              │     └── Да → оценить собственное условие
              │              (для sensor-режима: проверить порог)
              │              (для schedule-режима: сразу активировать)
              │
              └── Устройство выключено или не найдено?
                    └── Ждать (не активировать)
```

### Как проверить состояние устройства предшественника

**На том же модуле:**
- Модуль уже хранит состояние своих устройств. Прямой доступ к `device.isOn` + `device.ruleUid == dependsOnRuleUid`.

**На другом модуле:**
- Модули уже обмениваются состояниями устройств по UDP broadcast. Данные уже хранятся.
- Найти в полученных данных устройство с `uid == dependsOnDeviceUid`.
- Проверить что оно включено и управляется правилом `dependsOnRuleUid`.

### Важно: проверка ruleUid

Недостаточно проверить что устройство включено. Нужно убедиться что оно включено **именно правилом-предшественником** (`ruleUid` совпадает). Устройство может быть включено вручную или другим правилом — это не считается стартом предшественника.

## 5. Таймаут ожидания предшественника (Fail-Safe)

**Файл:** `src/Core/Domain/UseCases/Rules/EvaluateRulesUseCase.h`

### Новое поведение

Если правило с `dependsOnRuleUid` ожидает старта предшественника дольше **5 минут** — правило переходит в Error.

### Когда запускать таймер

Таймер начинает отсчёт когда:
- Правило первого шага активировалось (запустило цепочку)
- Текущее правило ожидает старт предшественника
- Предшественник НЕ на этом модуле (если на этом — нет смысла, ответ мгновенный)

### Реализация

- Добавить поле `predecessorWaitStartMs` в runtime-состояние правила (не в хранимую модель)
- При первой оценке, где правило ожидает предшественника → записать `millis()`
- Каждую секунду проверять: `millis() - predecessorWaitStartMs > 300000` (5 мин)
- При превышении → правило в Error, устройство ВЫКЛ

### Сброс таймера

- Если предшественник стартовал — таймер сбрасывается
- Если цепочка завершилась и ComplexRule перешёл в Idle — таймер сбрасывается

## 6. Расширение широковещания — complexRuleUid

**Файлы:** `src/Application/DTOs/UpdateDto.h`, `src/Application/DTOs/DeviceDto.h`

### Текущее широковещание

Модули по UDP отправляют состояние своих устройств другим модулям в локальной сети. Каждое устройство уже содержит `ruleUid`.

### Что добавить

В структуру данных устройства в широковещании добавить поле `complexRuleUid`:

- Если устройство управляется правилом с заполненным `complexRuleUid` → передать этот `complexRuleUid`
- Если устройство управляется обычным правилом или не управляется → пустая строка

### Обратная совместимость

Модули со старой прошивкой не увидят новое поле — это нормально. Они не участвуют в ComplexRule (V1 = только S3-модули).

## 7. Список активных complexRuleUid

**Новый компонент** в runtime-состоянии модуля.

### Назначение

Модуль должен знать какие ComplexRule сейчас активны в сети — чтобы проверять `blockedByComplexRuleUids` для первого шага.

### Источники данных

1. **Собственные устройства:** если устройство управляется правилом с `complexRuleUid` ≠ пустая строка → добавить в список
2. **Широковещание от других модулей:** если получено устройство с `complexRuleUid` ≠ пустая строка → добавить в список

### Хранение

- Простой `Set<String>` / массив уникальных строк
- Обновляется при каждом получении широковещания и при каждой оценке собственных правил
- Если устройство выключилось и ни одно другое устройство не работает с тем же `complexRuleUid` → удалить из списка

### Время жизни записи

- Активный = хотя бы одно устройство с этим `complexRuleUid` включено (локально или по broadcast)
- Если все устройства с этим `complexRuleUid` выключены → убрать из списка

## 8. Проверка blockedByComplexRuleUids

**Файл:** `src/Core/Domain/UseCases/Rules/EvaluateRulesUseCase.h`

### Где проверять

Только при оценке правила с `stepNumber == 1` и непустым `blockedByComplexRuleUids`.

### Алгоритм

```
Оценка правила:
  │
  ├── stepNumber != 1 или blockedByComplexRuleUids пустой?
  │     └── пропустить проверку, перейти к обычной оценке
  │
  └── stepNumber == 1 и blockedByComplexRuleUids не пустой?
        │
        └── Пересечение blockedByComplexRuleUids ∩ activeComplexRuleUids
              │
              ├── Пересечение не пустое → ПРОПУСТИТЬ правило,
              │     цепочка не стартует
              │
              └── Пересечение пустое → оценить условие как обычно
```

### Порядок проверок в оценке правила

1. Проверка `blockedByComplexRuleUids` (если stepNumber == 1)
2. Проверка предшественника (если `dependsOnRuleUid` не пустой)
3. Оценка собственного условия (расписание / датчик / цикл)

## 9. Обновление DeviceDto для бэкенда

**Файл:** `src/Application/DTOs/DeviceDto.h`

В `DeviceDto`, который отправляется на бэкенд через `POST /api/v1/Hardware/update`, уже есть `ruleUid`. Бэкенд по `ruleUid` определит принадлежность к ComplexRule.

### Нужно ли добавлять complexRuleUid в DeviceDto для бэкенда?

**Нет.** Бэкенд и так знает какое правило к какому ComplexRule относится. `ruleUid` достаточно. `complexRuleUid` нужен только в локальном широковещании между модулями.
