# GDV1-3755: Report the rule condition that actually fired in hardware/update

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3755

---

## Ticket Description

### Problem Statement

A multi-condition rule over several different sensors turns the device on by one condition, but the
app shows a different one — always the first condition of the rule. S3 never selects the condition
that fired: the sensor descriptor sent in `hardware/update` (`sensorUid`, `sensorValue`,
`sensorValueLow`, `sensorValueHigh`) is filled from rule-level fields before the conditions are even
evaluated, and is never refined afterwards. Because the backend mirrors `conditions[0]` into the
rule-level `sensorUid`/`valueLow`/`valueHigh` (`RuleProfile.cs`), the descriptor is identical to the
first condition regardless of which one triggered. The backend-firmware contract already requires
the firing condition (`docs/contracts/backend-firmware/02-hardware-update.md:86`, added for the S2
fix GDV1-3463) and the app already resolves the shown condition by `activeRuleSensorUid`, so this is
a firmware-only gap.

### Solution

Select the condition responsible for the rule being on and build the descriptor from it:
- `combineConditionsDnf` reports the index of the condition that holds the rule:
  - **first `true` by order** for a legacy OR set,
  - **index 0** for a legacy AND set (all conditions true — same condition as before the fix),
  - **start index of the first satisfied AND group** for a DNF set (`a AND b OR c`), matching
    `firstFiredGroupStartIndex` from the S2 fix,
  - **`-1`** when nothing fired.
- Both condition evaluators propagate the index: `evaluateSensorRule` (sensor rules) and
  `evaluateConditionSet` (step rules).
- `evaluateRule` (SENSOR) and `evaluateStepRule` (STEP) write the descriptor from that condition;
  the rule-level values remain the fallback for rules that carry no `conditions`.
- Thresholds follow the rule type, as in S2: sensor conditions give `valueLow`/`valueHigh`, step
  conditions give `sensorValueLow = sensorValueHigh = valueTarget` (`StepHwRuleDto` carries no
  low/high, which is why step rules currently report zeros).
- **Trigger stickiness** (variant B, second iteration of the S2 fix `ac0a454`): while the rule is
  already committed on, the condition whose sensor is the previous trigger keeps the descriptor as
  long as it is still in the fired set; only when it releases does the descriptor hand off to the
  first fired condition.

### Technical Approach

Leverage the existing DNF combining and rule-state maps to:
1. Add an optional `int* firedIndex` out-parameter to `combineConditionsDnf` and track the start
   index of the group being evaluated.
2. Thread the index out of `evaluateSensorRule` / `evaluateConditionSet` (optional out-parameter,
   `-1` when the rule is not firing).
3. Apply trigger stickiness in the sensor branch only, using
   `_ruleActiveStates[rule.uid].sensorUid` as the previous trigger — no new state fields.
4. Write the descriptor from the selected condition in the SENSOR branch of `evaluateRule` and in
   the start branch of `evaluateStepRule`.
5. Carry the previous fired descriptor over while the rule stays committed on but no condition
   currently fires, so the descriptor does not fall back to the rule level during the `delayOff`
   tail.
6. Log the selected index, the sticky decision and the hand-off so the choice is reconstructable
   from logs.

### Related Tickets

- **GDV1-3463**: same defect fixed in the previous firmware generation (`growdirectoresp32_v3`,
  `ruleService.h`, commits `34c6169` + `ac0a454`) — semantics ported, not code.

## Development Plan

### **Overview**

The rule engine must answer "which condition is holding this rule on" and put that condition's
sensor and thresholds into the device descriptor that is published in `hardware/update`. The
information is already available inside the condition loop and is thrown away when `condFired[]`
is folded into one `bool`. The change keeps the folding semantics byte-for-byte identical and only
adds the index of the responsible condition, so no rule ever changes its on/off behaviour.

---

### **Instructions:**

1. **Report the fired condition index from the fold**
   - Add an optional out-parameter to `combineConditionsDnf`.
   - Legacy OR: first `true`. Legacy AND: index 0. DNF: start index of the first satisfied group.
   - `-1` when the fold result is `false`.

2. **Propagate the index through both condition evaluators**
   - `evaluateSensorRule(rule, committedOn, int* firedIndex)`.
   - `evaluateConditionSet(rule, int* firedIndex)`.
   - Reset the index to `-1` when the rule is not firing.

3. **Apply trigger stickiness in the sensor branch**
   - Previous trigger = `_ruleActiveStates[rule.uid].sensorUid`.
   - Only when the rule is already committed on; keep the previous trigger if its condition is still
     fired, otherwise hand off to the first fired condition.

4. **Write the descriptor from the selected condition**
   - SENSOR: in `evaluateRule`, before `applyDelay`, so `ruleSensorValueStart` records the fired
     condition's reading.
   - STEP: in `evaluateStepRule`, in the start branch, after the rule-level fill.
   - Carry over the previous fired descriptor while the rule is committed on and nothing fires.

5. **Cover the change with native tests**
   - New `test/test_rule_fired_condition.cpp`, registered in `test/test_main.cpp`.

### **Implementation Details:**

#### **Selecting the responsible condition:**

1. Conditions are evaluated exactly as before → `condFired[]`.
2. `combineConditionsDnf` folds `condFired[]` and reports the index:
   - no `joinOp` anywhere and `conditionOr` → first `true`;
   - no `joinOp` anywhere and AND → `0` (all conditions are true, so the first one by order is
     also the first fired — identical to the pre-fix `conditions[0]`);
   - `joinOp` present → groups are split on `OR`; the first group that evaluates to `true` reports
     its start index.
3. Fold result `false` → index `-1` → the rule-level fallback stays in place.
4. SENSOR only: if the rule is already committed on and the previous trigger's condition is still
   fired, its index wins (stickiness); otherwise the first fired condition takes over (hand-off).
5. The descriptor is written from that condition → `executeDeviceAction` copies it to the device →
   `DeviceService` / `ArduinoJsonConverter` publish it in `hardware/update`.

#### **Why stickiness is needed (variant B):**

The descriptor is written only when the device state changes (`executeRuleActions` returns early
otherwise). At turn-on the rule is not committed on, so `HOLD` verdicts map to `false` and
"first fired by order" is already correct. The single transition that writes the descriptor while
the rule *is* committed on is `DELAY_OFF -> REQUEST_ON`: there a condition merely sitting in its
hysteresis dead zone counts as fired and would steal the descriptor from the condition that
actually triggered. Stickiness closes exactly that hole and keeps one semantics across both
firmware generations. Step rules have no hysteresis at all (`evaluateConditionSet` compares raw
values without `committedOn`), so stickiness is deliberately not applied there.

#### **Known limitations (unchanged by this fix):**

- Two conditions on the same sensor are indistinguishable — the condition has no uid of its own;
  a per-condition uid from the backend is required (out of scope in S2 as well).
- The descriptor is frozen for the whole ON session, because it is only written on a state change.
  If the holding condition changes mid-session, the reported one stays as it was at turn-on.

#### **Logging & Observability:**

`EVALUATE_RULES: SENSOR_COND` line per condition (sensor, direction, value, band, `on`) plus a
summary line with `mode`/`ops`/`nConds`/`targetOn`; `evaluateConditionSet` logs the step summary
`EVALUATE_RULES: STEP_COND` with the same shape; `computeMean` logs `AVG_MEAN`. Nothing logged
which condition was chosen for the descriptor, because nothing chose one.

**How to debug from logs** —
(a) `python3 test_scripts/elk_download_logs_cli.py --uid <MODULE_UID> --from <ISO> --to <ISO>`, then
grep `SENSOR_COND`, `STEP_COND`, `FIRED_COND`, `FIRED_COND_STICKY`, `FIRED_COND_HANDOFF` and the
`hardware/update` payload for the device.
(b) Real line shape from the ticket's module, for the published side:
`"ruleType":"step","state":"stepOn","sensorUid":"84:F7:03:FE:88:40.03.01","sensorValueLow":0,"sensorValueHigh":0,"sensorValue":7656`
— after the fix the same rule must publish the sensor of the group that holds it, with
`sensorValueLow == sensorValueHigh == valueTarget` of that condition.
(c) Happy-path trace for a step rule with conditions `null/or/and/or`:
1. grep `STEP_COND uid=<rule>` → `firing=1 fired=1` proves the second group was selected;
2. grep `FIRED_COND uid=<rule>` → `index=1 sensor=<c1 sensor> low=<target> high=<target>`;
3. grep the module's `hardware/update` → `sensorUid` equals the sensor from step 2.
(d) Failure catalog:

| Symptom in logs | Cause | Fix |
|---|---|---|
| `fired=-1` while the device turned on | fold said `true` but the index was reset — index/fold disagreement | check the `joinOp` sequence in `ops=`, the fold and the index must be derived in the same pass |
| `FIRED_COND` missing after `fired>=0` | selected condition has an empty `sensorUids` | backend sent a condition without a sensor; see the `SENSOR_COND ... reason=no_sensor_uid` line |
| `sensorValueLow=0 sensorValueHigh=0` on a step rule | condition has no `valueTarget` and no low/high | check the rule payload in `RuleCommandNotification` |
| `FIRED_COND_STICKY` repeating with `instead=` pointing at a condition in its dead zone | expected: the dead-zone condition is not allowed to steal the descriptor | none |
| `FIRED_COND_HANDOFF` right after turn-on | previous trigger released within the same ON session | expected on `DELAY_OFF -> REQUEST_ON` |

**Logging correctness checklist:**
- [x] Flow entry is greppable and returns a record (`SENSOR_COND` / `STEP_COND` per condition + summary)

### Implementation Summary:

One production file changed: `src/Core/Domain/UseCases/Rules/EvaluateRulesUseCase.h`. The fold
`combineConditionsDnf` gained an optional out-parameter with the index of the condition responsible
for the rule being on; the boolean result is unchanged in every branch, so no rule changes its
on/off behaviour. Both condition evaluators pass the index out, and the SENSOR and STEP branches
build `sensorUid` / `sensorValue` / `sensorValueLow` / `sensorValueHigh` from that condition, with
the rule-level values kept as the fallback. Trigger stickiness (ported from the S2 fix GDV1-3463)
applies only to sensor rules and only while the rule is already committed on, which is exactly the
`DELAY_OFF -> REQUEST_ON` transition where a dead-zone condition could otherwise steal the
descriptor.

The new native suite has 11 tests. Against the pre-fix header 7 of them fail (including the
ticket's own step case: `sensorUid` `s1` instead of `s2`, `sensorValue` 7656 instead of 20,
thresholds 0/0 instead of 28/28) and the 3 regression tests pass; after the fix all 11 pass. The
whole rule-engine suite of the repository (19 rule-related translation units, 191 tests) is green.
