# GDV1-3421: [S3] Incorrect led indicator on working module — implement BlinkingStart / BlinkingStop

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3421

---

## Ticket Description

### Problem Statement

The simple module commands `BlinkingStart` and `BlinkingStop` are scaffolded in the new S3 firmware but not functional. Backend can dispatch them via MQTT, the routing layer reaches the use case, but the actual LED behavior is missing — so identifying a physical module from the app does nothing.

Concretely:

1. **`ModuleCommandExecutionUseCase::handleBlinkingStart()` / `handleBlinkingStop()`** are empty stubs with `// TODO: Implement blinking start logic` — they call a `getModuleByUid()` placeholder and return `true` without touching any LED.
2. **`LedUseCases::loop()`** decides LED state purely from `settings->getIfConfigured()` (USER_CAN_CONFIGURE / USER_CAN_RE_CONFIGURE / CONFIGURED_DONE). There is no concept of an "identification blinking" mode that would override the normal pattern.
3. **`ILedUseCases`** has no API for entering or leaving the identification mode.

The full behavior already exists in the v1 firmware (`isBlinking` global flag, `ledBlinks()` in `Led_blink_all.h`, 500 ms red blink toggled by MQTT — see `doc/simple-module-commands.md` in the v3 repo). It needs to be ported to the new clean-architecture layer.

### Solution

Implement an in-memory "identification blinking" mode that is triggered by MQTT and rendered by the existing LED loop:

- Add **`setBlinking(bool)`** and **`isBlinking()`** to `ILedUseCases` so the use case can be toggled from outside
- In `LedUseCases::loop()` — when `isBlinking() == true`, override the normal config-based state machine and blink **all red LEDs at 500 ms / 500 ms**
- Implement `handleBlinkingStart()` / `handleBlinkingStop()` in `ModuleCommandExecutionUseCase` — both inject `ILedUseCases*` and call `setBlinking(true/false)`
- Wire `&ledUseCases` into `ModuleCommandExecutionUseCase` in `globals.h`
- The flag is **in-memory only** — on reboot it resets to `false` (matches v1 behavior, no EEPROM write required)

### Technical Approach

Leverage the existing `ILedAdapter` (already exposes `setAllRedLedOn` / `setAllRedLedOff`) and the existing `CommandService → moduleCommandUseCase->execute()` simple-command path:

1. Extend `ILedUseCases` with `setBlinking(bool)` and `isBlinking()`
2. Add `_blinking` field + reuse the existing `lastBlinkTime` / `ledState` machinery in `LedUseCases::loop()` for the blink cadence
3. In `LedUseCases::loop()` — early-return branch when `_blinking == true`: turn all green off, toggle red according to a 500/500 ms timer
4. Inject `ILedUseCases*` into `ModuleCommandExecutionUseCase`; replace stub bodies with `ledUseCases->setBlinking(true/false)`
5. Wire `&ledUseCases` as the last constructor arg in `globals.h`
6. Unit tests via `MockLedUseCases` (for the use case) and a direct `LedUseCases` + `MockLedAdapter` test for the loop branch

### **Implementation Details:**

#### **End-to-end flow — BlinkingStart command:**
1. Backend publishes MQTT to `GrowDirectorMqttTopic/{MAC}` with `{"type":"ModuleCommandNotification","command":"BlinkingStart"}`
2. `MqttManager` → `CommandTopicHandler` → `CommandService::process()`
3. `command.isModuleCommand() == true` → `processModuleCommand()`
4. `isComplexModuleCommand("BlinkingStart") == false` → `moduleCommandUseCase->execute("BlinkingStart", options, uid, createdAt)`
5. `getModuleCommandEnum("BlinkingStart") == BLINKING_START` → `handleBlinkingStart("", options)`
6. `ledUseCases->setBlinking(true)` — sets `_blinking = true` in memory
7. On the next `LedUseCases::loop()` tick, the blinking branch runs and toggles red LEDs at 500 ms intervals

#### **End-to-end flow — BlinkingStop command:**
1. Same path as above with `command == "BlinkingStop"`
2. `handleBlinkingStop()` → `ledUseCases->setBlinking(false)`
3. Next `loop()` tick falls through to the normal `switch (configStatus)` and resumes the configured pattern

#### **Reset on reboot:**
- `_blinking` is a non-persistent member of `LedUseCases`, default `false`
- After reboot the field is re-initialized to `false` — matches v1 behavior, no EEPROM write required

#### **LED hardware notes:**
- `setAllRedLedOn()` / `setAllRedLedOff()` already iterate over all `ledsCount` red LEDs in the adapter — the blink branch does not need to loop over indices itself
- For sensor modules with one LED, this lights a single red LED; for device / hydro / analog input modules with multiple channels, all red LEDs blink in sync
