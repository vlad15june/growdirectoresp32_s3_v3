# GDV1-3182: Automatic Module Reset After Prolonged Offline State

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3182

---

## Ticket Description

### Problem Statement

Modules can become stuck in a non-functional state when they lose all network connectivity for extended periods. Without automatic recovery, these modules remain offline indefinitely, requiring manual intervention to restore functionality. Different module types have different criticality levels and require different timeout thresholds for automatic recovery.

### Solution

Implement automatic monitoring and recovery mechanism that:
- Continuously monitors module's connectivity status (WiFi, MQTT, API)
- Tracks duration of complete offline state
- Detects module type (sensor director vs other modules)
- Automatically triggers system reboot after appropriate timeout:
  - **15 minutes** for sensor director modules (critical sensor data)
  - **4 hours** for other modules (less time-sensitive)
- Sets `noScanSensors` flag to skip sensor scanning after reboot for faster recovery
- Uses `BOOT_TYPE_TECHNICAL` to indicate automatic recovery reboot
- Triggers restart via `CONFIGURED_NEED_RESTART` mode for graceful shutdown
- Reboots module to re-establish network connections
- Preserves all configuration and data during reboot
- Enables automatic recovery from prolonged connectivity failures

### Technical Approach

Leverage existing diagnostic monitoring infrastructure in `DiagnosticService` to:
1. Detect "all offline" state (no WiFi, MQTT, or API connectivity)
2. Track continuous offline duration using `millis()` timestamp
3. Determine module type from `IModuleConfig`
4. Select appropriate threshold (15 minutes for sensor directors, 4 hours for others)
5. Compare against selected threshold
6. Set `noScanSensors` flag via `ISettings` to skip sensor scan after reboot
7. Set boot type to `BOOT_TYPE_TECHNICAL` for automatic recovery indication
8. Trigger restart via `setRequestedModuleMode(CONFIGURED_NEED_RESTART)`
9. Main loop processes restart request and reboots module gracefully
10. Module re-initializes and re-establishes all connections after reboot (without sensor scan)

### **Implementation Details:**

#### **Offline Detection Logic:**
```cpp
// Module is considered "fully offline" when:
bool isFullyOffline = !wifiConnected || (!mqttConnected && apiDisconnected);

// Where:
// - wifiConnected: WiFi connection status
// - mqttConnected: MQTT broker connection
// - apiDisconnected: API is offline (countOffline > maxCountOffline)
```

#### **Module Type Detection and Threshold Selection:**
```cpp
// Determine appropriate timeout based on module type
const char* moduleType = _moduleConfig->getModuleType(); // e.g., "sensor_director" or "grow_director"
unsigned long threshold;

if (strcmp(moduleType, "sensor_director") == 0) {
    threshold = OFFLINE_RESET_THRESHOLD_SENSOR_MS; // 15 minutes
} else {
    threshold = OFFLINE_RESET_THRESHOLD_DEVICE_MS;  // 4 hours
}
```

#### **Reboot Flow:**
1. Detect module goes fully offline → Start timer
2. Check timer continuously in diagnostic loop
3. Determine module type and select appropriate threshold (15 min or 4 hours)
4. If offline for >= threshold duration:
   - Log reboot reason at ERROR/WARNING level (include module type, threshold, and offline duration)
   - Get settings: `ISettings *settings = _moduleConfig->getSettings()`
   - Set noScanSensors flag: `settings->setNoScanSensors(1)` to skip sensor scan after reboot
   - Set boot type: `settings->setBootType(BOOT_TYPE_TECHNICAL)` for technical boot
   - Trigger restart: `_moduleConfig->setRequestedModuleMode(CONFIGURED_NEED_RESTART)`
   - Reset timer to avoid repeated restart attempts
   - Module will restart via main loop processing CONFIGURED_NEED_RESTART
5. If connectivity restored before threshold → Reset timer and continue normal operation

### **Safety Considerations:**

- **Prevent Unnecessary Reboots**: Only reboot after continuous offline period (not cumulative failures)
- **Skip Sensor Scan**: Set `noScanSensors` flag to prevent sensor scanning after reboot, allowing faster recovery
- **Technical Boot**: Use `BOOT_TYPE_TECHNICAL` to indicate automatic recovery reboot
- **Proper Restart Mechanism**: Use `CONFIGURED_NEED_RESTART` mode to let main loop handle restart gracefully
- **Logging**: Log reboot event with timestamp, module type, threshold used, offline duration, and reason for audit trail
- **Module-Specific Thresholds**: 
  - Sensor directors: 15 minutes (faster recovery for critical sensors)
  - Other modules: 4 hours (more tolerance for less critical modules)
- **State Tracking**: Only reboot if continuously offline for full duration (not cumulative)
- **Graceful Degradation**: Module should attempt normal recovery before triggering reboot
- **Type Safety**: Verify module type detection works correctly for all module variants
- **Data Preservation**: Reboot preserves all configuration, credentials, sensors, and rules - only restarts the system
