# GDV1-3797: [S3][OTA] Preserve bootType across the CONFIGURED_NEED_RESTART reboot

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3797

---

## Ticket Description

### Problem Statement

After a successful OTA, S3 reports the reboot as an ordinary user reboot instead of a firmware
update. `handleUpdateFirmware()` correctly writes `settings->setBootType(BOOT_TYPE_FIRMWARE_UPDATE)`
(111) right after the image is flashed (`ModuleCommandExecutionUseCase.h:363`), then requests a
restart via `CONFIGURED_NEED_RESTART`. About a second later, the reboot handler for that mode —
`OnChangeModuleModeUseCase.h:48-61` — overwrites the flag with `BOOT_TYPE_USER` (86), because its
guard whitelists only `BOOT_TYPE_TECHNICAL` before deciding to stamp `USER`. The correct value never
survives to the next boot.

Two consequences, both observed on a live update of `9C:13:9E:99:47:38` (2.18.1 -> 2.18.2,
2026-08-04):
1. `POST /api/v1/HardWare/structure` reports `node.bootType = "reboot-user"` instead of
   `"reboot-firmware-update"` (`ModuleSetupService.h:1054-1058` reads the byte back and maps it via
   `getBootTypeName()`).
2. The `BOOT in OTA: reset_reason=... updateStatus=... bootType=... fw=...` record is never written
   to the OTA log, because that writer is gated on the same flag reading exactly
   `BOOT_TYPE_FIRMWARE_UPDATE` (`ModuleSetupService.h:1591-1605`).

The same mechanism silently affects sensor-configuration reboots too: `SensorCommandUseCase.h:93`
sets `BOOT_TYPE_SENSOR_CHNG` (122) and requests the same `CONFIGURED_NEED_RESTART` transition, so it
is overwritten to `USER` by the identical guard — `reboot-sensor-type-chng` is never reported either,
even though `getBootTypeName()` already has a string for it.

Impact is diagnostic only (confirmed in the ticket: no product behaviour breaks, the module updates
and runs correctly) — but the reboot reason is lost for good in the module's stored history, and the
OTA log loses its strongest per-session evidence that the reboot into the new image actually
happened.

### Solution

Extend the existing boot-type guard in `OnChangeModuleModeUseCase.h`'s `CONFIGURED_NEED_RESTART`
branch so that it preserves `BOOT_TYPE_FIRMWARE_UPDATE` and `BOOT_TYPE_SENSOR_CHNG`, the same way it
already preserves `BOOT_TYPE_TECHNICAL`, instead of stamping `BOOT_TYPE_USER` over anything that
isn't `TECHNICAL`.

### Technical Approach

1. Read the boot type once into a local variable at the top of the `CONFIGURED_NEED_RESTART` case.
2. Overwrite to `BOOT_TYPE_USER` only when it is none of `BOOT_TYPE_TECHNICAL`,
   `BOOT_TYPE_FIRMWARE_UPDATE`, `BOOT_TYPE_SENSOR_CHNG`; otherwise keep it and log which value was
   kept (mirrors the existing `else` branch that logs "Keeping boot type TECHNICAL").
3. Leave the hard-reset/soft-reset dispatch in `restart()` (`OnChangeModuleModeUseCase.h:83-97`)
   untouched — it independently reads the *final* stored `bootType` and only hard-resets on
   `BOOT_TYPE_TECHNICAL`. Since today `FIRMWARE_UPDATE`/`SENSOR_CHNG` already end up mapped to
   `USER` before `restart()` runs, and after the fix they stay `FIRMWARE_UPDATE`/`SENSOR_CHNG`
   (neither equal to `TECHNICAL`), the dispatch still takes the soft-reset branch exactly as it does
   today — no change in reset hardware behaviour for either path.
4. `getBootTypeName()` (`BootTypeEnum.h:13-24`) and the "BOOT in OTA" gate
   (`ModuleSetupService.h:1594`) already handle the preserved values correctly; no changes needed
   there.

### Related Tickets

- None directly related. Two adjacent findings from the same Jira ticket are explicitly **out of
  scope** here and are not touched by this fix (fix separately if needed):
  - `sendFirmwareVersion()` is implemented but never called on S3 (`RestApiService.h:301-345`), so

  - The `UPDATE_FIRMWARE` debug feature is `MqttLoggerMode::SerialOnly` (`DebugSystem.h:83`), so
    `FIRMWARE_UPD:` lines never reach ELK.

## Development Plan

### **Overview**

One guard, in one method, in one file, gets two more values added to its whitelist. This is the
same mechanism the code already uses for `BOOT_TYPE_TECHNICAL` — no new state, no new write points,
no change to the restart dispatch logic. Two native tests are added alongside the existing suite for
this use case, following the exact pattern of the existing `test_loop_technical_need_restart_calls_hard_reset`
test.

**Rejected alternative — write the flag before the download starts (S2's pattern,
`UpdateService.h:39-43` + `GrowDirectorEsp32_V3.ino:307-319`).** S2 writes `BOOT_TYPE_FIRMWARE_UPDATE`
immediately when the update task starts, and its restart path *reads* boot type (never blindly
overwrites it to `USER`), so the flag also survives an OTA that crashes mid-download. That is a
structurally different reboot model from S3's: S3 has a single generic `CONFIGURED_NEED_RESTART`
handler shared by six different mode transitions, which decides the final boot type with a
whitelist-then-overwrite guard; porting S2's read-only restart path would mean redesigning that
shared handler, not a one-line fix. It also protects a failure mode that isn't what this ticket
reports or reproduces: this bug is about a **successful** OTA whose correct flag gets clobbered a
second later, not about surviving a mid-OTA crash. Per `conventions/new-fits-existing.md` and
`bug-fix-flow.md` (no "заодно" scope creep), the crash-survival property is a legitimate idea for a
**separate** ticket if ever needed, not something to fold into this fix. The chosen fix (extend the
whitelist) is the smaller change that fits the pattern the code already has.

### **Implementation Details:**

#### **OTA reboot flow, after the fix:**
1. `handleUpdateFirmware()` flashes the image, then
   `settings->setBootType(BOOT_TYPE_FIRMWARE_UPDATE)` + `setRequestedModuleMode(CONFIGURED_NEED_RESTART)`
   (`ModuleCommandExecutionUseCase.h:362-364`, unchanged).
2. `OnChangeModuleModeUseCase::loop()` sees the mode transition, enters `CONFIGURED_NEED_RESTART`:
   `currentBootType == BOOT_TYPE_FIRMWARE_UPDATE` → **no overwrite**, log "Keeping boot type 111"
   (or similar) → `restart()` → `bootType != BOOT_TYPE_TECHNICAL` → soft reset via
   `_arduinoAdapter.restart()` (same as today).
3. On the next boot, before `initializeModuleConfiguration()`:
   `bootSettings->getBootType() == BOOT_TYPE_FIRMWARE_UPDATE` is now **true** →
   `ModuleSetupService.h:1591-1605` writes `BOOT in OTA: reset_reason=... updateStatus=...
   bootType=111 fw=<new version>` to the OTA log.
4. Later in the same boot, `createBaseNodeStructure()` reads the same still-unchanged flag,
   `node.bootType = getBootTypeName(BOOT_TYPE_FIRMWARE_UPDATE) = "reboot-firmware-update"`, then
   resets it to `BOOT_TYPE_POWER_ON` for the next cycle (`ModuleSetupService.h:1054-1058`,
   unchanged).

#### **Sensor-change reboot flow — same shape, `BOOT_TYPE_SENSOR_CHNG` (122) →
`"reboot-sensor-type-chng"`**, previously silently downgraded to `"reboot-user"` by the same bug;
fixed by the same whitelist entry (not a separate code change).

#### **Untouched paths (regression guard):**
- `USER_CAN_CONFIGURE` / `USER_CAN_RE_CONFIGURE` / `AP_TEST_MODE` / `CONFIGURED_DONE` (lines 63-77)
  unconditionally set `BOOT_TYPE_USER` — different `case` block, not touched by this fix.
- Diagnostic-triggered technical reboot (`PreventiveRestartUseCase.h:120`,
  `DiagnosticService.h:334-335`, `RemoteModuleCommandReceiver.h:73`) already sets
  `BOOT_TYPE_TECHNICAL` and is already whitelisted — behaviour unchanged.
