# GDV1-3793: Sensor rule with OR never switches the device off — a condition in its hysteresis dead zone keeps the rule ON

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3793

---

## Ticket Description

### Problem Statement

A sensor rule whose conditions are joined with OR never switches the device off if one of the
conditions sits inside its hysteresis dead zone. `evaluateSensorHysteresis` returns `HOLD` for a
value between `valueLow` and `valueHigh` — "no opinion" — and `evaluateSensorRule` turns that `HOLD`
into `condOn = committedOn`, the state of the **whole rule**
(`EvaluateRulesUseCase.h:1142-1145`). While the rule is on, every dead-zone condition therefore
reports `true` although it never fired, and `combineConditionsDnf` ORs that `true` in. The condition
that really triggered can release; the device stays on forever. Reproduced on Develop
(module `9C:13:9E:99:47:38`, fw 2.18.1): a wind-direction `BETWEEN` condition ORed with a
soil-moisture `Lower 10/60` condition reading a steady 32.7 % — the control rule with the same
`BETWEEN` condition and no OR partner switched off at 11:22:58, the OR rule never switched off at
all.

### Solution

Give `HOLD` its literal meaning: "this condition has no new opinion, keep whatever it said last
time" — instead of "the rule is on, so I am on". Hysteresis memory becomes **per condition** rather
than rule-level:

- new per-rule vector `_conditionHoldStates[rule.uid]`, one `bool` per condition, holding that
  condition's own previous output;
- it is passed to `evaluateSensorHysteresis` as `previouslyOn`, and it is what `HOLD` resolves to,
  so a condition contributes `true` only if it has fired (`TURN_ON`) or is still holding after its
  own trigger;
- it is reset whenever the rule's own state is not on or arming
  (`ON` / `REQUEST_ON` / `DELAY_ON` / `DELAY_OFF`), so no condition can carry a stale `true` into a
  new ON session — after a reboot, a rule edit, a mode switch or an off cycle every condition starts
  from "not holding";
- it is erased together with the other per-rule maps when the rule is deleted, switched off,
  deactivated, protectively shut down or its sensor becomes unreachable.

`combineConditionsDnf` is not touched: the fold stays exactly as it is, only its inputs become
correct.

### Technical Approach

1. Add `_conditionHoldStates` next to the other rule-state maps of `EvaluateRulesUseCase`.
2. Add `conditionHoldStates(rule)` — returns the vector for the rule, sized to the current condition
   list and reset when the rule is not in an ON session (`isRuleHoldSessionActive`).
3. In `evaluateSensorRule`, iterate conditions by index, feed each condition its own
   `condPreviouslyOn`, resolve `HOLD` to it, and store the resulting `condOn` back.
4. Log `prevOn=` on the per-condition `SENSOR_COND` line so the hold decision is visible in the
   serial log.
5. Erase the map alongside `_ruleActiveStates` in every rule-teardown path.

### Related Tickets

- **GDV1-3755**: reports the condition that actually fired in `hardware/update` (open MR #10). Same

  a condition may hold the rule. Its trigger stickiness stays meaningful after this fix (a condition

## Development Plan

### **Overview**

The rule engine has one hysteresis state per rule but needs one per condition. As long as the
deadband decision of a condition is resolved from the rule's committed state, a multi-condition rule
cannot distinguish "this condition is holding the rule" from "the rule happens to be on". Giving
each condition its own one-bit memory makes the deadband a property of the condition, which is what
`evaluateSensorHysteresis` already assumes with its `previouslyOn` argument, and leaves the fold
untouched.

### **Implementation Details:**

#### **Why per-condition memory is the fix (and why nothing smaller works):**

`evaluateSensorHysteresis` returns `HOLD` in three different situations: value in the ON region while
already on, value in the OFF region while already off, and value in the dead zone. All three mean
"no change", which is only meaningful against the state of the thing being switched. For a rule with
one condition, the rule's committed state *is* that state, which is why `condOn = committedOn`
looked right. For several conditions it is not: the OR fold is asked whether *this* condition holds
the rule, and it is answered with whether *the rule* is on — a tautology that can never become
`false` while any other condition keeps the rule on.

Alternatives that were considered and rejected:

- **`HOLD` -> `false` in the fold.** Kills the deadband: a single-condition rule would switch off as
  soon as the value entered the band, then chatter.
- **`HOLD` -> identity element of the fold (`false` for OR, `true` for AND).** For AND it lets a
  condition that has never been satisfied help turn the rule *on*, which is worse than the bug.
- **Require at least one condition to be "positively satisfied at level".** A single condition
  sitting in its dead zone is not positively satisfied, so the deadband dies again.
- **Reuse the fired-condition index of GDV1-3755.** That index says which condition is credited with
  the rule being on; it is derived *from* `condFired`, so it cannot repair `condFired`.

A one-bit memory per condition is the smallest state that makes `previouslyOn` mean what the
function's parameter name says. It is also idempotent: re-evaluating a rule twice in the same tick
with the same readings yields the same verdicts (`TURN_ON` -> `HOLD` -> same `condOn`).

#### **Condition evaluation flow (after the fix):**

1. `evaluateRule` (SENSOR) derives `committedOn` from `_ruleActiveStates[uid].state` as before.
2. `evaluateSensorRule` takes `condHeld` for the rule; if the rule is not in an ON session the
   vector is reset to all `false`.
3. Per condition: `verdict = evaluateSensorHysteresis(dir, value, low, high, condHeld[i])`.
   `TURN_ON` -> `true`; `TURN_OFF` / `INERT` -> `false`; `HOLD` -> `condHeld[i]`.
4. `condHeld[i] = condOn`; `condFired.push_back(condOn)` — the fold is unchanged.
5. `combineConditionsDnf` folds `condFired` -> `targetOn` -> `applyDelay` as before.

The ticket's own case: `wind BETWEEN` fires -> rule on; `moisture` at 32.7 with band 10..60 yields
`HOLD` with `condHeld = false`, so it contributes `false`; when `wind` leaves the arc the fold
collapses to `false` and the device switches off.

#### **Behaviour differences to be aware of:**

- A rule with a **single** condition behaves exactly as before in the steady states: off + value in
  the band -> stays off; on + value in the band -> stays on; below `low` -> on; above `high` -> off.
  Covered by `test_single_condition_deadband_regression`.
- Two edge cases of a single-condition rule change, both inside a **delay window**, because the
  memory now follows the condition instead of the post-delay rule state:
  - `DELAY_ON` + value drifts into the dead zone: previously the arming was cancelled
    (`unstable_sensor`, because `committedOn` is `false` in `DELAY_ON`), now it keeps counting and
    the rule turns on when the timer expires.
  - `DELAY_OFF` + value drifts into the dead zone: previously the pending off was cancelled and the
    rule went back to `REQUEST_ON` (`committedOn` is `true` in `DELAY_OFF`), now the pending off
    completes.
  In both cases the new behaviour is the consistent one — a value inside the deadband carries no new
  information, so the transition that a real verdict started is not reverted by it. No existing test
  covers these two paths (`test_rule_phase5_delay.cpp` tests `decideDelayTransition` directly), and
  `delayOn` / `delayOff` are 0 for the rules in the reproduction.
- Rules **without** a condition list are untouched, as are STEP rules (`evaluateConditionSet` has no
  hysteresis) and AVERAGE_SENSOR rules (one aggregated value, one hysteresis state — the rule's).

#### **Logging & Observability:**

**What already exists** — `evaluateSensorRule` logs one `EVALUATE_RULES: SENSOR_COND` line per
condition (`uid`, `sensor`, `dir`, `value`, `low`, `high`, `on`) plus a summary line (`mode`, `ops`,
`nConds`, `targetOn`); `evaluateRule` logs the rule verdict (`Rule %s condition MET/NOT MET`).
The per-condition line showed the *result* but not the state it was derived from, which is exactly
what was wrong — from the log one could not tell whether a condition was on because it fired or
because the rule was on.

**What to add** — one row per missing log point:

| Code site (file / method / branch) | `feature` | `action` | `details` fields |
|---|---|---|---|
| `EvaluateRulesUseCase.h::evaluateSensorRule`, per-condition line | `EVALUATE_RULES` | `SENSOR_COND` (extended) | `uid`, `sensor`, `dir`, `value`, `low`, `high`, **`prevOn`** (this condition's own previous output), `on` |

- This use case logs through `log()` / `logSerial()` in the `EVALUATE_RULES: <ACTION> key=value`
  format; the row above keeps it. No new action name is needed: `prevOn` + `on` on the existing line
  make the hold decision of every condition reconstructable, and the existing summary line already
  shows the fold result.
- `SENSOR_COND` is written with `logSerial`, i.e. serial only (`MqttLoggerMode::SerialOnly`), so this
  is a serial-log diagnostic, not an ELK one — unchanged by this fix.

**How to debug from logs** —
(a) The rule-condition lines are serial-only: `pio device monitor -b 115200`, grep `SENSOR_COND`.
For the externally observable half use ELK / `hardware/update`:
`python3 test_scripts/elk_download_logs_cli.py --uid <MODULE_UID> --from <ISO> --to <ISO>` and look at
`devices[]` for the device (`state`, `sensorUid`, `sensorValue`).
(b) Real line shape (serial):
`EVALUATE_RULES: SENSOR_COND uid=ba34a572-… sensor=9C:13:9E:99:41:6C.03.01 dir=up value=32.70 low=10.00 high=60.00 prevOn=0 on=0`
(c) Happy-path trace for the ticket's rule:
1. grep `SENSOR_COND uid=<rule> sensor=<wind>` -> `on=1` while the arc is satisfied;
2. grep `SENSOR_COND uid=<rule> sensor=<moisture>` -> `prevOn=0 on=0` on every tick — the dead-zone
   condition never holds;
3. grep `SENSOR_COND uid=<rule> mode=… targetOn=` -> `targetOn=1` while the wind holds, `targetOn=0`
   on the first tick after it leaves the arc;
4. `hardware/update` for the device -> `state` goes `on` -> `off` within one evaluation interval.
(d) Failure catalog:

| Symptom in logs | Cause | Fix |
|---|---|---|
| `prevOn=1 on=1` for a condition that has never had `on=1` after an `off` state of the rule | hold memory survived an OFF session | check `isRuleHoldSessionActive` — the rule state must leave `ON`/`REQUEST_ON`/`DELAY_ON`/`DELAY_OFF` for the reset to happen |
| `targetOn=1` while every `SENSOR_COND` line shows `on=0` | fold/inputs mismatch (`joinOp` sequence) | inspect `ops=` on the summary line, see `test_rule_dnf_combine.cpp` |
| A condition flips `on=1`/`on=0` every tick | value oscillating around `low`/`high`, not a deadband issue | widen the band, or use `delayOn`/`delayOff` |
| `prevOn=0 on=0` for the condition the user expects to fire | value never crossed `low` (UP) / `high` (DOWN) | compare `value` with the band on the same line |

### Implementation Summary:

One production file changed: `src/Core/Domain/UseCases/Rules/EvaluateRulesUseCase.h`. Hysteresis
memory moved from the rule to the condition: a new `_conditionHoldStates[rule.uid]` vector keeps one
bool per condition, that bool is what `evaluateSensorHysteresis` gets as `previouslyOn` and what a
`HOLD` verdict resolves to, and it is reset whenever the rule leaves its ON session. Only a
condition that fired — or that is still holding after its own trigger — can contribute `true` to the
AND/OR/DNF fold, so a condition sitting in its dead zone can no longer keep an OR rule on. The fold
itself and the verdict function are untouched.
