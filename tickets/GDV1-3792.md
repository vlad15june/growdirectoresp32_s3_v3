# GDV1-3792: hardware/update reports a stale sensorValue — the rule descriptor is latched at the last state change

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3792

---

## Ticket Description

### Problem Statement

`DeviceUpdateDto.sensorValue` is documented as the **current sensor reading**
(`specs: docs/contracts/backend-firmware/02-hardware-update.md`), but firmware publishes the value
that was read at the moment the rule last changed the device state. `evaluateRule` recomputes the
whole sensor descriptor on every tick (`EvaluateRulesUseCase.h:623-629`), while
`executeRuleActions` returns before writing anything when the state did not change
(`:756-758`) — the only writer of `device->sensorUid` / `sensorValue` / `sensorValueLow` /
`sensorValueHigh` is `executeDeviceAction` (`:440-444`), reached on transitions only. Reproduced on
Develop (module `9C:13:9E:99:47:38`, fw 2.18.1): a LUX rule switched a light on at 10:58:02Z with
`sensorValue 7830` and kept reporting `7830` in every `hardware/update` while the live reading of the
same sensor fell 7830 -> 7790 -> 7780 -> 7590; the same was observed on an air-temperature rule
(`27.69999886` for nine consecutive messages). The drift is unbounded — that sensor moved
94800 -> 7590 within 100 minutes without a single state change.

The same latch has a second symptom, described inside this ticket: the rest of the descriptor —
`sensorUid` and the thresholds `sensorValueLow` / `sensorValueHigh` — is frozen for the whole ON
session as well. On `develop` that is invisible because the descriptor is filled from the rule-level
fields (always `conditions[0]`, which is bug GDV1-3755), but it contradicts INV-2 of
`specs: docs/features/rules/tasks/triggered-condition-uid/triggered-condition-uid.md:64` — while the
rule is on, firmware must report the condition group that holds the rule **at the current moment** —
and the wording of `02-hardware-update.md:86` ("Sensor of the condition that actually
triggered/**holds** the rule"). Once GDV1-3755 (MR #10) lands, the descriptor becomes per-condition
and the freeze becomes user-visible: the reported condition stops following hand-off inside an ON
session.

Impact is reporting only — the device card in the app renders the live value from the sensor store
and not from this field (`specs: docs/contracts/frontend-backend/device.md:55-57`), so what suffers
is `DeviceHistory` and every consumer that trusts the contract wording. Hence Low/Minor.

### Solution

Publish the descriptor on every evaluation, not only on transitions:

- on the "state unchanged" path of `executeRuleActions`, copy the descriptor of the fresh evaluation
  result into the device rule context and into the `Device` entity;
- the copied set is exactly the descriptor — `sensorUid`, `sensorValue`, `sensorValueTime`,
  `sensorValueLow`, `sensorValueHigh` — nothing else;
- only while the rule holds the device (state is not `off` / `offByPowerOn` / `none`), so the
  stop report keeps the value that was read when the rule switched the device off, and the "rule is
  off ⇒ nothing is holding it" side of INV-2 is preserved;
- only when the fresh result actually carries a descriptor, when the device rule context belongs to
  **this** rule, and while the device is still rule-driven (`workByRule`).

The rule decision path is untouched: no state, no `switchedAt`, no `_ruleActiveStates`, no delay
timers, no hysteresis input. This closes both symptoms with one change, because both come from the
one gate: the value is refreshed for free, and the descriptor follows whatever `evaluateRule`
computed for the current tick — which after GDV1-3755 is the condition that currently holds the rule.

### Technical Approach

1. Add `isRuleHoldingDeviceState(state)` — the rule holds the device unless the state is `none`,
   `off` or `offByPowerOn`.
2. Add `refreshReportedSensorDescriptor(rule, evaluationResult)`: guard, then copy the five
   descriptor fields into `_deviceRuleContext[rule.deviceUid]` and re-point / assign the matching
   `Device` fields; log `SENSOR_REPORT_REFRESH` when the descriptor actually changed.
3. Call it from the early-return branch of `executeRuleActions` (state unchanged), before returning.
4. Cover both symptoms with native tests: value freshness inside an ON session and descriptor
   (threshold / sensor uid) freshness inside an ON session, plus regressions that the refresh moves
   neither the state nor `switchedAt` and does not run while the rule keeps the device off.

  - return early when there is no device model, when `evaluationResult.sensorUid` is empty (the rule

    survive), or when the state is not a holding state;

  - copy `sensorUid`, `sensorValue`, `sensorValueTime`, `sensorValueLow`, `sensorValueHigh` into the
    stored context, then assign them to the device, re-pointing `device->sensorUid` at the stored
    string (the context owns the storage behind that `const char*`);

    only when one of the four reported fields actually changed, so a steady sensor does not add a
    line per tick.

  before `return true`.
- Nothing else changes: `evaluateRule`, `executeDeviceAction`, `applyDelay`, the hysteresis and the

### **Implementation Details:**

#### **Why the republish is placed in `executeRuleActions`:**

`executeRuleActions` is the function that decides to skip the write, so it is where the skip has to
be narrowed. The alternatives were considered and rejected:

- **Fill the device inside `evaluateRule`.** `evaluateRule` is also called from paths that only want
  a verdict (`getLastEvaluationResult` consumers, protective-shutdown probes); writing to the device
  from a query function would make the write order depend on who asks.
- **Drop the early return and always call `executeDeviceAction`.** That writes ~25 fields including
  `state`, `switchedAt`, `timeOn`, `needToSwitchBack` and the step counters, sets
  `needReportingRuleUid`, and re-runs the `DEVICE_STATE_OFF` merge — a full transition side-effect
  set on every tick. It also changes `DeviceService`'s state signature and thus the update cadence.
- **Refresh `sensorValue` only.** Fixes symptom 1 and leaves symptom 2 (the frozen `sensorUid` and
  thresholds) open, which is the part that breaks INV-2 after GDV1-3755. The whole descriptor is one
  unit — a value that belongs to a different sensor than the reported `sensorUid` would be worse than
  a stale pair.
- **Refresh in all states, including `off`.** Would overwrite the sensor snapshot that accompanies a
  stop report (`ruleStopReason` + `ruleSensorValueStop` + `sensorValue` describe the moment the rule
  released the device) and would report a descriptor for a rule that holds nothing, against INV-2.

#### **Reporting flow (after the fix):**

1. `loop` -> `executeRuleActions(rule)` -> `evaluateRule(rule)` — descriptor recomputed for this
   tick as before.
2. State changed -> unchanged behaviour: `switchedAt` is stamped, `executeDeviceAction` writes the
   full context and the descriptor.
3. State unchanged -> `refreshReportedSensorDescriptor`:
   - rule holds the device and owns the context -> the five descriptor fields are updated in the
     context and on the device; `state`, `switchedAt`, `ruleSensorStartAt/StopAt`,
     `ruleSensorValueStart/Stop`, `ruleStopReason`, the step counters and `_ruleActiveStates` keep
     their transition-time values;
   - otherwise -> nothing happens, exactly as before.
4. `DeviceService::createDeviceUpdateDto` picks `device->sensorUid` / `sensorValue` /
   `sensorValueLow` / `sensorValueHigh` on the next update — now the current reading.

#### **Interaction with the two open MRs on the same file:**

- **GDV1-3755 (MR #10)** computes the descriptor per fired condition inside `evaluateRule` and keeps
  a sticky trigger while the rule is committed on. After both changes the descriptor published every
  tick is the sticky per-condition one, i.e. exactly INV-2/INV-5: it follows a hand-off, and it does
  not flicker while the same condition keeps holding. The stickiness anchor stays
  `_ruleActiveStates[uid].sensorUid` (the transition snapshot), which this change deliberately does
  not touch — the reported descriptor is a report, the anchor is rule state.
- **GDV1-3793 (MR #11)** only changes what `condFired` contains; the descriptor path is unaffected.

#### **Logging & Observability:**

**What already exists** — `evaluateRule` logs the rule verdict (`Rule %s condition MET/NOT MET,
state: …`, serial), `executeDeviceAction` logs `Executing device action - device … state … ruleUid …`
plus `WF_ATTR` on every transition, and `getSensorValue` logs each read under the
`RULE_SENSOR_VALUE_DEBUG` feature (`read sensorUid= value=`). There was **no** log line for the
reporting descriptor on non-transition ticks — precisely because nothing happened there; the
published value could only be recovered from the MQTT payload.

**What to add** — one row per missing log point:

| Code site (file / method / branch) | `feature` | `action` | `details` fields |
|---|---|---|---|
| `EvaluateRulesUseCase.h::refreshReportedSensorDescriptor`, descriptor changed | `EVALUATE_RULES` | `SENSOR_REPORT_REFRESH` | `uid` (rule), `deviceUid`, `state`, `sensor`, `value`, `low`, `high` |

- This use case logs through `log()` / `logSerial()` in the `EVALUATE_RULES: <ACTION> key=value`
  format; the row keeps it. `SENSOR_REPORT_REFRESH` is written with `logSerial`
  (`MqttLoggerMode::SerialOnly`) like the other per-tick rule lines, so it is a serial diagnostic;
  the externally observable half is the `hardware/update` payload itself, which is in ELK.
- The guard branches are intentionally silent: they are the normal steady state (rule off, device
  taken over, rule without descriptor) and would produce one line per rule per second.

**How to debug from logs** —
(a) Serial: `pio device monitor -b 115200`, grep `SENSOR_REPORT_REFRESH`. ELK / payload side:
`python3 test_scripts/elk_download_logs_cli.py --uid <MODULE_UID> --from <ISO> --to <ISO>`, then
compare `devices[].sensorValue` for the device with `sensors[].value` of the sensor named in
`devices[].sensorUid` in the same or neighbouring message.
(b) Real line shape (serial):
`EVALUATE_RULES: SENSOR_REPORT_REFRESH uid=bf9a859f-2481-4b81-8529-b3315fff0bd9 deviceUid=9C:13:9E:99:47:38.02 state=on sensor=9C:13:9E:9A:53:30.03.07 value=7590.00 low=150001.00 high=199001.00`
(c) Happy-path trace for the ticket's light rule:
1. grep `Executing device action - device 9C:13:9E:99:47:38.02 state on` -> the transition, one line;
2. grep `SENSOR_REPORT_REFRESH … deviceUid=9C:13:9E:99:47:38.02` -> one line per reading change,
   `value=` decreasing 7830 -> 7790 -> 7780 -> 7590 while `state=on` and no new transition line
   appears in between;
3. in ELK, `devices[]` for `.02` -> `sensorValue` follows the same sequence, and equals the
   `sensors[]` value of `9C:13:9E:9A:53:30.03.07` in the same window (that equality is the fix);
4. `low=` / `high=` stay at the rule thresholds, `switchedAt` stays at the transition timestamp.
(d) Failure catalog:

| Symptom in logs | Cause | Fix |
|---|---|---|
| `devices[].sensorValue` constant while `sensors[].value` moves and no transition line in between | refresh did not run | check the guards: `state=` must not be `off`, the device must still be `workByRule` (a stop report clears it), the rule must own `_deviceRuleContext[deviceUid]` |
| No `SENSOR_REPORT_REFRESH` at all for a sensor-driven device | rule never wrote the device context, or the rule is evaluated as inactive (no descriptor in the result) | grep `Executing device action` for the device and `SENSOR_EVAL uid=` for the rule |
| `sensorValue` moves but `sensorUid` does not, on a multi-condition rule | expected on `develop`: the descriptor is rule-level until GDV1-3755 lands | — |
| `switchedAt` changes on a tick without a state change | a transition really happened, or the refresh was widened beyond the descriptor | the refresh writes five fields only; compare with `Executing device action` lines |

### Implementation Summary:

One production file changed: `src/Core/Domain/UseCases/Rules/EvaluateRulesUseCase.h`. The reporting
descriptor is now republished on every evaluation instead of only on state transitions: the
unchanged-state branch of `executeRuleActions` copies `sensorUid`, `sensorValue`, `sensorValueTime`,
`sensorValueLow` and `sensorValueHigh` from the fresh evaluation result into the device rule context
and onto the `Device`, while the rule holds the device and owns that context. Both symptoms of the
one latch are closed: the value in `hardware/update` is the current reading, and the descriptor
(sensor uid + thresholds) follows the current tick instead of being frozen for the whole ON session —
which is what INV-2 of the triggered-condition-uid spec requires and what makes GDV1-3755's
per-condition descriptor observable inside an ON session. No decision, timer, transition timestamp or
committed rule state is touched.

the thresholds, the sensor uid, the multi-condition value, and the state/`switchedAt` regression,
which also asserts the refreshed value) and the sixth (descriptor frozen after the rule switched the
device off) passes both ways. The full native suite is green — 541 of 541 test cases, i.e. the 535 of
the `develop` baseline plus the 6 new ones. The suite is run with `-fno-sanitize=undefined` because
