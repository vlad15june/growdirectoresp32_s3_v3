# GDV1-3211: Check Module Deletion Status on Every Startup

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3211

---

## Ticket Description

### Problem Statement

After implementing the delete command functionality (GDV1-3169), modules can be remotely wiped via MQTT. However, if the module is offline or misses the delete command notification, it will continue operating in configured mode until the command is received. This creates an inconsistency where a module deleted from the server remains operational without the server's knowledge.

### Solution

Implement a startup check that verifies module deletion status with the server after every reset. This ensures that:
- Modules that missed the delete command while offline are caught on next startup
- Deleted modules are automatically reset to unconfigured state (mode 42 - USER_CAN_CONFIGURE)
- System consistency is maintained between server and hardware states
- No deleted modules remain in CONFIGURED_DONE mode after restart

### Technical Approach

Add a verification step during module initialization (after WiFi/API connection is established) to:
1. Query the server using existing `checkIsModuleDeleted()` REST API endpoint
2. If server confirms module is deleted (returns `isDeleted: true`)
3. Set module mode to USER_CAN_CONFIGURE (42) using existing `settings->setConfigured(ModuleModeEnum::USER_CAN_CONFIGURE)`
4. Clear all module data using existing `ClearModuleDataService::clearAllData()`
5. Restart module to apply changes

This check should only run when module is in CONFIGURED_DONE mode and network connectivity is established.

### Related Tickets

- **GDV1-3169**: Delete Command for remote module wipe (implements `checkIsModuleDeleted()` API and `ClearModuleDataService`)
- **GDV1-3182**: Automatic Module Reset After Prolonged Offline State (similar diagnostic/health check pattern in startup flow)

**Implement `checkModuleDeletionOnStartup()` method:**
```cpp
inline void ModuleSetupService::checkModuleDeletionOnStartup()
{
    // Defensive check: verify module config and settings are available
    if (!moduleConfig || !moduleConfig->getSettings())
    {
        return;
    }
    
    // Defensive check: verify module is in correct mode (redundant but safe)
    // Note: This method is called from ConfigureDoneModeConfigure() which only runs in CONFIGURED_DONE mode
    ModuleModeEnum currentMode = static_cast<ModuleModeEnum>(
        moduleConfig->getSettings()->getIfConfigured()
    );
    
    if (currentMode != ModuleModeEnum::CONFIGURED_DONE)
    {
        log("SETUP: Skipping deletion check - module not in CONFIGURED_DONE mode");
        return;
    }

    // Verify all required dependencies are available
    if (!hybridApiService || !clearModuleDataService || !arduinoAdapter)
    {
        log("SETUP: Cannot check module deletion - missing required services");
        return;
    }

    log("SETUP: Checking if module was deleted from server...");

    // Query server for deletion status
    bool isDeleted = false;
    try
    {
        isDeleted = hybridApiService->checkIsModuleDeleted();
    }
    catch (...)
    {
        log("SETUP: Failed to check deletion status - continuing normal operation");
        return;
    }

    if (isDeleted)
    {
        log("SETUP: Module is marked as DELETED on server - initiating factory reset");
        
        // Set module to unconfigured mode
        moduleConfig->getSettings()->setConfigured(ModuleModeEnum::USER_CAN_CONFIGURE);
        log("SETUP: Module mode set to USER_CAN_CONFIGURE");
        
        // Clear all data
        clearModuleDataService->clearAllData();
        log("SETUP: All module data cleared");
        
        // Restart to apply changes
        log("SETUP: Restarting module to complete reset...");
        arduinoAdapter->delay(1000); // Allow logs to flush
        arduinoAdapter->restart();
    }
    else
    {
        log("SETUP: Module deletion check passed - continuing normal operation");
    }
}
```

### Bug Fix (2026-01-08):

**Problem:** Original implementation used `wasSensorScanPerformed` flag to skip check on first boot. This caused issues:
- Flag only set after sensor scanning (works for sensor modules)
- **Device/relay/hydro modules without sensors never set this flag**
- Deletion check was permanently disabled for non-sensor modules
- Server returned `isDeleted: true` for newly configured modules not yet registered

**Solution:** Introduced `wasInitialSyncCompleted` flag:
- Set after **first successful module structure send** to server
- Works for **all module types** (sensor, device, relay, hydro, dimmer)
- Tied to actual registration moment (structure upload = server registration)
- More accurate indicator of "module is registered on server"
- Fixes false positives from server returning deleted status for unregistered modules

## Technical Design Decisions

### Why Check in ConfigureDoneModeConfigure()?

1. **Network Dependency**: Requires active WiFi connection to query server
2. **Scope**: Only relevant for configured modules (CONFIGURED_DONE mode)
3. **Timing**: After WiFi but before MQTT ensures connectivity without overhead
4. **Logic**: Unconfigured modules (USER_CAN_CONFIGURE, AP_TEST_MODE) don't need check

### Why Use wasInitialSyncCompleted Instead of wasSensorScanPerformed?

**Original Issue:**
- `wasSensorScanPerformed` only applies to sensor modules
- Device/relay/hydro modules without sensors never perform sensor scans
- These modules would never set the flag, permanently disabling deletion check
- Server returns `isDeleted: true` for modules not yet registered in database

**Solution with wasInitialSyncCompleted:**
1. **Universal**: Works for all module types (sensor, device, relay, hydro, dimmer)
2. **Accurate**: Tied to actual server registration (structure upload)
3. **Timing**: Set in `OnChangeLocalIpUseCase` after successful `sendToServerModuleStructure()`
4. **Reliable**: First successful structure send = module is registered on server
5. **Clean**: Prevents false positives from server treating unregistered modules as deleted

### First Boot Sequence:

```
1. Module configured via web → mode 106 → restart
2. Boot → WiFi connect → OnChangeLocalIpUseCase fires
3. Module structure sent to server → SUCCESS
4. wasInitialSyncCompleted = 1 (saved to EEPROM)
5. Subsequent boots → deletion check runs normally
```

### Why Not in DiagnosticService?

1. **Purpose**: `DiagnosticService` monitors runtime health, not startup state
2. **Frequency**: Deletion check needed once per boot, not periodically
3. **Timing**: Must run before MQTT/services initialize, not during runtime loop
4. **Separation of Concerns**: Startup logic belongs in setup service, not diagnostic service

### Error Handling Strategy

**Network Failures:**
- Log error and continue normal operation
- Don't block startup on network issues
- Server unavailability shouldn't prevent module operation

**Missing Dependencies:**
- Check for null pointers before API calls
- Log warning if services unavailable
- Graceful degradation - skip check rather than crash

**State Consistency:**
- Always set mode before clearing data
- Always restart after clearing data
- Atomic operations where possible
- EEPROM persistence ensures flag survives power cycles
