# GDV1-3169: ADD delete command for DG v4 (s3)

**Jira Link:** https://growdirector.atlassian.net/browse/GDV1-3169

---

## Development Plan

### **Overview**
Implement a delete command functionality that allows the server to remotely wipe and reset an ESP32 module to its unconfigured state when deleted from the system. The command will be received via MQTT, verified with the server via REST API, and then execute a factory reset using the existing `ClearModuleDataService`.

---

### **Instructions:**

1. **Add new command type to CommandDto**
   - Add support for `DeleteGdCommandNotification` message type
   - The command will arrive via MQTT topic `GrowDirectorMqttTopic/{moduleUid}`

2. **Add verification endpoint to REST API**
   - Implement `checkIsModuleDeleted()` method to call `/api/v1/HardWare/is_deleted` endpoint
   - Returns boolean indicating if module is marked as deleted on server

3. **Implement delete command handler**
   - Add `DeleteModule` to `ModuleCommandEnum`
   - Implement handler in `ModuleCommandExecutionUseCase`
   - Send acknowledgment via `CommandResultDto` back to server
   - Verify deletion status with server before proceeding
   - Execute `clearAllData()` using `ClearModuleDataService`

4. **Update command processing flow**
   - Modify `CommandService` to recognize and route delete commands
   - Update `TopicHandlers` to process `DeleteGdCommandNotification`

## Ticket Description (from Jira)

### Flow

1. **MQTT Message Reception (getMqtt)**
   - Listens for MQTT messages on the hardware command topic
   - Parses incoming JSON messages for notification type
   - When type == "DeleteGdCommandNotification" is received, triggers the deletion process

2. **Deletion Processing (processDeleteGdCommand)**
   - **Immediate Response**: Sends an acceptance acknowledgment back to the server via MQTT topic `hardware/command_result/grow_director_uid`
   - **Verification**: Calls checkIsModuleDeleted() to verify with the server that the module is actually marked as deleted
   - **If Confirmed Deleted**: Clears all data (see ticket GDV1-3132 - ClearModuleDataService)

3. **Server Verification (checkIsModuleDeleted)**
   - Makes HTTP GET request to `/api/v1/HardWare/is_deleted` endpoint
   - Includes authentication token and module's UID (grow_director_uid)
   - Parses server response to get isDeleted boolean flag
   - Returns `false` if request fails or module is not marked as deleted
   - Handles connection errors by setting offline counters

### Security & Safety

- The deletion only proceeds if the server confirms the module is marked as deleted
- Maintains logging at TRACE level for debugging and audit purposes
- Handles HTTP failures gracefully to prevent accidental wipes

### Result

The module is factory reset to an unconfigured state, ready for reconfiguration or disposal, while maintaining the firmware intact.

## Bug Fix: Module Mode Not Reset After Deletion

**Date:** 2025-01-08

### Issue:
After successful delete command execution and factory reset, module remained in `CONFIGURED_DONE` (106) state instead of resetting to `USER_CAN_CONFIGURE` (42).

### Root Cause:
`ClearModuleDataService` cleared all data files (sensors, rules, sensor types) but did not reset the module mode stored in EEPROM/Settings. After reboot, module read old configuration status from persistent storage.

### Solution:
Updated `ClearModuleDataService` to reset module mode after clearing all data by calling `settings->setConfigured(ModuleModeEnum::USER_CAN_CONFIGURE)` which saves the new mode to EEPROM.

### Files Changed:
- ✅ `Application/Services/ClearModuleDataService.h` - Added mode reset logic to set USER_CAN_CONFIGURE after clearing data

### Expected Behavior:
After delete command and factory reset, module will reboot in `USER_CAN_CONFIGURE` (42) state, ready for fresh configuration.
